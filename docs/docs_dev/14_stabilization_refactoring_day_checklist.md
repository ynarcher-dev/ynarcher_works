## 3. 사용자 승인 요청 작성법

크리티컬 이슈는 전문 용어만 나열하지 말고 아래 양식을 복사하여 작성합니다. 문장은 짧게 쓰고, 어려운 단어 뒤에는 반드시 쉬운 뜻을 붙입니다.

```md
### [결정 필요] 한 줄 제목

* 무엇을 발견했나요?
  * 아주 쉬운 설명 1~2문장
* 왜 문제인가요?
  * 지금 두면 생길 수 있는 일을 1~2문장
* 쉬운 비유
  * 예: "문은 잠겨 있지만 창문이 열려 있는 것과 비슷합니다."
* 지금 고치면 좋은 점
  * 사용자가 얻는 이점 1~2개
* 고칠 때 생길 수 있는 위험
  * 로그인 중단, 기존 화면 변경, 데이터 영향 등 실제 위험을 1~2개
* 제가 추천하는 선택
  * A/B/C 중 하나와 추천 이유 한 문장
* 선택해 주세요.
  * A. 지금 수정합니다.
  * B. 이번에는 건너뛰고 메모만 남깁니다.
  * C. 더 자세한 설명을 먼저 듣습니다.
* 승인 전 상태
  * 관련 코드는 변경하지 않았습니다.
```

### 설명 예시

```md
### [결정 필요] 운영 CORS 설정을 더 엄격하게 할까요?

* 무엇을 발견했나요?
  * 허용 사이트 목록이 비어 있으면 다른 사이트의 요청도 받아줄 수 있습니다.
* 왜 문제인가요?
  * 나쁜 사이트가 우리 서버 문을 두드릴 수 있습니다.
* 쉬운 비유
  * 초대 손님 명단이 없을 때 모든 사람을 들여보내는 것과 비슷합니다.
* 지금 고치면 좋은 점
  * 정해진 WORKS와 GUEST 사이트에서 온 요청만 받을 수 있습니다.
* 고칠 때 생길 수 있는 위험
  * 주소를 잘못 적으면 정상 사용자도 잠시 접속하지 못할 수 있습니다.
* 제가 추천하는 선택
  * 운영 주소를 확인한 뒤 A를 선택하는 것을 추천합니다.
* 선택해 주세요.
  * A. 운영 주소를 확인하고 수정합니다.
  * B. 이번에는 메모만 남깁니다.
  * C. 설정 화면과 영향 범위를 먼저 보여주세요.
* 승인 전 상태
  * 관련 코드는 변경하지 않았습니다.
```

- [ ] 운영 환경에서 허용 목록이 비어 있으면 전체 허용되는 구조인지 기록합니다.

- [ ] 저장소에 실제 토큰, 비밀번호, 서비스 키가 커밋되었는지 값은 출력하지 않고 존재 여부만 확인합니다.
- [ ] 실제 Secret 값을 문서, 로그 또는 사용자 메시지에 복사하지 않습니다.

### C-5. 보안 점검 결과 정리

- [ ] 발견 사항을 `높음`, `중간`, `낮음`으로 분류합니다.
- [ ] `높음`은 모두 쉬운 설명 양식으로 사용자 승인 요청을 작성합니다.
- [ ] `중간`과 `낮음`은 오늘 안전하게 고칠 수 있는 것과 추후 작업으로 나눕니다.
- [ ] 코드 변경 없이도 가능한 문서 보완 사항을 기록합니다.

## 8. Phase D — 작은 리팩토링

> [!NOTE]
> 파일을 짧게 만드는 것 자체가 목표가 아닙니다. 읽기 쉽고, 한 부분을 바꿀 때 다른 부분이 덜 깨지게 만드는 것이 목표입니다.

### D-1. 대상 선정

- [ ] 최근 자주 변경되고 500줄을 넘는 파일을 찾습니다.
- [ ] 파일별로 UI, 상태, API 호출, 계산 로직이 섞여 있는지 확인합니다.
- [ ] 테스트가 있거나 먼저 테스트를 추가할 수 있는 파일만 오늘 리팩토링 후보로 선정합니다.
- [ ] 현재 사용자 변경과 겹치는 파일은 후보에서 제외합니다.
- [ ] 한 파일을 고치기 위해 여러 워크스페이스의 업무 규칙이 달라질 수 있으면 크리티컬 이슈로 보류합니다.

### D-2. 우선 검토 후보

- [ ] `packages/ui/src/components/DataTable.tsx`는 현재 사용자 변경과 겹치는지 먼저 확인합니다.
- [ ] `apps/works/src/features/fund/hooks.ts`의 조회·변환·mutation 책임을 구분해 기록합니다.
- [ ] `apps/works/src/features/fund/InvestmentFormModal.tsx`의 폼 상태와 화면 표시 분리 가능성을 기록합니다.
- [ ] `apps/works/src/features/networks/hooks.ts`의 반복 쿼리와 캐시 키를 확인합니다.
- [ ] `apps/works/src/features/startup/StartupDetailForm.tsx`의 필드 그룹 분리 가능성을 확인합니다.

### D-3. 안전한 변경만 수행

- [ ] 공개 API와 사용자 화면 동작을 바꾸지 않는 작은 추출만 수행합니다.
- [ ] 순수 계산 함수 또는 표시 전용 하위 컴포넌트를 한 번에 하나씩 분리합니다.
- [ ] 의미 없는 이름 변경이나 저장소 전체 포맷팅은 하지 않습니다.
- [ ] 한 리팩토링 작업의 변경 파일 수를 가능한 5개 이하로 유지합니다.
- [ ] 변경 전후 테스트 결과가 같음을 확인합니다.
- [ ] 리팩토링마다 `lint`, 관련 테스트, `typecheck`를 실행합니다.

## 9. Phase E — CI/CD·성능·접근성 점검

### E-1. CI/CD 읽기 전용 점검

- [ ] `.github/workflows/ci.yml`의 실행 명령과 로컬 검증 명령이 같은지 확인합니다.
- [ ] `.github/workflows/deploy.yml`이 CI 성공을 기다린 뒤 실행되는지 확인합니다.
- [ ] 배포 워크플로에 lint·test·RLS 검증이 포함되거나 선행 조건으로 연결되는지 확인합니다.
- [ ] 배포 후 WORKS/GUEST smoke test가 있는지 확인합니다.
- [ ] CI/CD 변경 제안은 크리티컬 이슈로 기록하고 승인 전 수정하지 않습니다.

### E-2. 성능 점검

- [ ] 네트워크 요청이 반복되는 명백한 N+1 후보를 검색합니다.
- [ ] 큰 목록이 서버 페이지네이션 없이 전체 조회되는 지점을 기록합니다.
- [ ] route lazy loading 또는 큰 번들 후보를 기록합니다.
- [ ] 측정 없이 `useMemo`, `useCallback`, memoization을 대량 추가하지 않습니다.
- [ ] 성능 문제는 추측과 측정 결과를 구분하여 기록합니다.

### E-3. 접근성 점검

- [ ] 버튼과 입력 요소의 접근 가능한 이름(label 또는 `aria-label`) 누락을 표본 점검합니다.
- [ ] 모달의 초기 포커스, 닫기 후 포커스 복귀, ESC 동작을 표본 점검합니다.
- [ ] 영상·음성 요소의 자막 또는 대체 안내 정책을 확인합니다.
- [ ] 색만으로 상태를 구분하는 화면이 있는지 기록합니다.
- [ ] 접근성 라이브러리 도입이 필요하면 사용자 승인 요청을 작성합니다.

오늘 작업을 마쳤습니다.

   * 체크 완료 항목과 관련 파일을 적습니다.

3. 확인 결과
   * lint:
   * typecheck:
   * test:
   * build:

4. 아직 손대지 않은 위험한 문제
   * 문제마다 쉬운 비유, 좋은 점, 수정 위험, 추천 선택을 적습니다.

5. 사용자 결정이 필요한 것
   * A/B/C로 답할 수 있게 질문합니다.

   * 가장 먼저 할 일 1~3개만 적습니다.
