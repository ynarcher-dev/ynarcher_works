## 1. 작업 범위 규칙

* **범위는 사용자가 정합니다.** 요청받은 범위만 수행하고, 범위를 임의로 넓히거나 줄이지 않습니다.
* **PROGRESS.md에서 다음 작업을 선정하지 않습니다.** `PROGRESS.md`는 과거 추적 기록이며 작업 지시서가 아닙니다.
* **명시적 사전 승인은 그것으로 충분합니다.** 사용자가 이미 범위를 승인했다면 같은 내용을 다시 묻지 않고 바로 수행합니다. 승인은 승인된 범위에만 유효하며, 다음 작업으로 자동 연장되지 않습니다.
* 되돌리기 어려운 행위(커밋·푸시·배포·운영 DB 변경·외부 발송)는 **해당 행위에 대한 승인이 있을 때만** 수행합니다.
* 작업 중 판단이 갈리는 지점이 생기면, 영향이 없는 부분은 먼저 끝내고 갈리는 지점만 가정 또는 질문으로 분리해 보고합니다.
* **특정 세션의 한시적 범위는 이 문서에 적지 않습니다.** 이 문서는 지속 규칙만 담으며, 개별 작업의 허용·제외 범위는 그때 사용자가 승인한 지시가 정합니다.

## 2. 프로젝트 개요 (현재 구현 기준)

AC/VC 업무와 전사 운영(ERP 성격 — 인사·재무·자산·전자결재)을 묶은 통합 플랫폼입니다. 내부 `WORKS`와 외부 `GUEST`를 별도 SPA로 운영하고 백엔드는 Supabase를 공유합니다.

* **모노레포**: Turborepo — `apps/works`, `apps/guest`, `packages/ui`(순수 UI), `packages/master-data`, `supabase`, `infra`.
* **실행 모델**: React 19 + TypeScript + Vite SPA, S3 + CloudFront 정적 호스팅, Supabase(PostgreSQL/RLS/Storage/Edge Functions/RPC). Next.js 서버 런타임은 없으며 "서버 액션"은 Edge Function/RPC를 가리킵니다.
* **WORKS 라우트**(`apps/works/src/router.tsx` 확인): `office`·`my-office`·`startup`·`networks`·`project`·`fund`·`mna`(`buyers`/`sellers`)·`management`·`approval`·`admin`·`styleguide`·`me`. 구 `ac` 경로는 `LegacyRedirect`가 받습니다.
* **GUEST 라우트**(`apps/guest/src/router.tsx` 확인): 로그인, 사업 개요, 공지, Q&A, 지원, 모듈(글·링크·파일), 마이페이지, 공개 모듈 링크.

## 3. 확정된 아키텍처 결정 (변경 시 사용자 확인 필요)

아래는 현재 구현에서 확인되는 골격만 추립니다. 결정 배경과 전문은 [CLAUDE_HISTORY_2026-09-12.md](./CLAUDE_HISTORY_2026-09-12.md)에 보존되어 있습니다.

* **워크스페이스**: 전사 포털은 `OFFICE`, 스타트업 업무 화면은 `STARTUP`. 사업 워크스페이스는 `PROJECT`(구 AC, 2026-09-09 개명)와 `M&A/PE` 둘입니다.
* **마스터 데이터 SSOT**: 스타트업 물리 원장은 `public.startups`, 권한 판정 키는 `startup`. 네트워크는 `public.networks` 하나로 통합되어 구분과 국가가 직교한 두 축입니다.
* **사업 공용 모듈**: PROJECT와 M&A는 `apps/works/src/features/program` 구현을 공유하고, 차이는 워크스페이스 설정 객체로 주입합니다. 모듈·담당자·글·링크·참가자 명부는 한 벌의 원장을 쓰고 소속은 `entity_key`가 답합니다.
* **게스트 계정**: 임직원과 같은 `public.users`에 들어오고 ADMIN이 소유합니다. 하나의 계정이 여러 대상·맥락(PROJECT·FUND·M&A 등)에 연결되는 구조이며, 계정 단위·연결 단위·식별 정책의 세부는 [3_9_1_guest_unified_account.md](../docs_planning/3_9_1_guest_unified_account.md)와 [0_as_built_reverse_spec.md](../docs_planning/0_as_built_reverse_spec.md), 그리고 실제 스키마·코드가 답합니다. **여기서 단일 정책으로 단정하지 않으며, 인용 전 대조가 필요합니다.**
* **게스트 로그인·독립 계정 정책(2026-09-14 사용자 확정)**: 정본은 [3_9_1 §6](../docs_planning/3_9_1_guest_unified_account.md)과 [3_9_3](../docs_planning/3_9_3_guest_ledger_identity_policy.md)입니다. GUEST는 **이름·소속·이메일만 가진 독립 계정**이며 전화번호와 원장 관계를 저장·조회·인증·알림에 사용하지 않습니다. 원장 선택은 세 값을 입력 폼으로 복사하는 편의 기능이고 원장 ID를 저장하거나 이후 동기화하지 않습니다. 인증은 **이메일 아이디 + 개인 비밀번호**, **고정 초기 비밀번호**(설정 전에만 유효), 설정 전 세션 불발급을 유지합니다. 프로젝트·M&A·FUND 참여와 업무 기록은 계정 프로필과 별개로 보존합니다. 이 정책을 초대 토큰 강제 전환이나 초기 로그인 경로 차단으로 대체하려면 사용자 확인이 필요합니다. 잔여 위험 기술은 [SECURITY_REVIEW.md](../SECURITY_REVIEW.md) `F-0`, 확인 과제는 [MASTER_PLAN.md](../MASTER_PLAN.md) `AUTH-1`이 가집니다.
* **권한·RLS**: 기저 헬퍼는 `current_app_user_id()`/`current_app_role()`이고 업무 헬퍼는 이를 경유합니다. UI에서 숨기는 것은 보안이 아닙니다 — 서버(RLS/RPC/Edge Function)가 강제합니다.
* **생성자·담당자·기여자 3축**: 기여 로그(`entity_contributions`)의 **행위자 칸은 DB 트리거가 소유**합니다 — 클라이언트가 보낸 `user_id`는 무시되고 현재 세션 사용자로 덮어써집니다. 다만 "클라이언트가 INSERT하지 않는다"는 뜻은 아닙니다. 직접 쓰기는 승인된 RLS 정책과 테이블 권한이 함께 허용하는 경로에서만 이뤄지며, 현재 구현은 `authenticated`의 INSERT를 허용합니다(정책·권한·테스트가 정본입니다).
* **스타일링**: Tailwind CSS. 값의 SSOT는 `tailwind-preset.mjs`, 맥락별 토큰 매핑은 `packages/ui/src/densityScale.ts`입니다. 상호참조 값은 배지가 아니라 텍스트 링크(`RefLinkList`)로 세웁니다.

> [!NOTE]
> 아카이브에 남은 세부 정책은 자동으로 유효하지 않습니다. 인용하기 전에 현재 코드 또는 승인된 결정과 대조하고, 대조하지 못했다면 미검증임을 밝힙니다.

## 4. 개발 수칙

* **분량 기준(파일 500줄 / 컴포넌트 250 / 훅 150 / 함수 50)은 과거에 세운 목표치**입니다. 줄 수만으로 위반을 선언하거나 자동으로 리팩터링에 들어가지 않습니다. 분리 여부는 책임 경계·변경 위험·테스트 가능성으로 판단하고, 상세 기준은 [1_development_stack.md](../docs_dev/1_development_stack.md)와 [CLAUDE_HISTORY_2026-09-12.md](./CLAUDE_HISTORY_2026-09-12.md)의 구 규칙을 참고합니다.
* DB 변경은 마이그레이션으로만. 모든 테이블 RLS 필수, Default Deny.
* 새 테이블·RPC·Storage 정책·`SECURITY DEFINER` 함수는 [11_migration_security_gate.md](../docs_dev/11_migration_security_gate.md)의 보안 게이트를 통과해야 완료로 봅니다.
* **삭제는 민감 동작입니다.** 기본은 소프트 삭제이며, 물리 삭제가 필요하면 그때마다 [4_security_privacy_policy.md](../docs_dev/4_security_privacy_policy.md)·[5_backup_retention_privacy.md](../docs_dev/5_backup_retention_privacy.md)·[7_database_design_guidelines.md](../docs_dev/7_database_design_guidelines.md)의 정책과 승인된 예외, 그리고 서버 측 권한·데이터 수명주기를 확인합니다. 예외 목록은 이 문서에 고정하지 않습니다 — 원장·ADMIN 경로의 현재 구현은 문서와 다를 수 있습니다.
* **검증은 변경 범위에 맞춰 최소한으로 수행합니다.** 문서·문구만 바꾸면 diff와 필요한 링크·표기만 확인합니다. 코드 변경은 변경 파일 린트·관련 테스트와 영향받은 앱의 타입 검사를 기본으로 하고, 빌드는 번들·의존성·설정·공용 UI 영향이 있을 때 수행합니다. 전체 게이트는 전역 영향, 관련 검사 실패로 영향 범위가 불명확한 경우, 사용자 요청 또는 CI에서 수행합니다. **통과 여부는 실제 실행 결과로만** 보고합니다.
* **구현은 사실, 문서는 정책 참조입니다.** 문서와 코드가 다르면 코드는 "현재 이렇게 동작한다"는 사실 근거로, 문서는 "이렇게 하기로 했다"는 정책 참조로 각각 취급하되, **그 문서가 실제로 승인되었는지와 지금도 유효한지는 인용 전에 따로 확인합니다.** 불일치와 미해결 정책 판단은 `CURRENT_STATUS.md`에 기록합니다. **기존 구현이 존재한다는 사실만으로 보안·정책 위반이 정당화되지 않으며, 잘못된 동작을 승인된 정책으로 다시 쓰지 않습니다.**

### 기본 작업 흐름 — 구현 → 권한·실패 확인 → 문서 → 리뷰

사용자가 기능이나 변경의 범위를 승인하면, 아래 네 단계는 **그 승인 하나로 이어서 진행합니다.** 단계마다 다시 묻거나 제안 상태로 멈추지 않습니다.

* **승인의 범위**: 승인된 범위 안에서 필요한 구현·테스트·문서·리뷰 반영과 되돌릴 수 있는 수정이 포함됩니다. 승인되지 않은 과제를 임의로 끌어오거나 확정된 정책을 바꾸는 일은 포함되지 않습니다. **이미 받은 허가는 유지되며, 같은 행위를 다시 묻지 않습니다.** 되돌리기 어려운 행위(커밋·푸시·배포·운영 DB 변경·외부 발송)의 기준은 §1 그대로이며 이 흐름이 넓히지 않습니다.
* **역할과 리뷰**: 기본은 작업자가 구현·관련 검증·최종 diff 확인까지 수행합니다. 별도 에이전트나 독립 리뷰는 사용자가 요청하거나 인증·권한 경계, 데이터 파괴 가능성, 광범위한 공용 계약 변경에 필요할 때만 진행합니다. 독립 리뷰가 필요한데 수행할 수 없으면 그 항목만 리뷰 대기로 보고하며, 일반 수정은 별도 리뷰어를 기다리지 않습니다. 실제로 수행하지 않은 리뷰를 완료로 적지 않습니다.
* **검사 결과 재사용**: 같은 코드 상태와 환경에서 명령·검사 범위·종료 코드가 확인되는 성공 결과는 리뷰에서도 재사용합니다. 리뷰어가 다르다는 이유로 재실행하지 않습니다. 이후 관련 코드·의존성·설정이 바뀌었거나 결과가 불완전하거나 결함이 의심될 때만 영향받은 검사를 다시 실행합니다. 단언 전체 실행 여부와 정상 종료를 확인하며, `not ok` 검색만으로 성공을 판단하지 않습니다.
* **완료의 폭**: 변경한 동작의 정상 경로와 관련 실패 경로를 확인합니다. 인증·권한 경계를 바꾸면 영향받은 역할·회사·워크스페이스의 허용·거절을, 세션 처리를 바꾸면 관련 만료·위조 사례를 확인합니다. 저장소·외부 제공자 실패도 그 경로를 바꿀 때 검사합니다. 모든 기능에 전체 보안 사례를 반복 적용하지 않습니다. Edge 코드 변경은 함수 타입체크와 관련 테스트, DB 변경은 최종 변경 묶음에 격리 재생과 관련 pgTAP을 수행합니다. 실패는 고치거나 막힌 이유를 적고, 정책·권한·단언을 약화해 통과시키지 않습니다.
* **새 테이블·API를 만들 때**: RLS와 함께 **최소 GRANT/REVOKE를 명시**하고 실제 유효 권한을 확인합니다. 앱 롤(`anon`/`authenticated`)의 `TRUNCATE`·`REFERENCES`·`TRIGGER`는 정당한 승인 사유가 없는 한 두지 않습니다. 허용 한 쌍과 거절 한 쌍을 함께 남깁니다. 세부 점검 항목은 [11_migration_security_gate.md](../docs_dev/11_migration_security_gate.md)가 가지며 여기서 되풀이하지 않습니다.
* **문서와 기록**: 사용자 동작·계약·정책·운영 절차가 바뀌어 기존 설명이 틀리게 될 때만 해당 정본 문서를 고칩니다. 문구·스타일·내부 구현 수정마다 `CURRENT_STATUS.md`나 진행 이력을 갱신하지 않습니다. 검사 결과는 최종 응답이나 기존 작업 기록 한 곳에 짧게 남기고, 별도 보고서 파일을 만들지 않습니다. 관련 없는 문서 불일치는 이번 작업으로 끌어오지 않습니다.
* **병렬 작업과 중단**: 여러 Claude가 동시에 일할 때는 서로 독립적인 파일·인터페이스만 맡고 파일 소유자를 정합니다. 같은 파일을 고쳐야 하면 순서대로 진행하고, 합치는 시점에 리뷰를 거칩니다. 사용량 한도나 프로세스 중단으로 끊기면 **실제 상태·재개 지점·다음 할 일**을 기존 작업 기록에 남깁니다. 예약 실행은 실제로 설치되어 우리가 소유한 경우에만 씁니다.

## 5. 문서 작업 규칙

* 격식체("~합니다") 서술, 불릿은 `* **볼드 리드**: 설명` 패턴, 섹션 구분은 `---`, 강조는 `> [!NOTE]` 콜아웃.

* 파일 인코딩은 UTF-8, 문서 삭제·이동은 사용자 승인이 있을 때만 합니다.

## 6. 커밋 컨벤션 (커밋이 승인된 경우)

* 형식: `<type>(<scope>): <제목>` — type은 `feat`/`fix`/`docs`/`refactor`/`chore`/`test`, scope는 워크스페이스 또는 영역(`office`, `startup`, `project`, `ui`, `db`, `auth` 등).
* 제목과 본문은 한국어로 작성하고, 문서 수정은 `docs(<폴더>)` 스코프를 씁니다.
* 커밋·푸시는 사용자가 요청했을 때만 수행합니다.
