# 개발·배포·운영 가이드 (Operations)

본 문서는 로컬 개발부터 검토, 배포, 장애 대응과 복구까지의 공통 절차를 정의합니다. 상세 보안·배포·DB 지침은 기존 `docs_dev` 및 `infra/runbooks` 문서를 따릅니다.

> [!IMPORTANT]
> 현재 운영 URL, 운영 담당자, AWS 자원 식별자, Supabase 프로젝트 식별자는 저장소에 확정값으로 기록되어 있지 않습니다. 배포 또는 운영 DB 작업 전에 담당자와 실제 대상 환경을 반드시 확인합니다.

---

## 1. 환경 구분

| 환경 | 목적 | 상태 |
| :--- | :--- | :--- |
| 로컬 | 기능 개발, 로컬 Supabase, 단위 테스트 | 구성됨 |
| 스테이징 | 마이그레이션·RLS·복구·E2E 검증 | 자원과 URL 미확인 |
| 운영 | WORKS/GUEST S3 + CloudFront, 운영 Supabase | 워크플로는 있으나 실제 자원 상태 미확인 |

환경별 URL, 담당자, Supabase project ref, AWS 계정·리전, S3 버킷과 CloudFront 배포 ID는 비밀값 자체가 아닌 식별 가능한 운영대장에 별도로 기록해야 합니다.

---

## 2. 로컬 실행

### 2.1 최초 준비

```bash
pnpm install --frozen-lockfile
```

`apps/works/.env.example`, `apps/guest/.env.example`을 기준으로 각 앱의 `.env.local`을 구성합니다. 로컬 Supabase를 사용할 때는 Docker가 필요합니다.

```bash
pnpm db:start
pnpm db:status
pnpm dev
```

종료할 때는 다음 명령을 사용합니다.

```bash
pnpm db:stop
```

### 2.2 환경 변수 원칙

* **클라이언트 공개 변수**: `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `VITE_APP_ENV`만 앱 번들에 사용합니다.
* **서버 시크릿**: 서비스 역할 키, 이메일·카카오·SMS 공급자 키는 Supabase Secrets 또는 배포 환경의 비밀 저장소에 둡니다.
* **금지 사항**: 서버 시크릿에 `VITE_` 접두사를 붙이거나 `.env.local`을 커밋하지 않습니다.
* **운영 CORS**: 운영 도메인 확정 후 `ALLOWED_ORIGINS`를 명시합니다.

---

## 3. 작업 전 점검

모든 사람과 에이전트는 변경 전에 다음을 확인합니다.

```bash
git status --short
git branch --show-current
git log -5 --oneline
```

* 기존 수정과 미추적 파일은 사용자 작업으로 간주합니다.
* `hiworks_backup/`, 임시 스크립트, 덤프·내보내기 파일은 민감정보와 라이선스를 확인하기 전 커밋하지 않습니다.
* DB 변경은 `supabase/migrations/`의 새 순차 마이그레이션으로만 수행합니다.
* 검토 요청에서는 파일을 수정하지 않습니다. 구현 요청과 검토 요청을 분리합니다.

## 4. 변경 검증

### 4.1 기본 품질 게이트

```bash
pnpm lint
pnpm typecheck
pnpm test
pnpm build
```

Windows PowerShell 실행 정책으로 `pnpm.ps1`이 차단되면 `pnpm.cmd`를 사용합니다. 현재 알려진 실패 상태는 [CURRENT_STATUS.md](./CURRENT_STATUS.md)를 확인합니다.

### 4.2 변경 유형별 추가 검증

| 변경 | 필수 추가 검증 |
| :--- | :--- |
| 인증·권한 | 역할별 허용·차단 사례, 토큰 만료·갱신, 다른 워크스페이스 접근 차단 |
| DB·RLS | 마이그레이션 보안 게이트, 로컬 `db reset`, RLS 회귀 SQL, 운영 반영 전 diff |
| Edge Function | 정상·인증 실패·권한 실패·공급자 실패·CORS 사례 |
| 첨부파일 | 업로드, 다운로드, 삭제, 만료 링크, 권한 없는 사용자 차단 |
| 공통 UI | WORKS/GUEST 영향 범위, 키보드 접근, 작은 화면, 빌드 |
| 배포 | WORKS/GUEST 기본 진입, 딥링크, 로그인, 정적 자산 캐시, 롤백 확인 |

테스트 통과와 운영 가능은 같은 의미가 아닙니다. 외부 공급자, 실제 운영 DB, IAM, DNS, 백업 복구는 별도로 확인합니다.

---

## 5. 데이터베이스 변경

1. [마이그레이션 보안 게이트](./docs_dev/11_migration_security_gate.md)를 읽습니다.
2. 기존 마이그레이션을 수정하지 않고 새 파일을 생성합니다.
3. 테이블과 뷰, 함수, Storage 정책의 권한과 RLS 기본 거부(Default Deny)를 검토합니다.
4. 로컬 재구성과 회귀 테스트를 수행합니다.
5. 스테이징에 적용해 실제 역할별 접근을 확인합니다.
6. 운영 대상 project ref와 백업 시점을 확인한 뒤 승인된 절차로 반영합니다.
7. 적용 결과와 롤백·보정 방법을 기록합니다.

주요 명령은 다음과 같습니다.

```bash
pnpm db:migration <name>
pnpm db:reset
pnpm db:baseline:check
pnpm db:baseline:verify
```

운영 DB 반영은 데이터 변경 가능성이 있으므로 대상과 백업을 확인하고 사용자 승인 후 수행합니다.

## 6. 배포

현재 `.github/workflows/deploy.yml`은 `main` 푸시 또는 수동 실행 시 WORKS/GUEST를 빌드해 각각 S3에 동기화하고 CloudFront 캐시를 무효화합니다.

필요한 GitHub 설정은 다음과 같습니다.

| 종류 | 이름 |
| :--- | :--- |
| Repository Variables | `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` |
| Secrets | `AWS_ROLE_ARN`, `AWS_REGION`, `S3_BUCKET_WORKS`, `S3_BUCKET_GUEST`, `CF_DISTRIBUTION_WORKS`, `CF_DISTRIBUTION_GUEST` |

### 6.1 현재 위험

CI와 Deploy가 `main` 푸시에서 독립적으로 시작합니다. CI 실패가 배포를 자동으로 막지 않으므로, 안정화 전까지는 `main` 반영을 운영 배포 승인으로 간주하지 않습니다.

### 6.2 권장 릴리스 게이트

1. PR에서 린트·타입 검사·테스트·빌드 통과
2. DB 변경 시 스테이징 마이그레이션과 RLS 회귀 통과
3. 사용자 또는 지정 리뷰어 승인
4. CI 성공 결과를 조건으로 Deploy 실행
5. WORKS/GUEST smoke test
6. 배포 커밋, 수행자, 시간, 결과 기록

### 6.3 롤백

* **프론트엔드**: 직전 정상 커밋을 다시 빌드·배포하고 CloudFront 캐시를 무효화합니다.
* **DB**: 운영 마이그레이션 파일을 임의 삭제하거나 되돌리지 않습니다. 데이터 보존형 보정 마이그레이션 또는 검증된 백업 복구를 사용합니다.
* **외부 발송**: 공급자 장애 시 발송 기능을 격리하고 실패 로그를 보존합니다. 인증 우회 경로를 임의로 열지 않습니다.

---

## 7. 장애 대응

1. **탐지와 기록**: 발생 시각, 사용자 역할, URL, 요청 ID, 배포 커밋, 증상을 기록합니다.
2. **영향 범위 확인**: WORKS/GUEST, 특정 워크스페이스, DB, Storage, Edge Function, 외부 공급자 중 범위를 가릅니다.
3. **확산 차단**: 필요한 경우 배포 중단, 기능 플래그 비활성, 발송 중단 등 복구 가능한 조치를 우선합니다.
4. **복구**: 최근 변경과 로그를 근거로 프론트 롤백, 보정 마이그레이션 또는 백업 복구를 선택합니다.
5. **검증**: 정상 사용자와 권한 없는 사용자를 함께 점검합니다.
6. **회고**: 원인, 탐지 지연, 재발 방지 작업, 담당자와 기한을 기록합니다.

개인정보나 민감 금융정보 노출이 의심되면 일반 기능 장애보다 우선해 접근을 차단하고, 원본 로그와 감사 기록을 보존합니다.

---

## 8. 백업과 복구

복구 목표는 RPO 24시간, RTO 4시간입니다. 상세 절차는 [복구 리허설 런북](../infra/runbooks/restore-drill.md)을 따릅니다.

* 분기 1회 스테이징에서 DB 복원, 스키마 diff, S3 객체 복원, SPA 재배포와 RLS 검증을 수행합니다.
* 런북에 예시 행만 있는 것은 수행 증거가 아닙니다. 실제 수행일, 측정 RPO/RTO, 담당자와 개선 액션을 기록합니다.
* 복구 테스트에서 운영 원본을 덮어쓰지 않습니다.

## 9. 다른 에이전트에게 넘기는 절차

### 9.1 검토 에이전트 지시문

다음 형식으로 요청합니다.

```text
README.md, docs/CURRENT_STATUS.md, docs/OPERATIONS.md를 먼저 읽어라.
이번 단계는 검토만 수행하고 파일 수정, 커밋, 푸시, 배포는 하지 마라.
<검토 대상>을 실제 코드와 설정으로 확인하고 다음 형식으로 보고하라.
1) 확인한 사실과 근거 파일
2) 문제를 P0/P1/P2로 분류
3) 권장 변경 범위와 범위 밖 항목
4) 예상 회귀 위험
5) 실행할 검증 명령과 통과 기준
6) 롤백 방법
7) 사용자 결정이 필요한 질문
추측과 확인된 사실을 구분하라.
```

### 9.2 구현 에이전트 지시문

검토 결과를 승인한 뒤 다음 형식으로 요청합니다.

```text
승인 범위: <구체적인 항목>
기존 사용자 변경을 보존하고 승인 범위 밖 파일은 수정하지 마라.
구현 전 git status를 확인하고, 최소 변경으로 구현하라.
관련 테스트를 추가하거나 갱신하고 lint, typecheck, test, build를 실행하라.
DB 변경이면 마이그레이션 보안 게이트와 RLS 회귀를 포함하라.
완료 후 변경 파일, 핵심 판단, 검증 결과, 미검증 항목을 보고하라.
내 요청 없이 커밋, 푸시, 배포하지 마라.
```

### 9.3 검토 승인 기준

* 문제와 근거가 실제 코드에 연결되어 있습니다.
* 변경 범위와 하지 않을 일이 명확합니다.
* 사용자 데이터, 인증, 권한, 배포 영향이 설명되어 있습니다.
* 검증 명령뿐 아니라 기대 결과가 정의되어 있습니다.
* 실패 시 되돌리는 방법이 있습니다.
* 기존 미커밋 작업과 충돌 가능성을 확인했습니다.

## 10. 운영 문서의 다음 보완 항목

아래 값은 확인되는 즉시 본 문서 또는 접근 통제된 운영대장에 채웁니다.

* WORKS·GUEST 운영 및 스테이징 URL
* 서비스·DB·AWS·보안 담당자와 비상 연락 경로
* Supabase organization/project ref와 리전
* AWS 계정, S3 버킷, CloudFront 배포의 소유 관계
* 마지막 운영 배포와 마지막 정상 커밋
* 마지막 백업 성공과 복구 리허설 결과
* 모니터링 대시보드와 경보 수신 채널
