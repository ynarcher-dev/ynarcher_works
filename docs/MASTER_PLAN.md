# 마스터 플랜 (Master Plan)

본 문서는 **실행 가능한 단일 백로그**입니다. 다른 문서에 흩어진 제안·이력은 여기서 작업으로 승격될 때만 유효하며, 여기 없는 항목은 현재 계획이 아닙니다.

* **기준**: `main` / `846dfb83` **+ 현재 작업 트리(미커밋 포함)**. 아래 `완료`는 **커밋된 기준선이 아니라 작업 트리의 상태**이며, 미커밋 녹취 작업 등 다른 작업자의 변경도 같은 트리에 있습니다.
* **완료의 두 층**: 이 백로그는 **구현+로컬 검증 완료**와 **실제 실행 증거 확보**를 구분합니다. 워크플로·배포·운영 DB처럼 저장소 밖에서만 관측되는 것은 코드가 들어가도 `실행 증거 미확보`로 남습니다(GitHub 실행 이력·배포·운영 DB 확인은 이번에 수행하지 않았습니다).
* **함께 읽는 문서**: [SECURITY_REVIEW.md](./SECURITY_REVIEW.md)(근거), [CURRENT_STATUS.md](./CURRENT_STATUS.md)(검증 수치·현재 상태), [OPERATIONS.md](./OPERATIONS.md)(실행 절차), [DOCUMENTATION_MAP.md](./DOCUMENTATION_MAP.md)(문서 소유)
* **우선순위**: **P0**(운영·파일럿 전 해소), **P1**(안정화 단계), **P2**(구조 개선).
* **근거 표기**: 각 과제의 `근거`는 **저장소 코드·설정을 읽어 확인한 사실**입니다. 문서에만 적힌 규정을 인용할 때는 "문서 규정"이라고 밝히며, 코드로 확인하지 못한 것은 `미검증`으로 표시합니다.

## 3. 인증·인가·배포 위험

### AUTH-1 · 확정된 게스트 로그인 정책의 동작 확인과 강화 (P1)

* **정책 전제(2026-09-12 사용자 확정)**: 게스트 로그인은 **이메일 아이디 + 본인이 정한 비밀번호**이고, 비밀번호 설정 전에만 원장 연락처(숫자만)가 초기 비밀번호로 인정되며, **설정 전에는 세션을 주지 않고** 본인이 비밀번호를 정한 뒤에 세션이 열립니다. 자격증명의 오프라인 취급·배포는 사용자가 **저장소 밖 운영 정책**으로 확정해 관리합니다. 정본은 [3_9_1](./docs_planning/3_9_1_guest_unified_account.md) §6입니다. **이 과제는 인증 방식을 교체하는 과제가 아니라, 확정된 정책이 코드에서 그대로 동작하는지 확인하고 그 안에서 강화하는 과제입니다.**
* **확인된 흐름(사실)**: 판정은 [guest-auth-login/handler.ts](../supabase/functions/guest-auth-login/handler.ts)의 `createLoginHandler`에 있습니다 — 계정에 `password_hash`가 없으면 원장 연락처의 숫자열이 초기 비밀번호로 인정되고, 성공 시 세션이 아니라 설정 티켓(`changeTicket`)만 발급됩니다. 연락처는 계정 복사본이 아니라 원장에서 읽고([_shared/guestAccount.ts](../supabase/functions/_shared/guestAccount.ts)의 `readLedgerPhones`), 실패는 계정 단위 5회/15분으로 잠깁니다(같은 파일의 `recordFailure`·`isLocked`). 비밀번호 설정은 [guest-auth-password/handler.ts](../supabase/functions/guest-auth-password/handler.ts)가 받습니다.
* **조건부 잔여 위험(추론, 실증 아님)**: 비밀번호 설정 전에 한 계정의 이메일과 연락처가 **둘 다** 유출되면 제3자가 참여자보다 먼저 설정 티켓을 받는 사칭이 조건부로 성립합니다. 설정 이후에는 연락처가 통하지 않아 그 경로가 닫힙니다. 오프라인 취급 정책이 이 조건을 줄이는 수단이며, **그 집행은 저장소에서 확인할 수 없습니다**(코드 검증 대상이 아닙니다). 이 조건이 실제로 관측되면 대응 범위를 **정책 재검토 항목**으로 올리며, 기본 동작을 미리 바꾸지 않습니다.
* **의존**: 없음. 발송 경로(SEC-1·SEC-2)는 이 과제의 선행이 아닙니다 — 확정된 정책은 초대 발송이 닿는 것을 전제로 하지 않습니다. SEC-4는 추측 시도 상한을 낮추는 **병렬 보완 방어**입니다. 확인된 규칙의 고정은 TEST-2가 이어받습니다(테스트 자체는 TEST-2 소유).
* **완료 기준**:
  1. 확정된 정책이 정본 문서(3_9_1 §6)에 기재되고, 다른 문서가 이를 대체 제안 없이 인용합니다.
  2. 다음 세 경계가 **TEST-2에서** 단언됩니다 — ① 미설정 계정의 초기 비밀번호 인증이 **세션 토큰을 반환하지 않고 설정 티켓만** 준다, ② 설정 전 세션 요구가 거절된다, ③ 비밀번호 설정 **이후에는 연락처로 로그인이 거절**되고 실패 누적 시 계정 단위 잠금이 걸린다.
  3. 위 단언이 `pnpm test`에서 통과합니다.
* **현재 상태(2026-09-12, 작업 트리)**: 완료 기준 1~3을 충족했습니다 — 정책은 **바뀌지 않았고**, 판정 본체를 배선에서 분리하는 동작 보존 정리 뒤 TEST-2의 단언이 통과합니다. 덮은 경계는 TEST-2에 열거되어 있고, **게스트 인증 경로의 Deno 런타임·RLS 판정·브라우저 동작은 여전히 미검증**입니다.
* **범위 밖**: 초대 토큰 기반 강제 전환, 초기 로그인 경로의 기본 차단, 담당자 수동 개방 대체 경로. 자격증명의 오프라인 취급은 **사용자·운영 영역**이며 코드 검증 대상이 아니고, 이 과제에 별도 승인 관문을 두지 않습니다.
* **롤백(안전)**: 이 과제는 확인·테스트 중심이므로 제품 동작을 바꾸는 변경이 없습니다. 강화 구현이 포함되면 그 커밋만 되돌리며, 되돌린 뒤의 기준선은 **확정된 정책 그대로**입니다.
* **근거 문서**: [SECURITY_REVIEW.md](./SECURITY_REVIEW.md) F-0, [3_9_1 §6](./docs_planning/3_9_1_guest_unified_account.md).

### SEC-1 · 일반 발송 창구의 처리 (P0, **완료 — 창구 차단**)

* **종전 상태(해소됨)**: 옛 `notifications-dispatch`는 `auth.getUser`로 **토큰이 유효한 사용자임**만 확인하고 호출자의 역할·수신처(`to`)·문안(`variables`) 권한을 묻지 않아, 유효한 토큰 하나로 임의 수신처에 회사 발신 명의의 안내를 요청할 수 있었습니다.
* **처리(2026-09-12 승인대로 반영)**: 인가로 감싸지 않고 **창구를 닫았습니다.** 판정은 [handler.ts](../supabase/functions/notifications-dispatch/handler.ts)에 두고 `index.ts`에는 `withCors` 배선만 남습니다 — `POST` 403 `endpoint_disabled`, 그 밖의 메서드 405, 프리플라이트 유지. 임의 `to`·`variables`를 받는 계약은 남지 않았고 새 발송 계약을 연 것도 아닙니다. 게스트 초대·비밀번호 재설정(`guest-access-invite`·`guest-password-reset`)과 `_shared/notifications.ts`는 **그대로입니다.**
* **완료 기준(충족)**: 거절이 요청과 무관할 것, 응답이 요청 내용을 되비추지 않을 것, **발송기·특권 클라이언트·바깥 요청 부작용이 없을 것**, 콘솔에 남기지 않을 것이 함수 단위 회귀로 고정되어 통과했습니다(결과는 [CURRENT_STATUS.md](./CURRENT_STATUS.md) §3).
* **의존**: 선행 과제 없음. **실발송(`SEC-2`)은 별건이며 순서는 `SEC-1 → SEC-2` 한 방향입니다** — 이 과제가 끝난 것이 발송을 켜는 근거가 되지 않습니다.
* **뒤에 오는 것(이번 범위 아님)**: 실제 발송이 필요해지면 **승인된 사건 목록 + 서버가 원장에서 도출하는 수신처·문안 + 재발송/중복 제어**를 갖춘 계약을 먼저 세웁니다. 그 계약이 서기 전에는 `SEC-2`의 공급자 어댑터를 붙이지 않습니다.
* **롤백**: 직전 버전으로 되돌릴 때 **인가 없는 옛 엔드포인트를 그대로 재배포하지 않습니다.**

### SEC-2 · 발송 경로의 정직한 결과 보고와 실발송 (P0, **거짓 성공만 해소**)

* **해소된 것(2026-09-12, 작업 트리)**: [_shared/notifications.ts](../supabase/functions/_shared/notifications.ts)에서 공급자 키가 설정된 경로가 `{ ok: true }` 대신 `{ ok: false, provider: '<채널>:unimplemented' }`를 반환하고, 실패 로그에 수신처·본문을 남기지 않습니다. 집계 쪽에서는 재설정 안내가 호출 성공이 아니라 `notified === true`만 발송으로 세도록 고쳤습니다([participantAccessHooks.ts](../apps/works/src/features/program/participantAccessHooks.ts)의 `countNotified`, [ParticipantPool.tsx](../apps/works/src/features/program/ParticipantPool.tsx)). 두 자리 모두 단위 테스트로 고정했습니다. 로컬 스택의 로그 폴백(키 미설정)은 종전 동작 그대로입니다.
* **남은 것(이 과제의 본체)**: **채널 어댑터가 없어 어떤 경로로도 실제 발송이 일어나지 않습니다.** 초대 안내·비밀번호 재설정 링크는 여전히 담당자가 직접 전달해야 합니다.
* **의존**: SEC-1이 선행입니다. 다만 SEC-1이 일반 창구를 **닫는** 방향으로 확정되었으므로(위), 어댑터를 붙이기 전에 **승인된 사건 목록 + 서버 도출 수신처·문안 + 재발송/중복 제어를 갖춘 발송 계약을 먼저 세우는 일**이 이 과제 안에 들어옵니다. 일반 창구를 되살리는 방식은 쓰지 않습니다. **게스트 로그인 정책(AUTH-1)의 선행도 후행도 아닙니다.**
* **완료 기준(잔여)**: ① 위 발송 계약이 서고, ② 구현된 채널이 공급자 응답 코드를 근거로 성공을 판정하며, ③ 그 판정이 채널별 테스트로 고정됩니다.
* **롤백**: 키 미설정과 동일한 실패 경로로 되돌립니다. (채널별 비활성 스위치는 **아직 없는 기능**이며, 필요하면 이 과제에서 함께 구현할 대상입니다.)
* **정책 결정 필요**: 공급자 선정, 발신 프로파일·템플릿 사전 승인.

### OPS-1 · 배포를 같은 커밋의 CI 성공에 연결 (P0, **코드 완료 / 실행 증거 미확보**)

## 4. 권한 인벤토리와 회귀 커버리지

> 순서: **AUTHZ-1(권한의 현재 모습을 확정)** → 부정 경로 테스트(TEST-1·E2E-1). 무엇이 허용인지 정하지 않은 상태에서 "거부되어야 한다"는 테스트를 쓰면, 테스트가 현재 구현을 그대로 베낍니다. **AUTHZ-2**는 그 인벤토리가 지목한 보정이며, 둘 다 **승인된 범위 안에서만** 닫혔습니다 — 전역 감사는 남아 있습니다.

### AUTHZ-1 · 권한 원장 인벤토리 (P1, **승인 범위 내 완료 / 전역 감사 잔여**)

> [!NOTE]
> **이번에 닫은 것은 승인된 범위(인벤토리 + 그 인벤토리가 지목한 최소 보정)뿐입니다.** 그 범위의 검증 결과는 [CURRENT_STATUS.md](./CURRENT_STATUS.md) §3이 소유합니다. 서비스 전체의 **역할×워크스페이스 감사는 완료가 아닙니다** — 아래 후속이 그 자리를 가집니다.

* **산출물**: 역할×기능·RPC(`SECURITY DEFINER`/`INVOKER`·`search_path`·EXECUTE)·Edge Function의 `service_role` 사용 지점·Storage를 한 벌로 정리한 [15_authorization_inventory.md](./docs_dev/15_authorization_inventory.md)와 `supabase/security/`의 기계 산출물(`acl-decisions.json`이 표별 결정의 정본)입니다. **수치는 [CURRENT_STATUS.md](./CURRENT_STATUS.md) §3.1이 요지만 갖고, 전문은 산출물이 가집니다** — 여기서 되풀이하지 않습니다.
* **판단 축 다섯**: 정책·화면의 직접 호출·`SECURITY INVOKER` RPC가 호출자 권한으로 닿는 표·Edge의 자격(`service_role` 대 호출자 JWT)·쓰기가 함께 요구하는 `SELECT`. 하나라도 빼면 인벤토리가 닫히지 않습니다.
* **`authenticated`는 임직원과 게스트가 함께 쓰는 한 롤입니다** — 게스트 세션 JWT가 `role: "authenticated"`로 서명되므로 `grant … to authenticated` 한 줄은 외부 참여자에게도 열리고, 둘을 가르는 것은 **오직 RLS 술어**입니다.
* **구 문서와의 차이(확인됨)**: [3_database_rls_policy_matrix.md](./docs_dev/3_database_rls_policy_matrix.md) §4의 매트릭스는 원장 통합 이전 판이라 **ACL 판단의 근거로 쓰지 않습니다.** [1_roles_permissions.md](./docs_planning/1_roles_permissions.md) §3의 "3요소+OTP" 게스트 로그인 기술은 **폐기된 기술**이고 정본은 [3_9_1 §6](./docs_planning/3_9_1_guest_unified_account.md)입니다 — **그쪽으로 되돌리는 제안은 하지 않습니다.**
* **연결된 후속(이번에 구현하지 않음)**:
  * **전역 권한 감사** — 역할×워크스페이스 전수 확인과 **쓰이지 않는 레거시 ACL**(특히 회수하지 않고 경고로만 드러낸 `DELETE`) 정리. 다시 꺼낼 조건: 릴리스 게이트를 확정하는 시점.
  * **`open_program_guest_access`의 지원 범위(FUND·M&A)와 `guest_invitations` 정책 범위(PROJECT·GUEST)의 불일치** — **관측된 사실이며 도메인 차원의 정리 과제**입니다. 지금 RLS를 넓혀 맞추지 않습니다. 다시 꺼낼 조건: FUND·M&A 게스트 개방을 실제로 쓰기로 결정하는 시점.
  * **`guest-temp-resolve` 부재** — [TempGuestPage.tsx](../apps/guest/src/pages/TempGuestPage.tsx)가 부르는데 저장소에 소스가 없습니다. 다시 꺼낼 조건: 배포 함수 목록을 조회할 수 있게 되는 시점, 또는 임시 게스트 링크를 쓰기로 하는 시점.
  * **`is_active` 확인의 불균일** — `aiFill/run`·`aiFill/extractRun`·`material-download`·`employee-create`·`link-metadata`가 `is_active`를 보지 않거나 `public.users`를 조회하지 않습니다. **관측된 것은 검사의 불균일이며, 실제 영향은 경로마다 따로 확인해야 합니다** — 뒤이은 질의·권한 검사가 막아 주는 경로가 있지만 **다섯 경로 전부에 대해 그것이 증명되지는 않았으므로, 일괄로 안전하다고 적지 않습니다.** 다시 꺼낼 조건: 퇴직·정지를 즉시 차단으로 보장해야 하는 요구가 생기는 시점, 또는 이 경로들 중 하나를 다른 이유로 고치는 시점.

### AUTHZ-2 · 신규 DB의 테이블 권한을 정책과 맞춥니다 (P0, **승인 범위 내 완료**)

* **근거**: [docs_master/CLAUDE.md](./docs_master/CLAUDE.md) §4의 분량 기준(파일 500줄 등)은 같은 문단에서 **"과거에 세운 목표치"이며 줄 수만으로 위반을 선언하거나 자동 리팩터링에 들어가지 않는다**고 밝히고 있습니다(문서 규정). 즉 500줄은 **현행 절대 상한이 아니라 완화된 과거 지침**이며, 여기서는 후보 신호로만 씁니다. 긴 파일이 존재하는 것은 확인했으나 **그 자체가 착수 근거는 아닙니다.**
* **선정 기준**: ① 최근 변경 빈도(커밋 이력), ② 실패 시 영향 범위, ③ 한 파일이 지는 책임의 수. 이 세 근거가 모이기 전에는 어떤 파일도 착수 대상으로 확정하지 않습니다.
* **완료 기준**: 후보별 변경 빈도·영향·책임 수를 적은 표가 존재하고, 근거와 함께 착수 대상 2~3건이 선정됩니다. 선정된 건은 각각 "동작 변경 없음 + 기존 테스트·`pnpm typecheck` 통과"를 완료 조건으로 하는 개별 커밋으로 진행합니다.
* **의존**: **후보 지도 작성과 선정 근거 수집은 선행 과제 없이 병렬로 진행합니다.** 실제 구조 변경 착수만 해당 영역의 안전망(TEST-2·TEST-3 등 그 코드를 덮는 테스트)이 선 뒤에 합니다.
* **롤백**: 구조 변경만 담은 단일 커밋 되돌리기.

### CI-1 · Edge Function 정적 검사의 CI 편입 (P1, **코드 완료 / 실행 이력 미확인**)

* **들어간 것(2026-09-12, 작업 트리)**: [ci.yml](../.github/workflows/ci.yml)에 `typecheck:functions` 단계가 있고, [eslint.config.mjs](../eslint.config.mjs)에 `supabase/functions/**` 전용 규칙 블록이 생겨 함수 트리도 린트를 받습니다. `tsconfig.functions.json`의 포함 목록은 손으로 들던 방식에서 함수 전체 글롭으로 넓어졌습니다(소스 제외 없음). CI에는 DB 회귀 잡과 PR 완료 템플릿도 함께 들어갔습니다.
* **남은 것**: 위 단계들이 **GitHub에서 실제로 돌아간 이력을 확인하지 않았습니다.** 로컬에서 같은 명령이 통과한 결과는 [CURRENT_STATUS.md](./CURRENT_STATUS.md) §3에 있습니다.
* **롤백**: 추가한 CI 단계 제거.

### CI-2 · 문서 동반 갱신 규칙의 실효화 (P2, **사람 확인 수단까지 마련**)

* **현재 수단 셋을 구분합니다**: ① **문서 규칙** — [CURRENT_STATUS.md](./CURRENT_STATUS.md)의 **「갱신 규칙」 절**(절 번호는 바뀔 수 있으므로 제목으로 가리킵니다), ② **리뷰어 확인** — PR 템플릿에 문서 동반 갱신 항목이 있어 작성자가 표시하고 리뷰어가 봅니다, ③ **기계적 강제** — **아직 없습니다**(CI가 문서 갱신 누락을 막지는 않습니다).
* 따라서 "강제 수단이 전혀 없다"는 종전 기술은 맞지 않고, "자동으로 막힌다"도 맞지 않습니다. 템플릿이 GitHub에서 실제로 렌더·사용된 이력은 확인하지 않았습니다.
* **완료 기준(잔여)**: 인증·배포·DB 경로를 건드린 PR에서 문서 갱신 누락이 **사람의 기억이 아닌 수단으로** 드러납니다(CI 경고 등). 사람 확인만으로 충분하다고 판단하면 그 결정을 근거와 함께 남기고 닫습니다.
* **의존**: 없음(문서 소유 표기는 DONE-1에서 확정되었습니다).
* **롤백**: 체크 제거.

## 7. 파일럿 전 실행 순서 (작업 묶음)

묶음 번호는 **우선순위 표시일 뿐 전면 직렬 순서가 아닙니다.** 진행을 구속하는 것은 `선행` 열에 적힌 과제 ID뿐이며, **선행이 비어 있는 묶음은 서로 병렬로 진행합니다.** 다만 `파일럿 필수`로 표시된 게이트는 **파일럿 개방 전에 모두 통과**해야 하고, 표시가 없는 묶음은 파일럿 이후로 미룰 수 있습니다. 선행 관계는 아래 의존 그래프와 각 과제의 `의존` 항목이 서로 같으며, 한 방향으로만 적어 순환을 만들지 않습니다.

| 묶음 | 과제 | 선행(과제 ID) | 게이트(통과 조건) | 파일럿 필수 |
| --- | --- | --- | --- | --- |
| **P-0 사실 확인** | SEC-4 유입 경로 확인, AUTHZ-1 | 없음 | 유입 경로가 기록되고, 역할·RPC·`service_role` 인벤토리 표가 존재 | 필수 |
| **P-1 배포 게이트** | OPS-1 → CI-1 | 없음 (CI-1은 OPS-1) | 같은 커밋 SHA의 CI 성공 없이는 배포가 시작되지 않음(실행 이력 확인), 함수 정적 검사가 CI에 포함 | 필수 |
| **P-2 인증 정책 확인** | AUTH-1 → TEST-2 | 없음 | 확정된 게스트 로그인 정책이 정본에 기재되고, 설정 티켓·설정 전 세션 거절·설정 후 연락처 거절·잠금 단언이 `pnpm test`에서 통과 | 아니오 (P1 안정화 — 정책이 확정되어 파일럿을 막지 않습니다) |
| **P-3 발송 경로** | SEC-1 → SEC-2 | 없음 (SEC-2는 SEC-1) | 일반 발송 창구가 닫히고(403), 어댑터 없는 채널이 실패를 반환하며, 실발송을 켤 때는 승인된 발송 계약 위에서 공급자 응답으로 판정 | 필수 |
| **P-4 권한 회귀** | AUTHZ-2, TEST-1(로컬 완료) → E2E-1, DB-1 | AUTHZ-1 (판정 기준) | 새 환경 재생 뒤 ACL 상태 확인, `supabase/tests/` SQL 전수 통과 기록(로컬 확보), 핵심 부정 경로 시나리오 실행 기록 | AUTHZ-2 필수 / E2E-1 권장 |
| **P-5 입구 제한** | SEC-3 → SEC-4 | 없음 (SEC-4는 SEC-3) | 운영 오리진 목록 적용 상태에서 미등록 preflight 403, 임계값 초과 429 | SEC-3 필수 / SEC-4 권장(병렬 보완) |
| **P-6 운영 준비** | OPS-2, OBS-1, PRIV-1 | OPS-2 ← OPS-1, OBS-1 ← DB-1 | 함수·DB 반영 절차 문서화, 복구 리허설 1회 기록, 개인정보·외부 전송 현황표 | OPS-2 필수 / 나머지 권장 |
| **P-7 정리** | REF-1, TEST-4, PERF-1, DOC-1, DOC-2, CI-2 | REF-1 착수 ← TEST-2·TEST-3, TEST-4 ← TEST-1, DOC-2 ← AUTHZ-1 | 후보 지도와 기준선 수치 기록, 구 문서 링크 10건 분류·처리 | 아니오 |

### 의존 그래프

아래 화살표는 **검증 순서**이며 한 방향뿐입니다 — 순환은 없습니다. 다만 `AUTHZ-2`와 `TEST-1`은 **구현 위에서 서로를 필요로 합니다**: 테이블 권한이 없으면 RLS 회귀가 판정에 닿기 전에 권한 오류로 멈추고, 반대로 어떤 권한이 옳은지는 그 회귀가 실제로 돌아야 확인됩니다. 이 상호 관계는 **같은 작업 안에서 권한과 회귀를 함께 고쳐 푸는 것**이고, 검증 순서로는 `AUTHZ-2 → TEST-1` 한 방향으로만 적습니다.

* **선행 없이 지금 착수 가능**: SEC-1, SEC-3, DB-1, AUTHZ-1, **AUTHZ-2**, DOC-1, PERF-1, PRIV-1, CI-2, REF-1 후보 지도 작성.
* AUTHZ-2 → TEST-1 (권한이 서야 회귀가 판정까지 도달합니다 — 위 상호 관계 설명 참조)
* OPS-1 → CI-1, OPS-2
* SEC-1 → SEC-2 (발송 경로 — **AUTH-1과 선후 관계 없음**)
* AUTH-1 → TEST-2 → REF-1 착수
* TEST-3 → REF-1 착수
* AUTHZ-1 → TEST-1, E2E-1, DOC-2
* DB-1 → OBS-1 (TEST-1과는 **병렬** — 선후 관계 없음)
* TEST-1 → E2E-1, TEST-4
* SEC-3 → SEC-4 (**SEC-4는 AUTH-1의 선행이 아니라 병렬 보완 방어**)

### 7.1 개발 중 진행 / 기능 완성 후 2차 안정화

기능 개발이 계속되는 동안 **지금 같이 가는 것**과 **기능이 다 선 뒤에 전용 환경에서 하는 것**을 갈라 둡니다. 과제 ID·우선순위·완료 기준은 위 절들이 소유하며 여기서 다시 적지 않습니다. 이 절은 **권고 일정**이고 **착수 승인이 아닙니다** — 여기 적혀 있다는 이유로 백로그가 자동으로 시작되지 않습니다.

작업 한 벌의 순서(기능 구현 → 권한·실패 경로 점검 → 문서 갱신 → Codex 검토)는 [docs_master/CLAUDE.md](./docs_master/CLAUDE.md)가 정본이므로 여기서 되풀이하지 않습니다.

| 시기 | 과제 | 그때 하는 이유 |
| :--- | :--- | :--- |
| **개발 중(지금부터)** | `AUTHZ-1`·`AUTHZ-2` — 기능 단위로 권한 인벤토리와 **최소 ACL 보정**을 함께 | 권한 공백은 미루지 않습니다. 표를 늘리는 기능마다 그 자리에서 정리하는 편이 나중에 전수로 되돌리는 것보다 싸고, 회귀도 그때 붙습니다 |

| | 스테이징 CI·Edge Function·DB 반영과 리허설 | 운영과 분리된 환경이 있어야 성립합니다 |
| | 복구 RTO/RPO 리허설, 경보 수신, 개인정보 보존·삭제 점검 | 실제 데이터 수명주기를 돌려 봐야 답이 나옵니다 |
| | 문서 **최종 as-built 교차 확인** | 문서 동반 갱신은 **지금의 규칙**이고, 2차에서는 완성된 릴리스 범위와 문서·운영 절차가 서로 맞는지 마지막으로 맞춥니다 |

* **보안 항목을 2차로 미루지 않습니다.** 권한·인가·정화기·시크릿은 위 표의 **개발 중**에 있습니다. 2차로 가는 것은 *전용 환경이나 최종 형태가 없으면 성립하지 않는 검증*뿐입니다.
* 위 전부는 기본적으로 **비운영 기준의 계획·로컬 작업**입니다. 실발송·배포·운영 DB 접근처럼 **밖으로 나가는 행위는 승인된 작업 범위에 명시적으로 포함되어 있어야** 하며, 포함돼 있지 않으면 범위를 먼저 넓힙니다. **이미 명시적으로 승인된 행위는 시도마다 다시 확인받지 않습니다.**
* 큰 구조 리팩터링은 **근거와 테스트가 선 자리**에서만 하며, 전면 재작성은 이 백로그의 계획이 아닙니다(`REF-1`).

**2차 종료 기준(제안)**: ① 합의된 릴리스 게이트 목록에 **P0·P1 차단 항목이 남아 있지 않다**, ② 핵심 사용자 여정이 **반복해서 안정적으로** 통과한다, ③ 배포와 복구가 **재현 가능**하고 수행 기록이 남는다, ④ 각 항목에 증거 문서가 붙는다. 구체적 수치 임계값은 여기서 정하지 않습니다. ①의 범위는 **합의된 릴리스 게이트에 올린 항목**이며, **백로그의 모든 P1이 자동으로 릴리스 차단 항목이 되는 것은 아니고** 반대로 P1 전부를 릴리스 밖으로 미루라는 뜻도 아닙니다 — 무엇을 게이트에 넣을지는 합의로 정합니다.

### 7.2 승인된 다음 작업 순서 (2026-09-12)

§7.1이 **권고 일정**인 것과 달리, 아래는 사용자가 **착수를 승인한 순번**입니다. 세 순번은 **한 번의 승인으로 이어서 진행하며, 순번 사이에 다시 묻는 관문을 두지 않습니다** — 순서는 논리적 선후일 뿐 허가의 경계가 아닙니다. 범위 판단이 필요한 것은 **이 표에 없는 과제**뿐입니다. 각 과제의 근거·완료 기준·롤백은 위 절들이 소유하므로 여기서 되풀이하지 않습니다.

| 순번 | 과제 | 이번 승인에 담긴 것 | 상태 |
| :--- | :--- | :--- | :--- |
| **1** | `AUTHZ-1` · `AUTHZ-2` 잔여 | 권한 인벤토리와 그 인벤토리가 지목하는 **한정된 보정**. 인벤토리 없이 권한을 넓히는 변경은 담기지 않습니다 | **완료** — 전역 감사는 이 승인 밖 |
| **2** | `TEST-3` 잔여 · `SEC-1` | `richText` 정화기 회귀(실제 DOM 기준)와 일반 발송 창구의 처리 | **둘 다 완료** |
| **3** | `DB-1` | **로컬 격리 스택** 기준의 베이스라인 산출물. 새 유료 프로젝트·원격 DB는 담기지 않습니다 | **완료 — 작업 트리 산출물까지**(커밋은 별도 승인 사항) |

* **이번 승인 밖**: 커밋·푸시·배포·운영 DB 변경·외부 발송, `SEC-2`의 실발송(어댑터), 그리고 역할×워크스페이스 **전역 권한 감사**는 담기지 않았습니다. `SEC-1 → SEC-2` 한 방향은 그대로이며, 창구를 닫은 것이 발송을 켜는 근거가 되지 않습니다.
* **1차 안정화 기록은 보존합니다**: `DONE-2`와 `TEST-1`·`TEST-2`·`AUTH-1`의 통과 기록은 **그때의 증거로 남습니다** — 지우거나 이번 순서로 덮어쓰지 않습니다. 다만 그것이 재검증 면제는 아닙니다. 이번 변경이 그 범위에 닿으면 **영향받은 검사를 다시 돌리고, 새로 돌린 결과로** 보고합니다.
