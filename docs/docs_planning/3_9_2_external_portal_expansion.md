# [3-9-2] 외부 포털 확장 — AC · FUND · M&A (External Portal Expansion)

> [!IMPORTANT]
> 본 문서는 **외부인이 들어오는 자리 전체의 단일 원천(SSOT)** 입니다. 어느 워크스페이스가 외부인을 받는가, 그 계정이 어떻게 갈리고 합쳐지는가, 발급 창구가 무엇을 보는가에 관한 판단은 이 문서가 답합니다. [3_9_1](./3_9_1_guest_unified_account.md) §4(계정의 키)는 이 문서 §5가 승계하고, [3_6](./3_6_workspace_ma.md) §게스트 차단과 [3_5](./3_5_workspace_fund.md) §4는 이 문서를 참조합니다.

**확정일**: 2026-09-08 · **적용 범위**: WORKS(AC·FUND·M&A·ADMIN) + GUEST 앱

---

## 1. 목적

외부인이 자료를 보고 내는 자리를 **AC 한 곳에서 AC·FUND·M&A 세 곳으로** 넓힙니다. 앱은 하나로 두고, 계정 단위를 **원장 행에서 사람으로** 옮기며, 발급 창구가 보는 범위를 **사업이 아니라 인격의 출처 원장**으로 좁힙니다.

---

## 2. 배경 — 지금 어디까지 열려 있는가

세 곳의 준비 상태가 서로 다릅니다. 이 확장은 "셋을 새로 만드는 일"이 아닙니다.

| 워크스페이스 | 지금 상태 |
| :--- | :--- |
| **AC** | 운영 중. 계정 발급 창구·명부·모듈·게스트 화면이 모두 서 있습니다. |
| **M&A** | **DB는 이미 열려 있습니다.** `app.guest_program_ids()`가 `ma_programs`를 union하고(20260907170000), 세션 맥락 클레임이 `ma_program`을 받으며, 모듈 계열 원장이 `entity_key`로 한 벌입니다. 막힌 것은 셋 — 발급 창구가 AC 사이드바에 `entity_key='program'`으로 고정, 명부 `master_table`이 `startups`·`networks`만, 그리고 [3_6](./3_6_workspace_ma.md)에 *"게스트 전면 차단"* 이 명시돼 있습니다. |
| **FUND** | 화면·원장 모두 없습니다. 사후관리보고의 게스트 입력은 [3_5 §4](./3_5_workspace_fund.md)에 기획만 되어 있습니다. 다만 세션 맥락 클레임은 2026-09-05에 `program_id`에서 `context_type`+`context_id`로 일반화하며 **FUND가 들어올 자리를 비워 두었습니다.** |

> [!NOTE]
> **M&A는 창구를 여는 일이고, FUND는 맥락을 하나 세우는 일입니다.** 이 비대칭이 구현 순서를 정합니다.

## 3. 구조 판단 — 층으로 가릅니다

"세 워크스페이스를 통합할 것인가"는 답할 수 없는 물음입니다. 통합할 층과 갈릴 층이 다르고, **갈리는 층은 이미 갈려 있기** 때문입니다.

| 층 | 무엇 | 셋이 같은가 |
| :--- | :--- | :--- |
| **1. 신원·인증** | 계정, 비밀번호, 세션, 맥락 전환, 접근 기간, 차단, 잠금 | **같습니다.** 이미 만들어져 있습니다. |
| **2. 셸** | 사이드바, 상단바, 공지, Q&A, 내 정보, 비밀번호 변경 | **같습니다.** 이미 만들어져 있습니다. |
| **3. 화면 종류** | 무엇을 보고 무엇을 내는가 | **갈립니다.** 그리고 지금도 모듈 종류마다 다른 컴포넌트가 섭니다. |

그래서 실제 물음은 **"FUND의 정형 보고와 M&A의 자료 선별을 모듈로 표현할 것인가"** 이고, 그 답이 §8·§9입니다.

**앱은 하나로 둡니다.** 셋으로 가르면 도메인·배포·로그인이 셋이 되고, 무엇보다 *계정 하나가 여러 맥락을 갖는다*는 전제 자체가 앱 하나를 요구합니다.

## 4. 세 곳이 실제로 무엇을 여는가

주고받는 방향이 이 확장의 설계를 전부 정합니다.

| | 외부 참여자 | 자료의 방향 | 외부 A → 외부 B 노출 |
| :--- | :--- | :--- | :--- |
| **AC** | 참여기업(`startups`) · 참여전문가(`networks`) | 내부 ⇄ 밖 | **있음** — 스타트업이 올린 것을 전문가가 봅니다(전량) |
| **FUND** | 포트폴리오사(`startups`) | 밖 → 내부 → 밖(보완요청) | **없음** |
| **M&A** | 매도자(`ma_sellers`) · 인수후보(`ma_buyers`) | 밖(셀러) → 내부 → 밖(바이어) | **있음 — 그리고 선별됩니다** |

> [!IMPORTANT]
> **FUND의 3단 검토는 외부가 아니라 내부입니다.** 투자팀이 세팅하고, 포트폴리오사가 올리고, **딜메이커가 1차 확인하고**, 투자팀이 2차 검토합니다. 그런데 딜메이커는 `startup_managers`의 리드, 곧 **내부 임직원**입니다([fund/hooks.ts:548](../../apps/works/src/features/fund/hooks.ts)). 밖에서는 이 왕복이 '검토 의견' 한 카드로만 보이며, 상태 전이는 WORKS 쪽 일입니다. 그 모양은 전자결재 되돌림 흐름([3_1_3](./3_1_3_approval_return_flow.md))의 *제출 → 검토 → 보완요청 → 재제출 → 승인* 과 같습니다.

**FUND의 대상은 포트폴리오사 하나입니다(2026-09-08 사용자 확정).** LP·조합원(`fund_lps`)은 이번 범위에서 뺍니다 — 보는 것이 자기 회사 한 줄이 아니라 조합 전체(투자 포트폴리오·수익률·재무)이고, [3_5 §4.1](./3_5_workspace_fund.md)의 *"GP 내부 데이터는 절대 노출하지 않는다"* 와 정면으로 부딪히므로 **무엇을 보여줄지부터 새로 정해야 합니다.** 방향이 반대인 둘을 한 맥락에 담지 않습니다(§14).

## 5. 계정 — 원장 행에서 사람으로

### 5.1 지금 무엇이 막고 있는가

[3_9_1 §4](./3_9_1_guest_unified_account.md)는 *"계정 = 사람이다. 로그인 ID(이메일) 하나, 비밀번호 하나"* 로 시작해 놓고, 실제 발급은 원장 행이 이메일을 정하게 두었습니다.

* `issue_guest_account(p_master_table, p_master_id)` — **사람을 인자로 받지 않습니다.** 이메일·이름·연락처를 `startups.contact->>'email'` 또는 `networks.email`에서 꺼내 씁니다.
* `guest_identities`의 PK가 `(master_table, master_id)` — **원장 행 하나에 계정 하나**입니다. ①번 분기가 기존 계정을 그대로 돌려주므로 **같은 회사에 두 번째 사람을 발급할 방법이 없습니다.**

원장 행에 이메일이 하나뿐이라, 결과적으로 **회사 = 계정**이 되었습니다.

AC에서는 참을 만했습니다. 참여기업 대표 한 명이 들어와 자료를 내고 공지를 보면 되기 때문입니다. **M&A와 FUND에서는 사고입니다.**

* 인수 후보사 담당자가 셋인데 계정이 하나면 **비밀번호를 셋이 돌려 씁니다.**
* **누가 어느 자료를 열었는지 감사할 수 없습니다** — M&A에서는 이것이 필수입니다.
* 담당자 한 명이 이직하면 회사 계정 전체를 갈아야 합니다.
* 포트폴리오사에서 CFO가 재무를, IR이 사업진행을 올리는데 계정 하나를 공유합니다.

### 5.2 전환

**계정의 키를 이메일(사람)로 옮기고, 원장 행은 소속으로 남깁니다.**

| | 종전 | 개정 |
| :--- | :--- | :--- |
| 발급 인자 | 원장 행만 | 원장 행 + **사람**(이름·이메일·연락처) |
| `guest_identities` PK | `(master_table, master_id)` | **`(master_table, master_id, user_id)`** |
| 원장 행 : 계정 | 1 : 1 | **1 : N** |
| 이메일 유일 제약 | 게스트 전역 유일 | **그대로** — 사람 단위이므로 이것이 맞습니다 |

원장 연락처는 발급 폼의 **기본값**으로 채우되 담당자가 고칠 수 있습니다. 원장에 이메일이 없어도 사람을 지정하면 발급되므로, 종전의 *"원장에 이메일이 없어 계정을 세울 수 없습니다"* 차단이 완화됩니다.

> [!IMPORTANT]
> **이 전환이 기밀 격리를 함께 해결합니다.** 회사 단위였을 때는 대표 이메일 하나로 AC 계정을 받아 둔 기업에 M&A 셀러 계정을 발급하면 `issue_guest_account`의 ②번 분기(같은 이메일이면 같은 계정)가 **AC 실무자 계정에 딜룸 맥락을 붙였습니다.** 사람 단위가 되면 AC는 IR 실무자 이메일로, M&A는 대표 이메일로 발급되어 **애초에 다른 계정**입니다. 이메일 병합 예외를 따로 둘 필요가 없습니다.

### 5.3 계정이 합쳐지는 경우와 갈리는 경우

**합쳐지는 기준은 하나 — 같은 사람인가.** 관계의 종류가 아니라 사람이 정합니다.

| 상황 | 결과 |
| :--- | :--- |
| 같은 사람이 AC 참여기업 대표이자 그 회사가 우리 펀드의 포트폴리오사 | **계정 하나, 맥락 둘** |
| 같은 회사인데 AC는 실무자가, M&A는 대표가 담당 | **계정 둘** |
| 같은 사람이 AC 참여기업 대표이자 다른 회사의 자문 전문가 | **계정 하나, 인격 둘** |

말씀하신 생애주기(AC → FUND → M&A)에서 앞 두 칸이 자연히 이어지는 것이 이 규칙의 결과입니다. 몇 년에 걸쳐 관계가 쌓이는데 그때마다 자격증명을 새로 안내하면, 상대는 우리와의 관계가 세 번 처음부터 시작하는 것으로 느낍니다.

## 6. 발급 창구가 보는 범위 — 사업이 아니라 인격의 출처 원장

### 6.1 종전 규칙이 왜 성립하지 않는가

2026-09-07에 이렇게 정했습니다.

> **좁히는 것은 사업이지 계정이 아니다** — 목록에는 게스트 계정이 전부 서고 달라지는 것은 참여 사업 칸(건수·목록)뿐이다. 계정은 대상마다 하나이고 사업을 가로질러 존재하므로, 사업 하나를 못 본다고 계정을 빼면 이미 있다는 사실이 숨겨져 같은 대상에 발급을 다시 시도하게 된다.

**M&A가 들어오면 그 근거가 사라집니다.** AC 창구가 발급하는 대상은 `startups`·`networks` 행이고 M&A 창구는 `ma_sellers`·`ma_buyers` 행이라, **애초에 재시도가 일어날 수 있는 같은 대상이 아닙니다.** 중복 발급은 여전히 `issue_guest_account` ①번 분기가 막습니다. 반면 계정을 전부 세우면 `ma_sellers` 인격이 전 직원에게 보입니다.

### 6.2 개정

| 창구 | 서는 계정 |
| :--- | :--- |
| **AC** — `GUEST계정 발급` | `startups` · `networks` 인격 |
| **FUND** — `GUEST계정 발급`(신설) | `startups`(포트폴리오사) 인격 |
| **M&A** — `GUEST계정 발급`(신설) | `ma_sellers` · `ma_buyers` 인격 |
| **ADMIN** — `게스트 계정 관리` | **전부** |

**AC와 FUND는 `startups`에서 겹치고, 그것이 맞습니다.** 둘 다 "그 회사가 우리와 관계 맺고 있다"는, 비밀이 아닌 사실입니다.

`guest_accounts_list`의 인자를 `p_entity_key`(사업 축)에서 `p_master_tables text[]`(원장 축)로 바꿉니다. 참여 사업 칸은 지금처럼 `security invoker`가 알아서 가립니다 — 읽을 수 없는 딜은 조인에서 떨어져 나갑니다.

> [!NOTE]
> **ADMIN은 가리지 않습니다(2026-09-08 사용자 확정).** ADMIN은 최고 정보보안 책임자이고, 전 정보에 대한 비밀유지는 **회사 내부 규정**이 답합니다. 시스템이 인격 목록을 가리면 정지·해제라는 그 화면의 본래 일이 무엇에 걸리는 것인지 화면이 답하지 못합니다.

## 7. 내부 유출 — `guest_identities` 정책 한 줄

[20260905120000](../../supabase/migrations/20260905120000_guest_unified_account_schema.sql)의 SELECT 정책은 **내부 사용자 전원**이고, 그 근거가 같은 파일에 이렇게 적혀 있습니다.

> 이 표가 답하는 것은 "이 원장 행에 계정이 있는가"뿐이고 **그 사실은 명부 화면이 이미 보여 준다**

이 근거는 `master_table`이 `startups`·`networks` 둘뿐이라 성립합니다. 둘 다 전사 공용 SSOT라 누구나 읽습니다. **`ma_sellers`가 그 체크 제약에 들어오는 순간 근거가 사라집니다** — 회사 이름은 원장 RLS에 막혀 `null`로 오지만, `master_table='ma_sellers'`와 계정 이름·이메일(`users`는 내부 전원에게 열려 있습니다)은 그대로 나오므로 **이메일 도메인만으로 어느 회사가 매각 검토 중인지 드러납니다.**

**정책을 원장별로 좁힙니다.** 그 원장을 읽을 수 있는 사람만 그 인격 행을 봅니다.

```
using (
  app.current_app_user_id() is not null
  and not app.is_guest()
  and app.can_read_master_table(master_table)   -- 신설 헬퍼
)
```

`guest_accounts_list`의 `personas` CTE도 같은 규칙으로 맞춥니다. **화면만 고치면 안 됩니다** — 정책이 열려 있으면 PostgREST로 표를 직접 읽을 수 있고, *UI에서 숨기는 것은 보안이 아닙니다*.

## 8. M&A — 자료를 옮기지 않고 여는 목록을 만듭니다

### 8.1 모듈은 둘이고 종류가 다릅니다

| 모듈 | 누가 보는가 | 담기는 것 |
| :--- | :--- | :--- |
| **요청자료(워크북)** | 매도자 | **요청 항목이 먼저 있고 거기에 회신이 붙습니다**(체크리스트) |
| **데이터룸** | 인수후보 | 공개하기로 고른 자료 목록 |

**같은 종류일 수 없습니다.** 담기는 것이 다르고, 2026-09-03 결정대로 **공유 성격이 종류에 박히므로** 어차피 갈라야 합니다. 티저(`PUBLIC_LINK`)와 IM·데이터룸(`GUEST_ONLY`)도 같은 이유로 종류가 갈립니다.

### 8.2 선별은 파일이 아니라 목록입니다

`attachments.program_module_id`는 **컬럼 하나**라 자료 한 건이 모듈 하나에만 속합니다. 그래서 "셀러 자료 100건 중 80건을 데이터룸에 넣는다"를 파일로 하면 셋 다 실패합니다.

* **복제** — 두 목록이 어긋나고, 셀러가 원본을 고쳐도 데이터룸은 옛 파일을 듭니다(2026-09-06 파일·링크 한 표 결정과 같은 판단).
* **이동** — 넣는 순간 셀러 모듈에서 사라져, **셀러가 자기가 낸 자료를 못 보게 됩니다.**
* **전량 참조**(`app.attachment_ref_sources`) — 고를 수가 없습니다.

**연결 표 한 벌을 둡니다.** 자료의 집은 하나(셀러가 낸 자리)이고, 데이터룸은 *무엇을 여는가*만 갖습니다.

> [!IMPORTANT]
> **전량이면 함수, 고르면 표.** 2026-09-08 '위치가 아니라 참조' 결정에서 방향을 함수 하나(`app.attachment_ref_sources`)에 모은 이유는 참조가 **전량**이라 행마다 어긋날 자리가 없었기 때문입니다. 여기서는 **골라야** 하므로 그 선택이 데이터입니다. 함수에 넣을 수 없습니다.

### 8.3 단계 — 바이어 개별이 아니라 단계로 가릅니다

지금 모듈은 그 사업 게스트 **전원**에게 열립니다. NDA 전 인수후보와 후 인수후보를 갈라야 하므로 축 하나를 더합니다.

* `program_participants.stage` — 이 참여자가 어느 단계인가
* `program_modules.min_stage` — 이 모듈이 어느 단계부터 보이는가

AC·FUND는 값이 비어 있어 영향이 없습니다(기본 = 전원). **바이어 개별 커스터마이즈는 두지 않습니다** — 실무에서 갈리는 것은 단계이고, 사람 단위로 열면 "누구에게 무엇이 열렸는지"를 아무도 답할 수 없게 됩니다.

### 8.4 인수후보 화면은 원본 건수를 드러내지 않습니다

데이터룸에는 `[80]`만 섭니다. 셀러가 회신한 100이라는 수는 **어디에도 나오지 않습니다** — 무엇이 빠졌는지가 그 자체로 정보이기 때문입니다.

## 9. FUND — 온기보고

**대상은 포트폴리오사 하나**이고, 화면은 조합 개요·공지사항·Q&A 고정 3메뉴 + 온기보고입니다.

온기보고 탭은 **펀드별 모듈 인스턴스**로 두되, **안의 항목은 담당자가 정하지 않습니다.** 서식의 단일 원천이 모태 온기영업보고서이므로([3_5 §3](./3_5_workspace_fund.md)) 항목 구성은 ADMIN 템플릿이 갖고 담당자는 배치와 회차(분기)만 정합니다. 모듈처럼 자유 구성으로 두면 **서식이 펀드마다 달라지고**, 그 값이 영업보고서로 자동 편입되므로 칸이 어긋나는 순간 보고서가 서지 않습니다.

> [!NOTE]
> **이 절은 아이데이션 단계입니다(2026-09-08).** 확정된 것은 *대상은 포트폴리오사 하나*와 *항목은 템플릿이 소유한다* 둘뿐이며, 회차 운용·상태 전이·영업보고서 편입 시점은 FUND 전면 보완 작업에서 확정합니다.

## 10. 이름 — 와이앤아처 포털

외부 앱의 이름을 **`와이앤아처 GUEST` → `와이앤아처 포털`** 로 바꿉니다(2026-09-08 사용자 확정).

바꾸는 이유는 **받는 사람이 읽는 말**이기 때문입니다. 'GUEST'는 손님 등급을 통보하는 말이라, 인수 후보 대기업이나 기관 투자사에게는 어울리지 않습니다. AC 참여기업에게만 맞던 말이 셋을 덮으면 "외부인" 이상을 말하지 못합니다.

**바꾸는 것은 부르는 이름뿐입니다.** 2026-09-07에 `AC`→`Accelerator`로 하며 정한 방식 그대로 — `guest` 워크스페이스 키, `external_*` enum, 정책·감사 로그·저장된 설정은 **그대로 둡니다.** 그 값들은 마이그레이션과 정책 본문에 박혀 있고, 바뀐 것은 부르는 이름 하나입니다.

| 자리 | 종전 | 개정 |
| :--- | :--- | :--- |
| 외부 앱 제목·로그인 lockup | 와이앤아처 GUEST | **와이앤아처 포털** |
| AC·FUND·M&A 사이드바 | GUEST계정 발급 | 그대로 (창구 이름은 §6.2 표 참조) |
| ADMIN | 게스트 계정 관리 | 그대로 |
| 권한 키·enum·정책 | `guest` / `external_*` | **그대로** |

> [!NOTE]
> **`user_type`은 늘리지 않습니다.** 지금 3종(`external_startup`·`external_expert`·`temporary_guest`)은 어디서도 서로 갈라 판정하지 않습니다 — 30여 곳에서 *한 묶음으로* 내부/외부를 가르는 데만 쓰이고 나머지는 라벨입니다. 하나 늘리면 그 30여 곳을 전부 고쳐야 하고, 정작 "이 사람이 무엇인가"는 2026-09-05 결정대로 `master_table`이 답합니다.

이메일 + 비밀번호 2요소. 제목 lockup만 `포털`로 바뀝니다.

한 계정에 맥락이 여럿이면 로그인 직후 한 번 고릅니다. 각 줄은 `[구분] 이름` + `자격 · 이용 종료일`입니다. 구분 배지가 필요한 이유는 워크스페이스가 셋이 되면서 이름만으로 어느 성격의 자리인지 답하지 못하게 되었기 때문입니다.

### 11.3 세 맥락의 사이드바

| | 고정 메뉴 | 원장이 세우는 메뉴 |
| :--- | :--- | :--- |

| **FUND** | 조합 개요 · 공지사항 · Q&A | 온기보고 · 제출 이력 |

메뉴 이름은 **모듈명이 그대로 노출됩니다**(2026-09-08 사용자 확정) — 딜마다 담당자가 지은 이름이 서면 됩니다.

### 11.4 전환기

현행 컴포넌트 그대로입니다. 갈 곳이 하나뿐이면 화살표 없이 이름만 섭니다.

## 14. 완료 기준 (Definition of Done)

1. 같은 회사에 담당자 둘을 각각 발급할 수 있고, 계정과 비밀번호가 갈린다.
2. 같은 사람이 AC·FUND 두 맥락을 가지면 로그인 하나로 둘을 오간다.
3. AC 발급 창구에 `ma_sellers` 인격을 가진 계정이 서지 않는다.
4. `mna` 읽기 권한이 없는 계정으로 `guest_identities`를 직접 조회하면 M&A 행이 0건이다.
5. 셀러가 회신한 자료 중 데이터룸에 넣은 것만 인수후보에게 보이고, 원본은 셀러 화면에 그대로 남는다.
6. 인수후보 화면 어디에도 셀러 회신 총건수가 나오지 않는다.
7. NDA 전 단계 참여자에게 IM·데이터룸 모듈이 서지 않는다.
8. 포트폴리오사가 온기보고를 제출하고, 보완요청을 받고, 재제출할 수 있다.
9. 외부 앱 제목이 `와이앤아처 포털`이고, `guest` 권한 키·`external_*` enum·정책은 바뀌지 않았다.
10. [11_migration_security_gate.md](../docs_dev/11_migration_security_gate.md) 체크리스트 통과.

## 15. 미결 사항

* **IM을 어느 문으로 여는가** — 퍼블릭 링크 / 매직 링크 / 게스트 계정. 셋 다 도착지가 같아(모듈 하나를 보는 화면) 선별 구조와 무관하므로 나중에 정합니다. 판단 기준은 하나 — **유출됐을 때 누가 흘렸는지 지목해야 하는가.** 지목이 필요하면 계정, 열람 사실 확인이면 매직 링크, 배포가 목적이면 퍼블릭 링크입니다.
  * 매직 링크를 만들게 되면 **"링크 계통"이 아니라 "로그인 방법"으로 붙입니다.** `guest_credentials`의 재설정 토큰과 거의 같은 물건이고, 계정 축에 얹으면 차단·기간·감사가 그대로 따라옵니다. 독립 계통으로 두면 담당자가 게스트를 차단해도 링크는 살아 있는 상태가 생깁니다.
* **LP·조합원 포털** — 이번 범위 밖(§4). 여는 날 정해야 하는 것은 *조합 전체 중 어디까지 보여주는가*(밸류·회수·관리보수)이며, 포트폴리오사와 **다른 맥락 타입**으로 세웁니다.
* **FUND 온기보고의 회차 운용·영업보고서 편입 시점** — FUND 전면 보완에서 확정(§9).
* **M&A 인수후보가 자료를 올리는가**(LOI·인수 제안서) — 올린다면 셀러 쪽과 대칭인 회신 구조가 하나 더 필요합니다.
* **공개 전용 도메인** — 2026-09-03부터 미정인 채 남아 있습니다(`VITE_PUBLIC_MODULE_BASE_URL`·`VITE_APPLY_BASE_URL`·`ALLOWED_ORIGINS`). 티저를 퍼블릭 링크로 뿌리기로 하면 이 건이 선행됩니다.
