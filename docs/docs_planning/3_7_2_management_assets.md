# [3-7-2] MANAGEMENT 자산 관리 기획서

본 문서는 MANAGEMENT 워크스페이스 `자산 관리`(`/management?tab=assets`) 화면의 데이터 모델과 기능 요건을 명세합니다. 현재 화면은 자산명·분류(자유입력)·상태·할당 대상·회수 예정일 다섯 열의 조회 전용 표에 머물러 있어, **자산을 등록하고 취득부터 폐기까지 추적하는 원장(Ledger)** 으로 확장하는 것이 본 기획의 골자입니다. 상위 워크스페이스 기획은 [3_7_workspace_management.md](./3_7_workspace_management.md), 지사 원장 구조는 이미 구현된 `지사 관리`(`public.branches`)를 전제합니다.

---

## 1. 목적

* **자산의 소재를 지사 단위로 확정합니다**: 노트북·차량·비품이 어느 지사에 속한 물건인지가 기록되지 않아, 지사가 늘어난 뒤로는 "어디에 있는 자산인가"에 답할 수 없었습니다. 지사 원장(`branches`)을 참조하는 필수 귀속 축을 두어 **지사별 자산대장**이 곧 화면 구조가 되게 합니다.
* **취득·보유·폐기의 전 주기를 한 행에 담습니다**: 취득일자·금액·폐기일자를 원장에 두어 보유 기간과 취득 원가를 자산 단위로 조회할 수 있게 합니다.
* **소유 형태를 구분합니다**: 구매·리스·렌탈·기타를 `분류`로 명시해, 회사 소유 자산과 계약 기간이 있는 자산을 같은 표에서 갈라 봅니다.
* **반출 통제의 기준값을 원장에 둡니다**: OFFICE `반출대장`이 참조할 **반출 가능 여부**를 자산 속성으로 확정하여, 반출 기록 화면이 별도 판단 없이 후보를 거를 수 있게 합니다.

---

## 2. 이 문서가 다루는 범위

* **포함**:
  * 자산 원장(`public.assets`) 필드 확장 정의와 제약 규칙
  * 분류(취득 형태) 4종 및 상태 4종의 값 체계와 전이 규칙
  * 지사(`branches`) 필수 귀속과 지사 탭 기반 목록 구조
  * 자산 등록·수정 폼과 목록 표의 열 구성
  * 반출 가능 여부 토글과 OFFICE `반출대장` 연계 지점
  * 권한·RLS 및 마이그레이션 설계
* **제외(별도 범위)**:
  * **반출대장 화면 자체의 기능 명세** — 반출 신청·승인·반납 흐름은 OFFICE 소유이며 후속 문서에서 다룹니다. 본 문서는 자산 쪽 기준값(`is_portable`)까지만 정의합니다.
  * **감가상각·재무 회계 연동** — 금액은 취득가 단일 값이며, 상각 스케줄과 재무제표 반영은 다루지 않습니다.
  * **유지보수 이력 원장** — 상태 `MAINTENANCE`로 현재 시점만 표기하며, 정비 이력 테이블은 후속 과제입니다.
  * **소프트웨어 라이선스 좌석 관리** — 라이선스는 품목의 하나로 등록하되 좌석 수·갱신 주기 관리는 범위 밖입니다.

---

## 3. 핵심 사용자

* **자산 담당자 (`management` write)**: 자산을 등록·수정하고 할당 대상과 상태를 갱신하며, 폐기 시 폐기일자를 확정합니다.
* **지사 관리자 (`super_admin`)**: `지사 관리`에서 지사를 세팅하고, 그 지사에 귀속된 자산 현황을 확인합니다.
* **경영지원 조회자 (`management` read)**: 지사별 보유 자산과 취득 원가 합계를 조회합니다. 등록·수정은 하지 않습니다.
* **임직원**: 본인에게 할당된 자산을 확인하는 대상이며, 본 화면에는 직접 진입하지 않습니다(할당 대상으로만 등장합니다).

---

## 4. 정보 구조 (Information Architecture)

`자산 관리` 탭은 **지사 탭 → 자산 표 → 등록/수정 모달** 3단으로 구성합니다. 지사 탭은 `지사 관리`가 세팅한 활성 지사 목록을 그대로 사용하므로, 지사가 추가되면 자산 화면의 탭도 함께 늘어납니다.

```
[자산 관리 탭]
 ├── 상단 액션 (자산 등록)
 ├── 지사 탭 (지사 관리의 활성 지사 목록 — 전사 공용 원장)
 └── 자산 표 (선택 지사 소속 자산)
      ├── 도메인 열: 자산명 · 품목 · 분류 · 상태 · 할당 대상 · 취득일자 · 폐기일자 · 금액 · 반출
      ├── 표준 열: 수정일 · 관리(비활성화)   ← 등록자 열은 노출하지 않는다
      └── 행 클릭 → 자산 수정 모달(등록 모달과 동일 폼)
```

> [!NOTE]
> **등록자 열을 두지 않습니다.** 자산은 "누가 등록했는가"보다 "지금 누구에게 할당되어 있는가"가 관리 축이며, 원장에 `created_by`가 없습니다. 공용 표 컴포넌트(`DataTable`)의 표준 메타 열 중 **수정일만 남기고 등록자는 끕니다**(`showAuthor={false}`).

## 5. 자산 원장 데이터 모델

### 5.1 필드 정의

| 화면 항목 | 컬럼 | 타입 | 필수 | 설명 |
| :--- | :--- | :--- | :---: | :--- |
| 자산명 | `name` | `text` | O | 식별 열. 예: `MacBook Pro 16 (2025)` |
| 품목 | `item_type` | `text` | | 노트북·차량·라이선스·비품 등 물건의 종류. 기존 `category` 컬럼을 개칭해 데이터를 승계 |
| 분류 | `acquisition_type` | `public.asset_acquisition` | O | 구매/리스/렌탈/기타. 기본값 `PURCHASE` |
| 상태 | `status` | `public.asset_status` | O | 할당됨/가용/유지보수/폐기. 기본값 `AVAILABLE` |
| 지사 | `branch_id` | `uuid` → `branches(id)` | O | 자산의 소재 지사. 지사 탭의 기준 축 |
| 관리자 | `manager_id` | `uuid` → `users(id)` | | 이 물건을 맡은 내부 임직원 한 명. OFFICE 반출대장이 표에 적는 값이며, 반출 요청·승인을 받는 상대 |
| 할당 대상 | `assigned_to` | `uuid` → `users(id)` | | 이 물건을 지급받아 쓰는 내부 임직원 한 명. 외부 게스트 계정은 선택 불가 |
| 취득일자 | `acquired_on` | `date` | | 구매·리스·렌탈 개시일 |
| 폐기일자 | `disposed_on` | `date` | | 값이 있으면 상태는 반드시 `RETIRED` |
| 금액 | `amount` | `numeric(14,2)` | | 취득가(원). 0 이상 |
| 보유 수량 | `quantity` | `integer` | O | 기본값 1, 1 이상. 같은 물건을 여러 개 두는 자산에서만 커지며, OFFICE 반출대장의 잔여 계산 기준 |
| 반출 가능 여부 | `is_portable` | `boolean` | O | 토글. 기본값 `false`(반출 불가) |
| 반출 시 승인 필요 | `requires_approval` | `boolean` | O | 토글. 기본값 `false`. 반출 가능이 켜져 있을 때만 노출·의미를 가짐 |
| 중요 | `is_pinned` | `boolean` | O | 체크박스. 기본값 `false`. 켜면 목록 정렬을 건너뛰고 최상단에 고정되며 번호 칸이 핀 표식으로 바뀜 |
| 회수 예정일 | `return_due` | `date` | | 기존 컬럼 유지. 리스·렌탈 반납 예정일 및 할당 자산 회수 예정일 |
| 사진 | `photo_paths` | `text[]` | | `asset-photos` 버킷 키 배열(최대 5장, 순서 = 표시 순서). 기본값 `{}` |
| 비고 | `note` | `text` | | 자유 메모 |
| 수정일 | `updated_at` | `timestamptz` | 자동 | 트리거(`app.set_updated_at`)가 갱신. 표에 노출 |
| 비활성 | `deleted_at` | `timestamptz` | | soft delete. 물리 삭제하지 않음 |

> [!NOTE]
> **`분류`(화면)와 `acquisition_type`(컬럼)의 이름이 다른 이유** — 화면에서 부르는 이름은 사용자가 쓰는 말인 `분류`를 따르되, 컬럼은 그 값이 실제로 무엇을 가르는지(취득 형태)를 이름에 남깁니다. 기존 `category`(자유입력 품목)를 `item_type`으로 개칭하는 것도 같은 이유이며, 이름을 재활용하면 뜻이 바뀐 컬럼이 남아 이후 조회가 어긋납니다.

### 5.2 분류(취득 형태) 4종

| 값 | 라벨 | 의미 |
| :--- | :--- | :--- |
| `PURCHASE` | 구매 | 회사가 소유권을 가진 자산. 기본값 |
| `LEASE` | 리스 | 리스 계약 자산. 계약 종료일을 `회수 예정일`에 기입 |
| `RENTAL` | 렌탈 | 단기 렌탈 자산. 계약 종료일을 `회수 예정일`에 기입 |
| `OTHER` | 기타 | 무상 임대·기증 등 위 셋에 들지 않는 취득 형태 |

### 5.3 상태 4종과 전이 규칙

기존 값 체계(`ASSIGNED`/`AVAILABLE`/`MAINTENANCE`/`RETIRED`)를 그대로 유지하며 배지 톤도 현행과 같습니다.

| 값 | 라벨 | 배지 | 규칙 |
| :--- | :--- | :--- | :--- |
| `AVAILABLE` | 가용 | success | 할당 대상이 비어 있는 보유 자산 |
| `ASSIGNED` | 할당됨 | info | **할당 대상이 반드시 지정되어야 합니다** |
| `MAINTENANCE` | 유지보수 | warning | 정비 중. 할당 대상은 유지할 수 있습니다 |
| `RETIRED` | 폐기 | neutral | 폐기 처리. 폐기일자를 함께 기입합니다 |

* **`폐기일자` → `상태`는 단방향 구속입니다**: 폐기일자가 입력되면 상태는 `RETIRED`여야 하지만, 그 역은 강제하지 않습니다. 날짜를 모르는 과거 폐기 자산을 등록할 수 있어야 하기 때문입니다.
* **폐기 시 할당 대상을 비웁니다**: 폐기 상태로 전환할 때 화면이 할당 대상을 자동으로 비우고, 사용자가 되돌릴 수 있게 안내합니다.

### 5.4 사진 첨부 (자산당 최대 5장)

자산은 글로 적은 사양만으로 같은 물건인지 가리기 어렵습니다(같은 모델의 노트북 여러 대, 흠집이 난 자리, 명판에 붙은 관리 번호). 사진이 그 확인을 대신하므로 원장이 함께 들고 있습니다.

* **저장 형태는 경로 배열 하나입니다**: `assets.photo_paths text[]`에 Storage 오브젝트 키를 담고, **배열 순서가 곧 표시 순서**입니다. 별도 테이블을 두지 않는 이유는 사진에 붙는 속성이 없기 때문입니다 — 순서 외에 적을 것이 없는 값에 테이블을 주면 조인만 늘고 규칙은 그대로입니다.
* **자료(`attachments`)와는 다른 축입니다**: 자료는 파일명·업로더·크기·다운로드 로그가 필요해 테이블이 맞고, 사진은 자산을 알아보기 위한 이미지라 원장 컬럼이 맞습니다. 둘을 합치지 않습니다.
* **버킷은 비공개입니다**: `asset-photos`(공개 아님)를 쓰고 표시에는 단기 Signed URL을 발급합니다. 시리얼 명판·차량 번호판처럼 식별에 쓰이는 것이 함께 찍히므로, 회의실 사진(`meeting-room-photos`, 공개 버킷)과 달리 기본값인 비공개를 따릅니다.
* **상한은 5장이며 DB가 최종 판정합니다**: 화면은 다섯 장을 채우면 첨부 자리를 감추고, `assets_photo_paths_max` check 제약이 화면을 거치지 않는 경로까지 막습니다.
* **업로드는 고른 자리에서 끝납니다**: 폼 저장에 파일 업로드를 묶으면 넷째 장에서 실패했을 때 무엇이 저장되고 무엇이 안 됐는지 알 수 없습니다. 사진은 선택 즉시 올리고 폼은 경로 배열만 저장합니다. 그 대신 등록을 취소하면 방금 올린 오브젝트가 참조 없이 남으며, 비공개 버킷이므로 물리 삭제를 하지 않는 원칙을 지키는 쪽을 택했습니다.
* **삭제는 배열에서 빼는 것입니다**: Storage 오브젝트는 지우지 않습니다(물리 삭제 금지).

## 6. 지사 연동 (지사 관리와의 관계)

* **원장은 하나입니다**: 지사 목록은 MANAGEMENT `지사 관리`가 소유한 `public.branches`가 단일 원천이며, 자산 화면은 이를 **조회만** 합니다. 자산 화면에서 지사를 만들거나 고치지 않습니다.
* **귀속은 필수입니다**: `branch_id`는 `NOT NULL`이며 등록 폼에서 지사를 고르지 않으면 저장할 수 없습니다. 귀속 없는 자산이 남으면 지사 탭 어디에도 뜨지 않아 사실상 유실되기 때문입니다.
* **탭 목록은 활성 지사만 노출합니다**: `지사 관리`에서 비활성화한 지사는 탭에서 사라지되, 그 지사에 귀속된 자산 행은 보존됩니다. 지사를 다시 활성화하면 탭과 함께 자산도 되돌아옵니다.
* **자산 이동은 지사 변경으로 표현합니다**: 별도의 이동 이력 테이블을 두지 않고, 수정 폼에서 지사를 바꾸는 것으로 처리합니다. 이동 이력이 필요해지면 후속 과제로 다룹니다.

> [!NOTE]
> 회의실 예약의 지점 탭은 이 원장이 아니라 `meeting_places`(ADMIN `회의실 관리` 소유)를 씁니다. 자산은 회의실과 달리 **조직 정보로서의 지사**에 귀속되므로 `branches`를 참조합니다 — 두 목록을 혼동하지 않습니다.

## 7. 반출 가능 여부와 OFFICE 반출대장

* **자산 원장이 기준값을 소유합니다**: `is_portable`은 "이 자산을 사외로 들고 나갈 수 있는가"에 대한 관리자의 사전 판단이며, 자산 등록·수정 폼의 **토글**로만 바뀝니다.
* **반출대장은 이 값을 소비합니다**: OFFICE `반출대장`(`/office?tab=outbound`)은 반출 기록을 남길 때 **`is_portable = true`이고 상태가 `RETIRED`가 아닌 자산**만 후보로 제시합니다. 반출대장이 자산의 성격을 다시 판단하지 않게 하기 위함입니다.
* **반출 흐름과 그 원장은 OFFICE 소유입니다**: 반출 신청·승인·반납 확인 흐름은 [3_1_2_office_asset_checkout.md](./3_1_2_office_asset_checkout.md)가 정의하며, 본 문서는 자산 쪽 기준값까지를 소유합니다.
* **승인 필요 여부(`requires_approval`)도 자산 원장이 소유합니다**: "이 물건은 반출 시 승인을 거쳐야 하는가"를 자산별 토글로 둡니다. **반출 가능 여부가 켜져 있을 때만 노출**하며(반출 불가 자산에는 뜻이 없는 질문입니다), 기본값은 꺼짐입니다. 품목(`item_type`)은 원장이 없는 자유입력 텍스트라 정책을 매달 자리가 없어(`노트북`과 `랩탑`이 서로 다른 정책을 갖게 되고 오타가 곧 정책 구멍이 됩니다) 자산 단위로 두며, 품목 단위 운용은 **검색으로 골라 선택 요약 줄에서 일괄 설정**하는 경로로 지원합니다.

## 8. 화면 사양

### 8.1 목록

* **지사 탭**: 활성 지사를 순서대로 노출하며, 첫 진입 시 첫 번째 지사를 선택합니다. 지사가 하나도 없으면 "지사 관리에서 지사를 먼저 등록하세요" 안내를 표시합니다.
* **표 열 구성**: `자산명`(식별 열) · `품목` · `분류` · `상태`(배지) · `관리자` · `할당 대상`(임직원 이름) · `취득일자` · `폐기일자` · `금액`(우측 정렬·천 단위 구분) · `반출`(가능/불가 배지) + 표준 열 `수정일` · `관리`.
* **표준 열 규칙**: 등록자 열은 끄고(`showAuthor={false}`) 수정일은 남깁니다. 관리 열에는 비활성화 버튼만 두며, 수정은 행 클릭으로 엽니다.
* **관리자와 할당 대상은 이웃한 두 열입니다**: 맡은 사람과 쓰는 사람은 다른 축이며, 공용 비품처럼 누구에게도 지급되지 않는 물건은 관리자만 있고 할당은 비어 있는 것이 정상입니다.
* **사람 표기**: `users` 원장의 이름을 붙여 보여 주며, 값이 없으면 빈 칸으로 둡니다. 연락처·이메일은 목록에 노출하지 않습니다.
* **정렬**: 중요(`is_pinned`) 자산이 먼저 서고, 그 안에서 자산명 오름차순입니다. 폐기 자산은 목록 하단으로 밀지 않고 상태 배지로만 구분합니다.
* **중요(상단 고정)**: 중요로 표시한 자산은 번호(No.) 대신 핀 표식(📌)을 받습니다. 게시판의 공지와 같은 장치이며, 정렬을 건너뛴 행에는 순번이 뜻을 잃기 때문에 그 자리를 표식에 내어 줍니다. 정렬은 **서버에서** 겁니다 — 페이지 안에서만 올리면 2페이지의 중요 자산이 1페이지 맨 위에 서지 못해 "맨 위"가 "이 페이지 맨 위"라는 다른 뜻이 됩니다.
* **중요 값은 자산의 속성입니다**: OFFICE 반출대장도 같은 값으로 같은 자리에 세웁니다(화면마다 다른 순서를 두지 않습니다).

### 8.2 등록·수정 모달

등록과 수정은 같은 폼을 쓰며, 제목만 `자산 등록`/`자산 수정`으로 갈립니다.

```
[자산 등록 / 자산 수정]
 ├── 1행: 자산명(필수)            | 시리얼 번호
 ├──      중요 (체크박스 — 목록 최상단 고정)
 ├── 2행: 품목(자유입력, 자동완성) | 분류(셀렉트, 필수)
 ├── 3행: 보유 수량(필수, 기본 1)
 ├── 4행: 지사(셀렉트, 필수)      | 상태(셀렉트, 필수)
 ├── 5행: 관리자(임직원 검색)     | 할당 대상(임직원 검색)
 ├── 6행: 금액(원)               | 결제 주기(셀렉트, 필수)
 ├── 7행: 취득일자               | 만료일(폐기 상태면 폐기일자)
 ├── 8행: 반출 가능 여부 (토글)
 ├──      반출 시 승인 필요 (토글 — 반출 가능이 켜졌을 때만)
 ├── 사진 (최대 5장, 썸네일 격자 + 첨부 자리)
 ├── 비고 (여러 줄)
 └── 푸터: [비활성화]            [취소] [저장]
```

* **중요는 폼 맨 앞자리입니다**: 필드 차례는 표의 열 차례를 따르는데, 이 값이 목록에서 차지하는 자리가 맨 앞의 번호 칸이기 때문입니다. 아래 반출 묶음(토글)에 넣지 않는 이유는 축이 다르기 때문입니다 — 반출 가능·승인 필요는 물건을 어떻게 다루는가이고, 중요는 목록에서 어디에 서는가입니다.
* **품목은 자유입력 + 자동완성입니다**: 이미 등록된 품목 값을 목록으로 제안해 표기 흔들림(`노트북`/`랩탑`)을 줄이되, 새 품목은 그대로 입력할 수 있게 둡니다. 태그 원장으로 승격하는 것은 후속 과제입니다.
* **관리자와 할당 대상은 한 줄에 나란히 둡니다**: 두 값이 답하는 질문이 "이 물건을 누가 맡았는가"와 "지금 누가 쓰는가"로 갈리기 때문입니다. 관리자는 상태와 무관하게 유지되고(폐기해도 비우지 않습니다 — 맡은 사람은 물건을 정리한 뒤에도 그 물건을 설명할 수 있습니다), 할당 대상만 폐기 시 비워집니다.
* **둘 다 내부 임직원만 고릅니다**: 외부 스타트업·전문가·임시 게스트 계정은 후보에서 제외합니다.
* **금액은 원 단위 정수로 입력받고** 표시할 때 천 단위 구분 기호를 붙입니다.
* **비활성화는 저장과 다른 무리에 둡니다**: 지사 폼과 같은 규칙으로 푸터 왼쪽 끝에 배치해, 저장하려다 누르는 자리를 만들지 않습니다.
* **사진은 값 입력이 끝난 뒤에 둡니다**: 파일을 고르는 동안은 폼이 멈춘 것처럼 보이는 자리라, 자산명·금액 같은 필수 값을 적는 흐름 중간에 끼우지 않습니다. 넘치게 고르면 앞에서부터 받고 몇 장만 붙었는지 알리며, 한 장이 실패해도 올라간 사진은 살립니다.

### 8.3 비활성화(soft delete)

자산은 물리 삭제하지 않습니다. 비활성화는 `deleted_at`을 채우는 것이며, 목록에서 사라집니다. **폐기(`RETIRED`)와 비활성화는 다른 축입니다** — 폐기는 자산의 실물 상태이고, 비활성화는 잘못 등록한 행을 목록에서 걷어내는 조치입니다.

## 9. 권한·RLS

* **테이블은 신설되지 않습니다**: `public.assets`는 이미 MANAGEMENT 워크스페이스 게이트로 RLS가 걸려 있습니다(`assets_mgmt_select`/`_insert`/`_update`). 컬럼 확장은 이 정책을 그대로 승계합니다.
* **조회**: `app.can_read_workspace('management')`. 외부 게스트는 접근하지 못합니다.
* **쓰기**: `app.can_write_workspace('management')`. 지사 원장은 관리자 전용이지만, 자산 등록·수정은 경영지원 실무자가 수행하므로 워크스페이스 쓰기 권한으로 충분합니다.
* **DELETE 정책은 만들지 않습니다**: soft delete만 사용합니다.
* **사진 버킷은 원장과 같은 게이트를 씁니다**: `asset-photos`(비공개)의 `storage.objects` 정책은 조회 `app.can_read_workspace('management')` / 업로드·수정 `app.can_write_workspace('management')`이며 DELETE 정책은 없습니다. 원장은 못 보는데 사진은 볼 수 있는(또는 그 반대) 상태를 만들지 않기 위해서입니다.
* **감사 로그 대상이 아닙니다**: 자산 정보는 개인정보 원본·권한 변경·대량 Export에 해당하지 않습니다. 다만 `할당 대상`은 임직원 식별자이므로 목록에 이름 외 개인 식별 정보를 덧붙이지 않습니다.

## 10. 마이그레이션 설계

새 테이블 없이 `public.assets` 확장 한 건으로 처리합니다.

1. **enum 신설**: `public.asset_acquisition`(`PURCHASE`/`LEASE`/`RENTAL`/`OTHER`) — 멱등 생성(`duplicate_object` 무시).
2. **기존 컬럼 개칭**: `assets.category` → `assets.item_type`. 기존 값(`노트북`·`차량`·`라이선스`·`비품`)이 품목으로 그대로 승계됩니다. 양쪽 컬럼 존재 여부를 확인해 재실행에도 안전하게 둡니다.
3. **컬럼 추가**: `acquisition_type`(기본 `PURCHASE`, NOT NULL) · `branch_id` · `acquired_on` · `disposed_on` · `amount` · `is_portable`(기본 `false`, NOT NULL).
4. **지사 백필 후 NOT NULL**: `branch_id`가 빈 기존 행을 정렬 순서상 첫 활성 지사로 채운 뒤, 남은 `NULL`이 없을 때만 `SET NOT NULL`을 겁니다. 지사가 하나도 없는 환경에서 마이그레이션이 실패하지 않도록 조건부로 두고, 건너뛴 경우 `raise notice`로 알립니다.
5. **제약 추가**:
   * `disposed_on >= acquired_on` (둘 다 있을 때)
   * `amount >= 0`
   * `disposed_on is not null → status = 'RETIRED'`
   * `status = 'ASSIGNED' → assigned_to is not null`
6. **인덱스**: `(branch_id, name)` — 지사 탭 조회가 기본 경로입니다.
7. **트리거**: `trg_assets_updated_at`이 이미 걸려 있어 추가 작업이 없습니다.

**보안 게이트 점검**([11_migration_security_gate.md](../docs_dev/11_migration_security_gate.md)): 소유 워크스페이스 `management` / 데이터 등급 `Internal` / 접근 주체 내부 임직원 / Scope `global` / 감사 로그 미대상. 새 테이블·새 RPC·`SECURITY DEFINER` 함수·Storage 정책이 없으므로 기존 RLS 정책을 승계하며, DELETE 정책은 추가하지 않습니다.

**중요 표시 후속 마이그레이션**(`20260730240000_asset_pinned.sql`): `is_pinned boolean not null default false` 컬럼과 정렬 인덱스 `(branch_id, is_pinned desc, name)`를 추가하고, `public.portable_assets` 뷰에 같은 값을 실어 OFFICE 반출대장도 같은 순서로 세웁니다. 새 테이블·RPC·`SECURITY DEFINER` 함수·Storage 정책이 없어 기존 워크스페이스 RLS를 그대로 승계하며, 뷰는 본문의 `app.is_internal_user()` 게이트와 `authenticated` 한정 `GRANT`를 유지합니다.

**사진 첨부 후속 마이그레이션**(`20260730160000_asset_photos.sql`): `photo_paths text[] not null default '{}'` 컬럼과 check 제약 2종(최대 5장 / 빈 값·`null` 경로 금지), 비공개 버킷 `asset-photos`와 `storage.objects` 정책 3종(SELECT/INSERT/UPDATE, DELETE 없음)을 추가합니다. Storage 정책이 생기므로 보안 게이트를 다시 통과시켰습니다 — 버킷은 기본 비공개(§3 체크리스트), 권한 판정은 `app.can_read_workspace`/`can_write_workspace` 헬퍼 경유, 개인정보 원본·다운로드 로그 대상이 아니라 `access_logs` 경로는 두지 않습니다.

## 11. 검증 규칙 (DB 제약 ↔ 화면 안내)

| 규칙 | DB | 화면 |
| :--- | :--- | :--- |
| 자산명 필수 | `not null` | 빈 값이면 저장 버튼 비활성 |

## 12. 후속 과제

* **자산 표의 반출 현황 파생 열** — 지금 나가 있는 자산에 반출자·반납 예정일을 표기(원장은 [3_1_2](./3_1_2_office_asset_checkout.md), 자산 원장에 상태를 저장하지 않고 파생).
* **품목 태그 원장 승격** — 자유입력 `item_type`을 태그 관리(`TAG_CONFIGS`) 원장으로 올려 표기를 통일.
* **자산 이동 이력** — 지사 간 이동과 할당 변경을 시계열로 남기는 이력 테이블.
* **유지보수 이력** — 정비 일자·비용·업체 기록.
* **지사별 취득 원가 집계** — 경영 현황 대시보드에 지사별 보유 자산 수와 취득가 합계 타일 추가.

## 13. 테스트 기준

* 지사 A 탭에서 자산을 등록하면 그 지사 탭에만 나타나고, 지사 B 탭에는 나타나지 않는다.
* 지사를 선택하지 않고 저장을 시도하면 저장되지 않는다.
* 상태를 `할당됨`으로 두고 할당 대상을 비우면 저장이 거부된다.
* 폐기일자를 취득일자보다 앞선 날짜로 입력하면 저장이 거부된다.
* 폐기일자를 입력하면 상태가 `폐기`로 전환되고, 저장 후 목록 배지가 `폐기`로 표시된다.
* 반출 가능 토글을 켠 자산만 이후 반출대장 후보 조회에 포함된다.
* 반출 가능 토글이 꺼져 있으면 승인 필요 토글이 폼에 나타나지 않는다.
* 여러 자산을 선택해 일괄 설정하면 선택한 자산의 승인 필요 여부가 한 번에 바뀐다.
* 목록 표에 `등록자` 열이 없고 `수정일` 열이 있으며, 자산을 수정하면 수정일이 갱신된다.
* 비활성화한 자산은 목록에서 사라지되 DB 행은 남는다(`deleted_at` 세팅, 물리 삭제 없음).
* 사진을 다섯 장 붙이면 첨부 자리가 사라지고, 한 장을 지우면 다시 나타난다.
