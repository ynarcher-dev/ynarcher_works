# [3-7-4] MANAGEMENT 거래처 정보 기획서

본 문서는 MANAGEMENT 워크스페이스 `거래처 정보`(`/management?tab=partners`) 화면의 데이터 모델과 기능 요건을 명세합니다. 이 화면은 **회사가 대금을 주고받는 상대(거래처)의 단일 원장(Ledger)** 이며, 상위 워크스페이스 기획은 [3_7_workspace_management.md](./3_7_workspace_management.md)가 소유합니다.

> [!NOTE]
> **구현 상태(2026-09-03)**: 거래처 코드 자동 채번, 거래처명, 구분(개인/법인), 사업자등록번호(개인은 생년월일), 은행명·계좌번호·예금주, 증빙 서류 2종(사업자등록증 또는 신분증 / 통장사본), 사용 여부가 화면과 원장에 연결되어 있습니다. OFFICE `거래처 정보` 전사 조회 목록과 전자결재·정산 연계는 후속입니다.

---

## 1. 목적

* **지급 상대를 원장으로 확정합니다**: 어느 회사에 어느 계좌로 돈을 보내는지가 담당자의 파일과 메일에 흩어져 있어, 담당이 바뀌면 같은 거래처가 두 번 등록되거나 옛 계좌로 송금되는 일이 생깁니다. 코드·상호·계좌·증빙을 한 행에 모아 그 판단의 근거를 한곳에 둡니다.
* **거래처를 부르는 이름을 코드로 고정합니다**: 상호는 바뀌고 표기도 흔들리지만(`(주)와이앤아처`/`와이앤아처(주)`), 코드는 발급 후 바뀌지 않습니다. 전표·정산이 가리키는 값이 이 코드입니다.
* **증빙을 지급 판단과 같은 자리에 둡니다**: 사업자등록증·통장사본을 원장에 붙여, 계좌를 확인하려고 메일함을 뒤지지 않게 합니다.
* **거래 중단을 삭제와 구분합니다**: 거래가 끝난 상대도 과거 지급 내역을 설명해야 하므로 목록에 남기고, `사용 여부`로만 가립니다.

---

## 2. 이 문서가 다루는 범위

* **포함**:
  * 거래처 원장(`public.trade_partners`) 필드 정의와 제약 규칙
  * 거래처 코드 체계(영문 2글자 접두어 + 일련번호 5자리)와 채번 규칙
  * 구분(개인/법인)에 따라 갈리는 등록번호·서류의 의미
  * 계좌 세 값(은행·계좌번호·예금주)의 동반 규칙
  * 증빙 서류 2종의 저장 위치와 열람 감사 경로
  * 목록·등록/수정 모달의 화면 사양, 권한·RLS, 마이그레이션 설계
* **제외(별도 범위)**:
  * **OFFICE `거래처 정보` 전사 조회 목록** — 노출 범위와 마스킹 규칙을 정한 뒤 연결합니다(§12).
  * **NETWORKS 외주/거래 마스터(`public.vendors`)** — 네트워크 관계 원장이며 본 원장과 다른 축입니다(§6).
  * **전자결재·정산 연계** — 결재 문서에서 거래처를 고르는 흐름은 후속 범위입니다.

---

## 3. 핵심 사용자

* **경영지원(management 쓰기 권한자)**: 거래처를 등록·수정하고 증빙을 붙입니다. 지급 직전에 계좌를 확인하는 사람도 여기입니다.
* **경영진(management 읽기 권한자)**: 거래처 목록과 사용 여부를 조회합니다.
* **그 밖의 내부 사용자**: 본 화면에 접근하지 않습니다. 계좌번호와 개인 거래처의 생년월일이 한 행에 있어 조회 범위를 좁혔습니다(§9).

---

## 4. 정보 구조 (Information Architecture)

* **자리**: MANAGEMENT 사이드바 `재무 관리` 바로 아래입니다. 돈이 나가는 상대를 다루는 일이라 재무 블록에 둡니다.
* **화면 한 장**: 검색(헤더) → 필터(구분·사용 여부) → 표 → 등록/수정 모달. 상세 페이지를 따로 두지 않습니다 — 한 거래처가 가진 값이 열 칸 남짓이라 확인과 수정이 같은 화면에서 끝납니다.
* **정렬**: 코드 오름차순입니다. 코드가 곧 등록 순서라 방금 등록한 거래처는 마지막 페이지에 있습니다. 이름으로 찾는 일은 검색이 대신합니다.

---

## 5. 거래처 원장 데이터 모델

### 5.1 필드 정의

| 컬럼 | 타입 | 규칙 |
| :--- | :--- | :--- |
| `code_prefix` | text | 영문 2글자(대문자). 등록 시 담당자가 정합니다. |
| `code_seq` | integer | 1~99999. **서버가 매깁니다**(클라이언트가 보내지 않습니다). |
| `code` | text (생성 열) | `code_prefix + lpad(code_seq, 5, '0')`. 원장 전체에서 유일하며 발급 후 불변입니다. |
| `name` | text | 거래처명. 공백만으로 채울 수 없습니다. |
| `partner_type` | text | `CORPORATE`(법인) / `INDIVIDUAL`(개인). |
| `registration_no` | text | 법인=사업자등록번호 10자리, 개인=생년월일 8자리. **숫자만 저장**합니다. |
| `bank_code` | text | 금융기관 코드 3자리(표준값). |
| `account_no` | text | 숫자와 하이픈. 은행마다 구분 기호가 달라 입력 그대로 둡니다. |
| `account_holder` | text | 예금주. 거래처명과 다를 수 있습니다. |
| `license_path` / `license_name` | text | 사업자등록증(개인은 신분증)의 오브젝트 키와 원본 파일명. |
| `bankbook_path` / `bankbook_name` | text | 통장사본의 오브젝트 키와 원본 파일명. |
| `is_active` | boolean | 사용 여부(거래 중단 축). 기본 `true`. |
| `created_by` / `created_at` / `updated_at` / `deleted_at` | — | 공통 감사 컬럼. 삭제는 soft delete입니다. |

### 5.2 코드 체계와 채번

* **접두어만 사람이 정하고 번호는 서버가 붙입니다**: 담당자는 영문 2글자(예: `YN`)만 고르고, 그 접두어의 다음 번호는 원장 트리거가 매깁니다. 화면은 다음 번호를 미리 보여 주되 그 값을 저장하지 않습니다 — 화면이 읽은 번호를 그대로 저장하면 두 사람이 같은 순간에 등록할 때 같은 번호가 두 번 발급됩니다.
* **채번은 접두어 단위로 잠급니다**: 다음 번호를 세는 동안 같은 접두어의 다른 트랜잭션을 막습니다(`pg_advisory_xact_lock`). 잠그지 않으면 한쪽이 유니크 위반으로 튕기고 사용자에게는 저장 실패로만 보입니다.
* **번호는 재사용하지 않습니다**: 중단·삭제된 거래처도 코드를 계속 점유합니다. 한 번 쓴 번호를 다시 내주면 옛 전표가 가리키는 거래처가 어느 날 다른 회사가 됩니다.
* **코드는 발급 후 불변입니다**: 수정 폼에서 읽기 전용으로 표시하며, 화면 밖 경로로 값이 바뀌면 원장 트리거가 거부합니다.

### 5.3 구분(개인/법인)이 가르는 것

* **한 칸이 두 값을 받습니다**: 등록번호 칸은 법인이면 사업자등록번호, 개인이면 생년월일입니다. 칸을 둘로 나누지 않는 이유는 한 거래처에 어느 쪽이든 하나뿐이라, 나누면 언제나 한 칸이 비어 있고 그 빈 칸이 "아직 안 적었다"인지 "여기 적을 값이 아니다"인지 구분되지 않기 때문입니다.
* **라벨·자릿수·검증이 함께 갈립니다**: 법인은 10자리 + 국세청 검증식, 개인은 8자리 + 실재하는 과거 날짜입니다. 서류 이름도 함께 갈립니다(사업자등록증 ↔ 신분증).
* **구분을 바꾸면 등록번호를 비웁니다**: 남겨 두면 사업자등록번호가 생년월일 칸에 그대로 서서, 자릿수 검증에 걸릴 때까지 담당자는 그 값이 옳다고 읽습니다. 서류 첨부는 비우지 않습니다 — 무엇이 붙어 있는지가 화면에 그대로 보이므로 잘못 붙였다면 그 자리에서 뗍니다.

### 5.4 계좌 세 값은 함께 섭니다

* **은행·계좌번호·예금주는 함께 채우거나 함께 비웁니다**: 반쯤 적힌 계좌는 없는 계좌보다 나쁩니다 — 이체에 쓸 수 없으면서 "계좌가 있다"고 말하기 때문입니다. 화면 검증과 DB check 제약이 같은 규칙을 강제합니다.
* **은행은 고정 목록에서 고릅니다**: 자유입력으로 두면 한 은행이 `국민은행`과 `KB국민은행` 두 이름으로 갈립니다.
* **원장에는 이름이 아니라 금융기관 코드 3자리를 담습니다**: 이름은 바뀌기 때문입니다(KEB하나은행 → 하나은행, 대구은행 → iM뱅크). 이름표는 `partners/config.ts`가 갖습니다.

### 5.5 증빙 서류 2종

* **비공개 버킷(`partner-docs`)에 올리고 원장에는 오브젝트 키와 원본 파일명만 담습니다**: 서명 URL은 만료되는 값이라 저장해 두면 어제 저장한 행이 오늘 열리지 않습니다. 파일명을 키에서 되짚지 않는 이유는 한글 파일명이 키로 안전화되는 순간 되돌릴 수 없기 때문입니다.
* **고른 즉시 올립니다**: 원장 한 행을 쓰는 일에 파일 업로드를 묶으면, 파일에서 실패했을 때 무엇이 저장되고 무엇이 안 됐는지 알 수 없습니다. 대신 등록을 취소하면 올라간 오브젝트는 참조 없이 남습니다(비공개 버킷이므로 물리 삭제 금지 원칙을 지키는 쪽을 택했습니다).
* **떼는 것은 원장에서 키를 비우는 일입니다**: 오브젝트는 지우지 않습니다.

---

## 6. NETWORKS 외주/거래 마스터(`vendors`)와의 관계

* **다른 원장입니다**: `public.vendors`는 "누구와 일하는가"를 담는 네트워크 마스터로 담당자·메모·연락처를 갖고 판정 키가 `networks`입니다. 본 원장은 "누구에게 어느 계좌로 보내는가"를 담습니다.
* **합치지 않는 이유는 노출 범위입니다**: 같은 표에 계좌와 신분증 사본을 얹으면 networks 읽기 권한자 전원에게 그 값이 열립니다. 이름이 비슷하다는 이유로 접근 범위를 넓히지 않습니다.
* **연결은 후속입니다**: 두 원장을 잇는 참조(같은 상대를 가리키는 두 행의 연결)는 필요가 생기는 날 설계합니다.

---

## 7. 화면 사양

### 7.1 목록

* **열 구성**: 코드 / 거래처명 / 구분 / 사업자등록번호(생년월일) / 은행명 / 계좌번호 / 예금주 / 서류 / 사용 여부.
* **등록번호는 여기서 꾸밉니다**: 법인 `123-45-67890`, 개인 `1990-01-01`. 원장에는 숫자만 있습니다 — 표기를 저장하면 같은 번호가 두 모양으로 갈려 중복을 셀 수 없습니다.
* **서류 열은 한 칸입니다**: 붙어 있는 것만 적습니다(`등록증·통장`). 두 열로 나누면 '없음'이 두 번 반복될 뿐입니다.
* **생성자·관리 열을 두지 않습니다**: 관리 축은 "지금 이 거래처와 거래하는가"이지 등록한 사람이 아닙니다. 사용 여부 전환은 행을 열어(모달) 또는 체크박스로 골라 한 번에 합니다.
* **검색**: 거래처명·코드·등록번호·예금주를 함께 훑습니다. 등록번호는 하이픈을 걷어낸 형태로도 봅니다(등록증에 적힌 대로 붙여 넣는 경우).
* **필터**: 구분·사용 여부(다중선택). 두 값을 다 고르면 조건이 없는 것과 같습니다.
* **대용량 업로드를 두지 않습니다**: 계좌와 증빙이 한 벌로 붙는 원장이라 표 한 장으로 옮겨지지 않고, 서류 없이 들어온 행은 결국 한 건씩 다시 열어 채워야 합니다.

### 7.2 등록·수정 모달

* **등록과 수정은 같은 폼이며 코드 칸만 갈립니다**: 등록은 접두어 입력 + 다음 번호 미리보기, 수정은 발급된 코드의 읽기 전용 표시입니다. 고칠 수 없는 값에 입력 칸 모양을 주지 않습니다.
* **중복 등록번호는 막지 않고 알립니다**: 같은 번호가 이미 있으면 어느 거래처와 겹치는지 이름과 코드를 보여 줍니다. 사업장이 둘인 같은 사업자, 같은 생년월일의 개인이 있을 수 있어 저장 자체를 막지는 않습니다.
* **푸터에 삭제를 두지 않습니다**: 거래처는 지우는 것이 아니라 거래를 그만두는 것이고, 그 스위치는 폼 안(`사용 여부`)에 있습니다.

---

## 8. 사용 여부와 삭제

* **`is_active`(사용 여부)**: 거래 중단입니다. 새 지급 대상 목록에서 빠지지만 원장에는 남아 과거 기록을 설명합니다. 목록에서 여러 건을 골라 한 번에 전환할 수 있습니다.
* **`deleted_at`(soft delete)**: 오등록 정리 축입니다. 현재 화면에는 경로를 두지 않았습니다 — 잘못 등록한 거래처도 `사용 여부`를 끄는 것으로 목록에서 가려지고, 코드가 이미 발급된 이상 그 행이 무엇이었는지는 남아 있어야 합니다. 정리 경로가 필요해지면 그때 화면을 엽니다.

---

## 9. 권한·RLS·감사

* **조회**: `app.can_read_workspace('management')`. 내부 사용자 전체로 열지 않습니다 — 계좌번호와 개인 거래처의 생년월일이 한 행에 있어, 지금 이 원장을 읽을 이유가 있는 사람은 지급을 준비하는 경영지원뿐입니다.
* **쓰기**: `app.can_write_workspace('management')`(INSERT·UPDATE 정책 분리). DELETE 정책은 없습니다.
* **담당자 원장을 두지 않습니다**: 행마다 담당을 나누는 원장이 아니므로 3축 규칙의 **공동관리**(management 쓰기 권한자 전원)에 해당합니다.
* **Storage**: `partner-docs` 버킷은 비공개이며 `storage.objects` 정책이 원장과 같은 게이트를 씁니다. 원장은 못 보는데 통장사본은 열리는 상태를 만들지 않습니다.
* **감사**: 서류 열람은 `log_sensitive_access` RPC로 `access_logs`에 적재한 뒤에만 서명 URL을 만듭니다. 로그 적재에 실패하면 파일을 열지 않습니다. 사유를 매번 묻지 않는 이유는 이 화면에서 서류를 여는 이유가 하나(지급·정산 준비)뿐이기 때문이며, 남겨야 하는 것은 사유가 아니라 "누가 언제 어느 거래처의 무엇을 열었는가"입니다.

## 12. 후속 과제

* **OFFICE `거래처 정보` 전사 조회 목록**: 코드·거래처명·구분·사업자등록번호·은행명·계좌번호·예금주까지를 조회 전용으로 노출합니다. 노출 범위를 넓히는 일이므로 **등록번호·계좌번호 마스킹 정책**을 먼저 정하고, 원장 SELECT 정책을 그에 맞춰 넓힙니다.
* **서류 열람 서버 강제**: 지금은 화면이 로그를 남긴 뒤 클라이언트가 서명합니다. 조회 범위를 OFFICE로 넓히는 시점에는 `material-download` 방식 Edge Function으로 옮겨 서명 자체를 서버가 쥐어야 합니다(마이그레이션 §5의 잔여 위험).
* **전자결재·정산 연계**: 결재 문서에서 거래처를 고르고 지급 내역이 이 원장에 쌓이도록 잇습니다.
* **NETWORKS 외주/거래 마스터 연결**: 같은 상대를 가리키는 두 행을 잇는 참조를 둘지 결정합니다.
