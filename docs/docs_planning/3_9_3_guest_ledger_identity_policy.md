# GUEST 독립 계정·원장 불러오기 정책

> 확정일: 2026-09-14
> 이 문서는 기존 `3_9_1`, `3_9_2` 문서 중 GUEST 계정과 원장 관계에 관한 내용을 대체합니다.

## 1. 핵심 원칙

* **독립 계정**: `users`의 GUEST 계정은 이름·소속·이메일만 가진 로그인 계정입니다. 전화번호와 원장 식별자는 계정 정보가 아닙니다.
* **원장 불러오기**: 현재 화면의 NETWORKS 원장 선택은 이름·소속·이메일을 입력 폼으로 복사하는 편의 기능일 뿐입니다. 원장 ID를 계정이나 별도 매핑표에 저장하지 않으며, 생성 후 자동 동기화하지 않습니다. 향후 다른 원장을 후보로 추가하더라도 같은 계약을 적용합니다.
* **사업 참여 분리**: 프로젝트·M&A·FUND 참여와 로그인 개방은 `program_participants`가 소유합니다. 원장의 사업 참가 명단인 `program_participant_entries`와 투자 원장은 그대로 보존합니다.
* **계정 상태 분리**: GUEST 계정 정지는 전체 로그인을 막고, 사업 접근 차단은 해당 사업만 닫습니다.

## 2. GUEST 데이터 계약

* **필수 프로필**: 이름·소속·이메일 세 값이 계정 생성과 ADMIN 수정의 전체 입력입니다.
* **로그인 ID**: 이메일은 미삭제 `users` 전체에서 정규화해 유일합니다. 같은 이메일과 같은 이름의 기존 GUEST 계정은 재사용할 수 있고, 이름이 다르면 자동 병합하지 않습니다.
* **전화번호 제거**: GUEST 생성·조회·수정·검색·인증·알림에서 전화번호를 받거나 사용하지 않습니다. 공유 `users.phone` 컬럼은 임직원 때문에 유지하되 GUEST 행에는 저장하지 않습니다.
* **원장 관계 제거**: GUEST의 `company_id`, `guest_identities`, 참여 줄의 계정-원장 식별값을 접근 권한이나 표시 분류에 사용하지 않습니다. 기존 관계값은 마이그레이션에서 정리합니다.
* **기존 기록 보존**: 계정, `guest_credentials`, 개인 비밀번호 해시, 사업/FUND 참여, 로그인 개방 상태, 제출·평가·파일 등 업무 기록은 유지합니다.

## 3. 관리 화면

* **통합 목록**: 내부 관리 화면은 `/guest-accounts` 하나를 사용합니다. 목록은 이름·소속·이메일·로그인 가능 수·최근 접속·계정 상태를 보여 줍니다.
* **분류 제거**: 원장 연결을 전제로 한 스타트업·전문가·BUYER·SELLER·미연결 탭과 인격 표시는 두지 않습니다. 사업 종류 필터가 필요하면 실제 `program_participants.entity_key`만 사용합니다.
* **원장 선택창**: 호출자가 읽을 수 있는 원장만 전용 축약 조회로 검색합니다. 응답은 화면 선택에만 쓰는 임시 행 키와 이름·소속·이메일만 포함하며, 전화번호 등 다른 원장 열은 브라우저로 보내지 않습니다. 고른 세 값은 빈 입력값만 채우고 원장에는 아무것도 쓰지 않으며, 임시 행 키는 생성 요청에 싣지 않습니다.
* **권한**: 일반 내부 사용자는 허용된 범위에서 계정을 조회·생성하고, ADMIN만 프로필 수정·비밀번호 초기화·계정 상태 변경·영구 삭제를 수행합니다.

## 4. 원장 자체 정책과의 경계

스타트업·NETWORKS·M&A 원장의 사업자등록번호·이메일·전화번호 중복 규칙과 연락처 이력은 해당 업무 원장에 계속 적용합니다. 이번 정책은 원장 데이터를 삭제하거나 원장의 연락처 품질 규칙을 바꾸지 않습니다. 제거하는 것은 원장 값을 GUEST 계정에 복제하거나 관계형으로 연결해 두는 경로입니다.

## 5. 마이그레이션과 배포

* **후속 이력**: 이미 적용된 마이그레이션은 수정하지 않고 최종 버전 뒤의 후속 마이그레이션으로 전환합니다.
* **데이터 정리**: GUEST 행의 전화번호·회사 FK, 초대 행의 연락처 복사본, 계정-원장 매핑을 정리하되 보존 대상 행의 건수와 참조 무결성을 적용 전후로 대조합니다.
* **재발 방지**: 단건·일괄 생성, ADMIN 수정, 사업 접근 개방, 로그인·갱신·재설정 경로에서 제거된 값이 다시 생기지 않도록 DB 제약과 회귀 테스트를 둡니다.
* **배포 순서**: 적용 직전 데이터 감사와 복구용 백업을 확인한 뒤, 새 Edge Function → DB 마이그레이션 → WORKS/GUEST 클라이언트 순으로 적용합니다. 구형 WORKS 호출은 DB의 명명 인자 호환 래퍼가 받으며, 래퍼 제거는 구형 클라이언트 종료를 확인한 별도 마이그레이션으로 수행합니다. 실제 운영 적용은 별도 승인 후 수행합니다.

## 6. 검증 기준

* **정리 정확성**: 기존 GUEST 전화번호와 원장 관계는 0건이고, 직원·업무 원장 연락처는 바뀌지 않습니다.
* **보존 정확성**: GUEST 계정·비밀번호·프로그램/FUND 참여·제출 기록의 식별자와 건수가 유지됩니다.
* **권한 경계**: 외부 GUEST가 내부 원장을 직접 읽지 못하고, 내부 사용자도 기존 워크스페이스·프로그램 권한을 우회하지 못합니다.
* **API 계약**: GUEST 프로필 입력·표시 값은 이름·소속·이메일이며 원장 ID와 전화번호를 노출하지 않습니다. 계정 목록의 상태·참여 요약은 별도 운영 정보로 유지합니다. 원장 선택 조회는 세 값과 선택 상태용 임시 행 키·전체 건수 외의 연락처·프로필 열을 전송하지 않습니다.
* **회귀 방지**: 전체 마이그레이션 재생, 기존 데이터 전환 pgTAP, RPC 허용·거절, Edge 인증 테스트, 앱 타입 검사와 화면 검수를 모두 통과해야 완료입니다.
