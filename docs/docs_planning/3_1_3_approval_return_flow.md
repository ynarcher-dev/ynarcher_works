# [3-1-3] 전자결재 반려·보완·재상신 기획서

본 문서는 OFFICE `전자결재`의 **반려**, **보완 요청**, **보완 후 재상신**과 결재선 반복 배치 규칙을 명세합니다. 양식·문서함·결재선 구분 등 전자결재 전반은 [3_1_workspace_hub.md §1.5](./3_1_workspace_hub.md)가 소유합니다.

> [!IMPORTANT]
> **2026-09-10 결정 — 반려와 보완을 분리합니다.** 2026-09-05에 도입한 `돌아갈 순번`·`기안자 경유`·`합의 초기화` 선택은 폐기합니다. **반려는 결재 종결**, **보완은 현재 결재 자리에서 일시 정지**입니다. 기안자가 보완을 마쳐 재상신하면 이미 받은 승인은 유지하고, 보완을 요청한 자리부터 남은 결재선을 이어갑니다.

## 1. 결정 모델

| 결재자 판단 | 결재선 결정 | 문서 상태 | 다음 행동 |
|---|---|---|---|
| 승인 | `APPROVED` | 남은 줄이 있으면 `IN_REVIEW`, 없으면 `APPROVED` | 다음 결재자가 처리 |
| 보완 요청 | `REVISION_REQUESTED` | `REVISION_REQUIRED` | 기안자가 내용을 수정한 뒤 재상신 |
| 반려 | `REJECTED` | `REJECTED` | 결재 종료. 수정·재상신 없음 |

반려와 보완은 사유가 필수입니다. 승인 의견은 선택입니다. 문서가 보완 중이거나 반려되면 같은 회차의 다른 구분을 포함한 모든 결재 처리가 멈춥니다.

## 2. 동일인 반복 결재선

결재선은 사람 목록이 아니라 **결재 자리 목록**입니다.

* 같은 사람을 같은 구분 또는 다른 구분에 **N회 배치할 수 있습니다**.
* 각 자리는 `(kind, step_order, round)`로 독립하며 같은 사람이어도 한 자리씩 차례대로 판단합니다.
* 지정 화면에서 같은 사람을 다시 선택하면 새 자리를 추가하고, 삭제는 선택한 자리 하나만 제거합니다.
* 참조자는 결재자가 아니므로 `approval_recipients`에 별도로 저장하며 같은 문서 안에서는 중복하지 않습니다.
* DB의 `approval_lines`에는 `(document_id, approver_id)` UNIQUE 제약을 두지 않습니다. 서버와 화면의 차례 판정은 사람의 유일성이 아니라 자리 순서를 기준으로 합니다.

## 3. 보완 요청과 재상신

예: 결재선이 `A → B → C`이고 B가 보완을 요청한 경우입니다.

1. A의 승인은 1회차 업무 기록으로 유지합니다.
2. B 행을 `REVISION_REQUESTED`로 기록하고 문서를 `REVISION_REQUIRED`로 멈춥니다.
3. 기안자는 제목·필드 값·첨부자료를 수정합니다. 양식·결재선·연결 문서는 바꾸지 못합니다.
4. 재상신하면 새 회차에 B와 C만 `PENDING`으로 복제합니다.
5. B부터 결재가 다시 시작되고, A에게는 본문 변경 뒤에도 승인이 유지됐음을 알립니다.

모든 구분은 자기 구분 안에서 순차이고 구분끼리는 병렬이라는 기존 규칙을 유지합니다. 재상신 시에는 현재 회차의 `REVISION_REQUESTED` 및 `PENDING` 행을 구분과 무관하게 다음 회차로 옮겨, 보완 중 멈췄던 모든 미처리 자리를 보존합니다.

## 4. 회차와 감사 이력

`approval_lines.round`가 회차를 소유하며 현재 회차는 `max(round)`로 파생합니다. 기존 승인·보완·반려 행은 갱신하거나 삭제하지 않습니다.

2026-09-05 흐름의 `return_to_step`·`return_via_drafter`·`return_reset_agreement` 컬럼은 과거 도장의 뜻을 읽기 위해 남겨 둡니다. 새 처리에서는 값을 쓰지 않으며, 화면은 과거 행만 당시 표현으로 표시합니다.

## 5. 화면 규칙

* 결재 처리 창은 `승인 / 보완 요청 / 반려` 세 판단만 제공합니다.
* 돌아갈 순번, 기안자 경유, 합의 초기화 입력은 제공하지 않습니다.
* **보완 요청 상태와 도장은 노란색**으로 표시합니다. 반려는 빨간색, 승인은 파란색 계열을 유지합니다.
* 기안자의 진행 현황에는 `보완` 항목을 별도로 두고, 해당 문서에서 `보완 후 재상신`을 실행합니다.
* 보완 화면 상단에는 요청자와 사유, 재개 지점을 고정 안내합니다.
* 지난 회차 도장은 그대로 열람할 수 있고 의견이 있는 도장은 사유를 확인할 수 있습니다.

## 6. 서버 계약과 권한

### 6.1 상태·결정 enum

* `approval_status.REVISION_REQUIRED`
* `approval_decision.REVISION_REQUESTED`

enum 값 추가와 그 값을 사용하는 함수 정의는 PostgreSQL 트랜잭션 제약 때문에 서로 다른 마이그레이션으로 나눕니다.

### 6.2 RPC

* `decide_approval_document(line_id, decision, comment)` — 현재 회차의 자기 차례에서 승인·보완 요청·반려를 처리합니다.
* `resubmit_approval_document(document_id, title, field_values)` — 기안자가 `REVISION_REQUIRED` 문서를 수정 후 재상신합니다.
* `app.clone_approval_revision_round(document_id)` — 보완 요청 및 미처리 행만 다음 회차로 복제하는 내부 헬퍼입니다.

예전 6인자 `decide_approval_document`와 `app.clone_approval_round`는 제거합니다. 두 public RPC는 `authenticated`만 실행할 수 있고, 내부 복제·알림 헬퍼는 사용자에게 열지 않습니다. RPC는 `SECURITY DEFINER`이므로 고정 `search_path`와 함께 현재 사용자, 담당 행, 문서 상태, 현재 회차, 자기 차례를 함수 안에서 다시 검증합니다.

## 7. 알림

| 유형 | 수신자 | 시점 |
|---|---|---|
| `approval_rejected` | 기안자 | 반려 즉시 |
| `approval_revision_requested` | 기안자 | 보완 요청 즉시 |
| `approval_pending` | 새 회차의 구분별 첫 결재자 | 재상신 즉시 |
| `approval_revision_resubmitted` | 승인이 유지된 앞 순번 | 재상신 즉시 |

같은 사람이 여러 알림 대상 자리에 있으면 알림 원장에서는 한 건으로 접습니다. 결재 자리 자체는 접지 않습니다.

## 8. 완료 기준

* 같은 사용자를 한 결재선에 두 번 이상 넣고 각 자리 하나씩 삭제·처리할 수 있습니다.
* 앞 순번이 남은 동일인의 뒤 순번을 먼저 처리할 수 없습니다.
* 보완 요청 중에는 다른 결재자가 처리할 수 없습니다.
* 보완 재상신 후 이전 승인은 유지되고 요청 자리와 남은 자리만 새 회차에서 진행됩니다.
* 반려된 문서는 수정하거나 재상신할 수 없습니다.
* 보완은 목록·상세·도장 표에서 노란색으로 구별됩니다.
* 과거 되돌림 이력은 삭제되지 않고 당시 의미로 열람됩니다.
