# [3-3-7] 'AI 작성하기' 재설계 — 눈으로 읽고, 자료는 상·하 두 칸으로 가른다

> [!IMPORTANT]
> **2026-09-09 확정 · 구현 완료.** 'AI 작성하기'를 다시 만들었습니다. 바꾼 것은 둘입니다 — **(1) PDF·이미지는 글자로 뽑지 않고 원본 그대로 모델이 눈으로 읽습니다**(스캔본도 같은 길입니다), **(2) 카드×자료 격자를 걷고 자료 칸을 읽을 자료(상)·읽지 않을 자료(하) 둘로 가릅니다.** 상에 서는 자료 한 벌을 모든 카드가 함께 읽고, 어느 칸에 설지는 파일명이 먼저 답하며 담당자가 줄을 눌러 옮깁니다. 서버는 자료 종류를 꼬리표로 붙여 확정 숫자를 어느 자료에서 읽을지 모델이 가리게 하고, 탐색 축 묶음이 둘 이상이면 자료를 컨텍스트 캐시에 한 번 올립니다. 원장 스키마 변경은 없습니다.
>
> 이 문서는 [3_3_5](./3_3_5_startup_ai_fill.md)의 **§4.2(격자)·§8.3(자료 조합 묶음)·§16.3(분석 버튼)을 대체**합니다. 엔진의 나머지 규약(근거 대조·작문 패스·프로파일 경계·감사 기록)은 3_3_5가 그대로 정본입니다. 같은 날 세웠던 비용·정확도 계획(3_3_6 — pdf.js 브라우저 추출·OCR 격하·표 점수)은 **채택하지 않고 스태시에 보관**했습니다(§9).

> 본 문서는 [3_3_5](./3_3_5_startup_ai_fill.md)(STARTUP)와 [3_6_1](./3_6_1_ma_seller_quick_review.md)(M&A 셀러 퀵 리뷰) 두 대상에 함께 적용됩니다. 화면 부품(`features/ai`)과 엔진(`_shared/aiFill`)이 한 벌이라 두 대상이 같은 날 같은 모양으로 바뀝니다.

## 0. 한 장 요약

| 물음 | 답 |

## 1. 목적

담당자가 첨부 자료로 카드 초안을 만들 때 **정확도를 첫 버전 수준으로 되돌리고, 토큰은 그때보다 줄이며, 고르는 일을 두 번(무엇을 읽나·무엇을 쓰나)으로 끝내는 것**입니다.

## 2. 결정 근거 — 눈으로 보기 대 VLM 마크다운

AI가 문서를 읽는 방법은 둘뿐입니다.

| | 눈으로 보기 | VLM 마크다운(한 번 옮겨 적어 저장) |
| :--- | :--- | :--- |
| 표·차트·배치 | 원본 그대로 봄 | 표는 살지만 차트·그림은 글이 되며 사라짐 |
| 숫자 틀릴 기회 | 1번(값을 뽑을 때) | 2번(옮겨 적을 때 + 값을 뽑을 때) |
| 쪽당 비용 | 258토큰 | 옮겨 적을 때 출력 800~1,300토큰, 이후 작성마다 그만큼 입력 |
| 스캔본·이미지 | 그냥 됨 | 별도 OCR 경로 |
| 근거 대조 | 원문 글자가 없어 '미검증' | 인용문을 원문과 대조 가능 |
| 긴 문서 | 한 번에 | 출력 상한 때문에 나눠 옮겨야 함 |

**제미나이를 그대로 쓰기로 한 뒤에는 답이 눈으로 보기입니다**(2026-09-09 사용자 결정). 마크다운이 싸 보였던 것은 같은 자료를 4번 읽는 구조를 전제로 했을 때이고, 자료가 한 벌이 되어 캐시로 묶이면 쪽당 258토큰이 쪽당 1,000토큰보다 싸다는 당연한 결과가 남습니다. 인식률도 첫 버전(눈으로 보기)이 앞섰습니다. 마크다운이 이기는 단 하나는 근거 대조이며, 눈으로 보기에서도 자료 단위 근거(`s2`)는 남고 원문 일치 확인만 못 합니다 — 필요해지는 날 상 자료에 한해 얹습니다(§10).

> [!IMPORTANT]
> **"VLM 파싱"은 새로 들여온 기술이 아닙니다.** Gemini가 PDF를 직접 읽는 것이 곧 페이지를 통째로 보고 이해하는 VLM 파싱이고, 이 기능은 처음부터 그렇게 읽고 있었습니다. 첫 버전이 비쌌던 원인은 읽기가 아니라 **같은 자료를 묶음마다·조합마다 다시 읽힌 구조**였고, 오늘자 보완은 그 구조를 두고 읽는 방식만 글자 추출로 바꿔 표를 잃었습니다. 이번 개정이 고치는 것은 읽는 방식이 아니라 **몇 번 읽히는가**입니다.

## 3. 범위

* **대상**: STARTUP 상세 편집 폼의 'AI 작성하기'(카드 12종)와 M&A 셀러 퀵 리뷰(절 7종). 등록·수정 두 모드, 참조 자료(연결된 원장의 첨부) 포함.
* **바뀌는 것**: 모달(자료 두 칸 + 카드 체크), 요청 모양(`assignments` 제거), 서버 묶음 계획(자료 한 벌), 프롬프트(종류 꼬리표 규칙), 컨텍스트 캐시.
* **바뀌지 않는 것**: 카드·절 정의와 저장 컬럼, 프롬프트 본문과 표기 규격, 근거 대조(서버 발급 id), 2단계 작문 패스, 교차 판정, 병합 규칙("AI는 값을 지우지 못한다"), 감사 기록(`access_logs` 적재 실패 시 모델을 부르지 않음), Files API 업로드와 `finally` 삭제, 링크 읽기와 SSRF 방어, 오피스·HWPX 파서와 캐시 원장 `attachment_extracts`.
* **제외**: 자료 배치의 영구 저장(§10), 마크다운 근거 대조(§10), 외부 파서 업체 도입(하지 않음 — 제미나이 유지).

## 4. 화면

모달 하나이고 위에서 아래로 **작성할 카드 → 읽을 자료 → 읽지 않을 자료 → 요약·경고 → 결과**가 섭니다. 폭은 `size="2xl"`입니다(격자 시절 3xl에서 좁힘 — 열두 열을 한 줄에 세울 일이 없어졌습니다).

### 4.1 작성할 카드

* 카드 체크박스가 **탐색 축 묶음**(개요·팀/지식재산·성장·재무/인력/자본) 아래에 모여 섭니다. 묶음 이름을 누르면 그 묶음이 통째로 켜지고 꺼집니다. 묶음을 화면에 세우는 이유는 열두 칸이 한 줄에 서면 눈이 덩이를 못 잡기 때문이지, 담당자가 묶음을 알아야 해서가 아닙니다.
* **아무것도 켜지지 않은 채 엽니다**(2026-09-06 사용자 지정 유지). `전체 선택`이 한 번으로 해냅니다.
* 값이 있는 카드는 이름 옆에 `있음` 배지가 섭니다(절반만 찬 카드도 '있음' — 그 절반은 손으로 적은 것이라 켜면 함께 바뀝니다). 켜진 카드 중 값이 있는 것은 아래 한 줄이 "현재 값이 AI 결과로 바뀝니다"로 다시 말합니다.

### 4.2 읽을 자료(상) · 읽지 않을 자료(하)

* 게스트 계정 창의 두 목록과 같은 부품(`PickList`·`PickRow`)이고 방향만 **상하**입니다. 좌우가 아니라 상하인 이유는 담기는 것이 이름이 긴 파일이기 때문입니다 — 좌우로 가르면 절반 폭에 파일명이 잘립니다.
* **줄을 누르면 반대 칸으로 갑니다.** 갈 자리가 하나뿐이라 고르기와 보내기가 같은 뜻입니다. 가운데 `전부 내리기`·`전부 올리기` 두 버튼은 한 줄씩으로 못 하는 일만 맡습니다.
* **기본 자리는 파일명이 정합니다**(§5). 담당자가 옮긴 줄만 기억하고(`AiReadSet`, 기본값과 다른 줄만), 기본 자리로 되돌린 줄은 기억에서 지웁니다 — 같은 사실을 두 곳에 적지 않습니다. 기억은 진입 버튼이 세션 동안 들고 있어 창을 닫았다 열어도 남고, 사라진 자료의 기억은 창이 걷습니다.
* 줄에는 이름 · (참조 자료면) 위치 · **종류**(기타가 아닐 때만, 회색 글자) · 형식 · 용량 · (할 일이 있을 때만) 상태 배지가 섭니다. 종류는 값이라 글자로, 상태는 상태라 배지로 섭니다(5_component_spec §3.4). 상태 배지는 `여는 중`·`열지 못함` 둘뿐입니다 — 대개의 줄은 그냥 읽히므로 '준비됨'을 줄마다 적으면 그것이 잡음입니다.
* **분석 버튼은 없습니다.** 상 칸의 오피스·한글·링크 자료는 창이 열릴 때(그리고 상으로 올라올 때) 서버가 알아서 엽니다. 담당자의 결정이 아니라 준비이기 때문입니다 — 열어 두면 작성이 빨라질 뿐 결과가 달라지지 않습니다. 여는 동안 실행 버튼은 `자료를 여는 중…`으로 잠기고, 한 줄이 왜 안 눌리는지를 답합니다. 열지 못한 줄은 배지가 사유를 들고 다시 돌지 않습니다.
* 읽을 수 없는 형식은 종전처럼 아래 별도 목록에 섭니다(옮기는 자리에 눌리지 않는 줄을 세우지 않습니다).

### 4.3 실행·결과

* 실행 버튼은 `선택한 N개 카드 작성`이고 카드 0개·읽을 자료 0건·합계 초과·한 건 초과·여는 중이면 잠깁니다. 실행 중에는 고른 것이 흐려질 뿐 자리에 남고, 결과는 아래 패널이 받습니다(2026-09-06 규칙 그대로).
* 외부 전송 고지는 제목 옆 말풍선이 갖습니다. 반출을 실제로 막는 것은 파일마다의 `access_logs` 적재와 그 실패 시 모델을 부르지 않는 규칙입니다(3_3_5 §8.2).

## 5. 자료 종류 — 파일명이 답하고 서버가 꼬리표로 붙인다

* 판정은 `_shared/docParse/sourceKind.ts` 한 벌이고 앱은 `@docparse` 별칭으로 같은 파일을 씁니다. 화면이 상에 세운 꼬리표와 모델이 읽는 꼬리표가 어긋나면 담당자가 본 것과 모델이 읽은 것이 다른 자료가 됩니다.
* 종류 9종 + 기타: 감사보고서 · 손익계산서 · 재무제표 · 주주명부 · 등기·등록 서류 · 인증서 · IR 자료 · 사업계획서 · 회사소개서. **먼저 걸리는 것이 이깁니다** — 확정 숫자를 담는 서류를 앞에 두어 "재무제표(손익계산서 포함)" 같은 이름에서 더 좁은 종류가 답이 됩니다. 영문 약어(`ir`·`bp`)는 낱말 경계로만 잡습니다(`first`의 `ir`이 IR이 되면 아무 파일이나 상에 섭니다). 링크는 주소의 마지막 마디를 봅니다.
* **모르면 읽지 않는 쪽입니다.** 잘못 읽은 자료는 그럴듯한 틀린 값을 폼에 앉히지만 잘못 뺀 자료는 담당자가 한 번 눌러 올리면 됩니다.
* 서버는 자료 머리글에 종류를 적고(`[자료 s2 · 재무제표: 2025_FS.pdf]`, 기타는 적지 않음) 공통 규칙 한 덩이(`SOURCE_KIND_RULES`)를 프로파일 프롬프트 뒤에 덧붙입니다 — 확정 수치의 우선순위, 서술 항목이 IR의 목표치를 실적으로 옮기지 않을 것, 파일명과 내용이 어긋나면 내용을 따르고 notes에 남길 것. 규칙이 엔진에 있는 이유는 꼬리표를 붙이는 쪽이 엔진이기 때문입니다 — 규약이 두 곳에 살면 라벨 하나를 고친 날 한쪽만 옛 이름으로 말합니다.

## 6. 서버

* **요청 모양**: `targetId`(또는 등록 모드의 파일·링크·참조 id) + `attachmentIds` + `cards`. `assignments`는 받지 않습니다(옛 화면이 보내도 무시). 요청에 실려 온 자료가 곧 밖으로 나가는 자료이므로 감사 로그도 그 목록 그대로입니다.
* **묶음**(`groups.ts`): 카드가 4개 이하면 한 요청, 5개 이상이면 탐색 축으로 가르되 **모든 묶음이 같은 자료 목록**을 듭니다. 탐색 축을 없애지 않는 이유는 그대로입니다(합치면 출력이 잘리고 카드별 탐색이 얕아짐, 3_3_5 §17.5).
* **컨텍스트 캐시**(`contextCache.ts`): 묶음이 둘 이상이고 전부 같은 조각을 실으면 자료 조각을 캐시에 한 번 올리고 묶음은 프롬프트만 싣습니다. 예산을 넘겨 묶음마다 다른 조각을 고른 날은 묶지 않습니다(그 묶음이 보지 못한 조각을 캐시가 실으면 근거 지도가 거짓이 됩니다). **캐시 실패는 실패가 아닙니다** — 사유는 실행 요약 로그의 `cache`에만 남고 초안은 종전 경로로 같게 나옵니다. 캐시 모델은 `GEMINI_CACHE_MODEL`로 못 박을 수 있고(공급자가 별칭 모델을 거절할 수 있음) 값이 없으면 작성 모델 그대로입니다. 캐시는 Files API 자료와 함께 `finally`에서 지웁니다. 보완 요청도 같은 조각이면 캐시를 탑니다.
* **자료 전송**: PDF·이미지·글자 파일은 원본(인라인 또는 Files API), 오피스·HWPX·링크는 서버가 뽑은 조각. 종전과 같고, 캐시 원장 `attachment_extracts`의 `original` 상태(PDF·이미지)도 그대로입니다.
* **예산 초과 시 조각 선별**은 남겨 둡니다 — 상 칸으로 자료가 줄어 넘길 일이 드물지만, 넘긴 날 자료를 통째로 버리는 것보다 낫고 이미 검증된 코드입니다.

## 7. 비용

M&A 셀러 사례(PDF 14건 ≈ 70쪽, 카드 7개 전체)를 기준으로 한 추정입니다. 절대 금액은 어느 경로든 실행당 수 센트입니다.

| 경로 | 작성 1회당 입력 |
| :--- | :--- |
| 첫 버전(격자, 조합별 묶음) | 조합 수 × 묶음 수 × 18K — 조합이 갈리면 캐시도 못 씀 |
| 오늘자 보완(글자 추출) | 4 × 40~56K = 160~224K, 표는 깨짐 |
| **이번 개정** | 상 자료만(예: 4건 ≈ 20쪽 ≈ 5K) × 4묶음, 캐시가 서면 자료 값은 한 번 남짓 |

캐시가 실제로 서는지는 배포 뒤 실행 요약 로그의 `cache` 값이 답합니다(§10).

## 8. 보안 게이트 체크포인트

* 원장 스키마·RLS·RPC 변경 없음. 마이그레이션 없음.
* 쓰기 자격 판정은 종전 그대로 프로파일이 정책의 함수를 되묻습니다(`can_write_startup`·`can_write_ma_seller`·`can_create_*`).
* 첨부 메타·캐시 조회는 호출자 토큰(RLS), 스토리지 바이트와 감사 로그만 `service_role`.
* 감사 로그는 요청에 실려 온 자료(= 상 칸) 전부에 대해 적재하고, 실패하면 모델을 부르지 않습니다. 하 칸의 자료는 요청에 실리지 않으므로 내려받지도 않습니다.
* 컨텍스트 캐시에는 기밀 자료가 담기므로 TTL 600초 + `finally` 삭제. 캐시 이름은 로그에 남지 않습니다.
* 클라이언트가 보낸 값(카드 키·첨부 id·파일 키)은 종전처럼 서버가 다시 검증합니다. `assignments`를 받지 않게 되어 검증할 표면이 하나 줄었습니다.

## 10. 열린 이슈

* **자료 배치의 영구 저장** — 지금은 세션 동안만 기억합니다. 첨부 행에 적으려면 참조 자료(남의 원장 행)에 이 화면이 값을 쓰는 일이 되어 미뤘습니다. 파일명 규칙이 대체로 맞으면 필요가 작습니다 — 실사용에서 같은 줄을 매번 옮기는 일이 잦으면 그때 봅니다.
* **캐시 성립 확인(G1)** — `cachedContents`가 이 키·모델(`gemini-flash-latest` 별칭)에서 서는지. 서지 않으면 `GEMINI_CACHE_MODEL`에 버전이 박힌 모델을 넣습니다. 어느 쪽이든 초안은 같습니다.
* **종류 낱말 표 보강** — 실사용 파일명에서 하에 잘못 서는 것이 잦은 낱말을 `sourceKind.ts`에 더합니다(한 곳).
* **마크다운 근거 대조** — 원문 일치 확인이 꼭 필요해지면 상 자료에 한해 옮겨 적기를 얹습니다. 지금은 자료 단위 근거('미검증')로 충분합니다.
