# [3-2] ADMIN (시스템 관리자) 워크스페이스 상세 기능 요건서

본 문서는 시스템 관리자가 사내 9개 내부 워크스페이스별 접근 권한(읽기/쓰기)을 유연하게 제어하고, 시스템 전반의 보안 트랙을 실시간 관제할 수 있도록 화면 요건과 비즈니스 흐름을 정의합니다.

---

## 1. 주요 화면 및 기능 명세

### 1.1 동적 메뉴 및 데이터 접근 권한 제어 콘솔
* **메뉴 권한 통제 매트릭스**
  * **기능**: 코딩 마이그레이션 없이, UI 상에서 각 등급별로 각 메뉴의 기본 CRUD 권한을 실시간 제어합니다.
  * **콘솔 구성**:
    * **역할 선택**: 관리자, 경영진, 매니지먼트(경영지원), 투자실, 사업부, M&A팀, 프로젝트팀, 스타트업, 전문가, 게스트 중 대상 역할을 선택합니다.
    * **메뉴별 토글 스위치**: 각 내부 워크스페이스(OFFICE, STARTUP, NETWORKS, AC, M&A/PE, PROJECT, FUND, MANAGEMENT, ADMIN)와 외부 서브도메인 앱 권한 도메인(GUEST) 옆에 **[읽기 권한 (Read)]** 및 **[쓰기 권한 (Write)]** 토글 스위치가 나열됩니다.
    * **동작**: 토글 스위치를 활성화/비활성화하고 [권한 적용] 버튼을 클릭하면, 해당 등급의 세션 권한 범위 및 프론트엔드 GNB 메뉴 노출 상태가 실시간 동적 갱신됩니다.

> [!IMPORTANT]
> 프론트 라우팅 기준의 권한 키는 `office`, `startup`, `networks`, `ac`, `fund`, `mna`, `project`, `management`, `admin`, `guest`입니다. 현재 일부 초기 DB enum·permission seed 및 권한 콘솔 설정에는 과거 `hub` 기준이 남아 있으므로, ADMIN 권한 콘솔은 위 10개 권한 키를 정본으로 노출하도록 정합화되어야 합니다.

### 1.2 시스템 보안 감사 로그 모니터 (Audit Log Monitor)
* **전사 중요 조작 및 접근 감사 로그 테이블**
  * **기능**: 전사 워크스페이스에서 발생한 비즈니스 중요 트랜잭션의 감사 추적 데이터를 제공합니다.
  * **수집 및 노출 항목**: 조작 사용자명, 대상 워크스페이스, 수행 액션(조회/수정/삭제/다운로드), 일시, 접속 IP 정보, 상세 변경 전/후 상태(JSON 데이터 대조 뷰어 팝업 제공).
* **첨부파일 다운로드 사유 로그 뷰 (Download Log View)**
  * **기능**: 사용자가 상세 뷰 첨부파일 목록에서 파일을 다운로드할 때 입력한 목적/사유 로그를 중점 관제합니다.
  * **주요 항목**: 다운로드 기안자, 소속, 대상 파일명, 입력된 상세 사유 텍스트, 다운로드 시각.

### 1.3 게시판·회의실 운영 원장

* **게시판 관리**: OFFICE에 노출할 게시판/자료실 레지스트리를 생성·수정하고 활성 상태와 종류(`POST`/`ARCHIVE`)를 관리합니다. 공지사항 고정 뷰는 이 레지스트리와 별개입니다.
* **회의실 관리**: 회의 장소와 회의실의 이름·위치·수용 인원·사진·활성 상태를 관리합니다. 실제 예약과 시간 충돌 검증은 OFFICE가 담당합니다.
* **모듈 관리**(2026-09-02 신설): 사업 운영 모듈의 **템플릿 카탈로그**를 배치합니다 — 분류·노출 순서, 사용 여부, 워크스페이스별(AC·M&A·PROJECT) 노출, 그리고 공유 상한 2종(GUEST 공개 허용 / 링크 공유 허용). 정본은 [3_2_1](./3_2_1_admin_module_registry.md)입니다. 게시판·회의실과 같은 성격이되 한 가지가 다릅니다 — **끄는 것이 기존 인스턴스에 미치는 영향이 축마다 갈립니다.** 카탈로그(사용 여부·워크스페이스 노출)를 끄면 새로 배치할 수만 없고 진행 중인 인스턴스는 그대로 동작하며, 노출 상한을 내리면 이미 열려 있던 것까지 즉시 닫힙니다(저장값·주소는 보존되어 되돌리면 복구). 모듈 인스턴스 자체의 이름·기간·담당자는 사업 담당자가 정하며 ADMIN이 관여하지 않습니다.

### 1.4 태그·민감정보 관리

* **태그 관리**: 태그 종류가 늘어도 사이드바가 길어지지 않도록 `태그 관리` 한 줄의 우측 플라이아웃에서 실제 태그 원장을 선택합니다. 메뉴는 태그 카탈로그에서 동적으로 파생합니다. 인사 기준정보(직책·직급·호봉)도 2026-08-03부터 이 그룹에 속합니다 — 태그 원장은 종류를 가리지 않고 쓰기 정책이 `app.is_admin()` 하나이므로, 소유 워크스페이스를 갈라 두면 기준정보를 고치러 갈 곳만 둘로 나뉩니다.
* **민감정보 관리**: 화면 콘텐츠 단위로 이름·이메일·연락처 등 마스킹 정책을 설정합니다. 외부 대상의 개인정보만 가리고 내부 임직원인 생성자·담당자는 마스킹하지 않습니다.

### 1.5 중복 병합 검증

* NETWORKS 계열 원장의 중복 후보를 비교하고 정본/중복 대상을 정해 병합합니다.
* 병합은 단순 화면 숨김이 아니라 원장 이관·비활성화·기여 이력을 함께 처리하며, 실제 허용 여부는 서버 RPC와 RLS가 판정합니다.

### 1.6 생성자 교체

생성자 교체는 `created_by`를 잘못 지정했거나 퇴사·조직 이관으로 정리가 필요한 경우 사용하는 관리자 오버라이드입니다.

1. 데이터베이스/워크스페이스 원장을 선택합니다.
2. 이름 또는 사업명으로 대상 레코드를 검색해 한 건을 선택합니다.
3. 새 생성자 임직원 한 명과 변경 사유를 입력합니다.
4. `set_entity_creator` RPC로 변경하고 `CREATOR_CHANGE` 감사 로그와 원장 변동 이력을 남깁니다.

대상은 STARTUP, 국내/글로벌 NETWORKS 원장, AC/M&A/PROJECT 사업, FUND 펀드입니다. 생성자 변경은 **담당자·배정 인력·워크스페이스 권한을 바꾸지 않으며**, `내 … 관리`의 생성자 기준 포함 범위와 상세의 기록 표기만 바꿉니다.

### 1.7 게스트 계정 관리 (2026-09-03 신설)

게스트 계정은 별도 원장이 아니라 임직원과 같은 `public.users`에 들어옵니다. 사업 담당자가 참가자 명부에서 로그인을 열 때 Edge Function이 삽입하며, 유형은 `external_startup` / `external_expert` / `temporary_guest` 셋입니다. 그래서 계정 원장을 유형으로 가르지 않으면 **MANAGEMENT 인사 관리 목록에 게스트가 섞여 나옵니다**. 실제로 그 목록을 읽는 결재선·딜메이커 후보·생성자 교체 후보·멘션 후보에도 함께 섞여 있었습니다(2026-09-03 사용자 발견).

* **가르는 축은 셋입니다 — 계정 · 문 · 열쇠**(2026-09-05 개정, 정본은 [3_9_1](./3_9_1_guest_unified_account.md) §3).
  * 사업 담당자(PM·MEMBER)는 **자기 사업의 문**을 여닫습니다(참가자 명부의 매핑·접근 기간·차단).
  * ADMIN은 **계정을 재웁니다**(정지·해제). 한 게스트가 세 사업에 걸려 있으면 어느 사업 담당자도 그 사람을 전부 멈출 수 없었고, 그 일을 할 자리가 지금까지 없었습니다.
  * **열쇠(비밀번호)는 아무도 대신 쥐지 않습니다.** 종전의 담당자 '초기화'는 **재설정 안내 발송**으로 바뀌었습니다 — 계정을 통합하면서 담당자가 값을 쥘 수 있으면 그 게스트가 참여 중인 **다른 팀 사업까지 전부 열리기** 때문입니다.
* **계정 발급은 ADMIN 전용이 아닙니다**(2026-09-05 개정). 종전에는 *"ADMIN은 있는 것을 배치할 뿐 없는 것을 만들지 않는다"* 는 이유로 발급을 두지 않았습니다. 그러나 **발급만으로는 아무것도 보이지 않고**(사업에 매핑되기 전까지 로그인해도 빈 목록), 대상도 임의가 아니라 **원장에 이미 있는 행**으로 제한되므로 발급은 권한이 걸릴 자리가 아닙니다. 권한이 걸릴 자리는 그 다음 — **매핑**입니다. 그래서 발급·전체 조회·재설정 안내는 내부 사용자 전원에게 열리며, 전원용 창구는 [OFFICE > 게스트 계정](./3_1_workspace_hub.md)에 둡니다. ADMIN 화면은 그 기능을 포함하고 **정지·해제와 연락처 원본**을 더 가집니다.
* **목록**: 이름, 유형, 소속 기업, 이메일(로그인 ID), 참여 사업(열린 건수/전체 건수 — 눌러 사업별 개방 상태와 접근 기간을 펼침), 최근 접속, 계정 상태. 사업 원장이 셋이라 각 사업은 어느 워크스페이스(AC·M&A·PROJECT) 것인지 함께 밝힙니다. **ADMIN 화면만 연락처를 원본으로 표시하고**, OFFICE 창구는 민감정보 정책에 따라 마스킹합니다.
* **계정 발급**: 원장(기업·전문가)에서 대상을 검색해 계정을 세웁니다. 사업에 붙지 않은 상태로 생성되며, 같은 원장 행에 이미 계정이 있으면 그 계정을 돌려줍니다(멱등). 계정의 키는 이메일이 아니라 **원장 행**이라, 같은 사람이 기업 인격과 전문가 인격을 함께 가지면 계정 2개가 정상입니다([3_9_1](./3_9_1_guest_unified_account.md) §4).
* **정지·해제**: 정지는 그 계정이 걸린 **모든 사업에서 동시에** 멈추고 접속 중인 세션까지 끊습니다. 정지 사유는 필수이며 감사 로그(`GUEST_ACCOUNT_SUSPEND` / `GUEST_ACCOUNT_RESTORE`)에 남습니다. **사업별 개방 상태(`login_status`)는 건드리지 않습니다** — 그것은 사업 운영 기록이지 계정 상태가 아니므로, 정지를 풀면 원래 열려 있던 사업이 그대로 열립니다.
* **삭제는 두지 않습니다.** 물리 삭제 금지 원칙 그대로이며, 게스트 계정은 명부 행·초대 레코드가 가리키는 대상이라 지우면 그 기록들이 누구 것인지 답할 근거가 사라집니다. 되돌릴 수 있는 정지 하나로 충분합니다.

> [!IMPORTANT]
> **정지가 실제로 막는 지점은 셋입니다.** `app.current_app_user_id()`가 `is_active`를 확인하므로 정지된 계정의 모든 요청은 Default Deny로 떨어지고, 정지 시 `session_version`을 올려 이미 발급된 토큰까지 무효화하며(올리지 않으면 정지를 푼 뒤 옛 토큰이 되살아납니다), 로그인 자체는 `service_role`로 도는 Edge Function이 계정 상태를 확인해 막습니다(RLS가 가로막지 않는 경로라, 여기서 막지 않으면 "로그인은 되는데 아무것도 안 보이는" 화면이 됩니다).

> [!NOTE]
> **내부 임직원 목록을 만드는 조회는 반드시 게스트 유형을 제외합니다.** 유형 목록의 단일 원천은 프론트 `apps/works/src/lib/userTypes.ts`, DB `app.is_guest_user_type()`입니다. 다만 `users`의 SELECT 정책은 좁히지 않습니다 — 내부 사용자가 게스트 행을 읽을 수 있어야 참가자 명부가 그 게스트의 이름을 붙일 수 있기 때문이며, 여기서 거르는 것은 접근 차단이 아니라 **목록의 사실 관계**입니다. 쓰기는 좁힙니다: `users_insert` / `users_update`의 MANAGEMENT 분기에서 게스트 행이 빠집니다(보이지 않는 행을 고칠 수 있는 권한은 사고 경로일 뿐입니다).

## 2. 관제 안전 장치 요건

* **재귀 잠금 방지 (Self-Lockout Prevention)**: 시스템 관리자가 본인의 `ADMIN` 워크스페이스 접근 권한이나 쓰기 권한을 비활성화하는 조작을 실행하려고 할 경우, "시스템 관리자 권한은 해제할 수 없습니다"라는 시스템 경고와 함께 적용이 원천 차단되도록 안전장치를 기획합니다.
