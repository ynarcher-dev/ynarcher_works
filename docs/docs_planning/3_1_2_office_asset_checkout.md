# [3-1-2] OFFICE 반출대장 기획서

본 문서는 OFFICE 워크스페이스 `반출대장`(`/office?tab=outbound`) 화면의 데이터 모델과 기능 요건을 명세합니다. 반출대장은 **회사 물건이 사외로 나갔다가 돌아오는 사실을 기록하는 원장**이며, 후보가 되는 자산과 그 반출 가능 여부는 MANAGEMENT `자산 관리`([3_7_2_management_assets.md](./3_7_2_management_assets.md))가 소유합니다. 상위 워크스페이스 기획은 [3_1_workspace_hub.md](./3_1_workspace_hub.md)입니다.

---

## 1. 목적

* **물건의 현재 소재를 사실대로 답합니다**: "그 빔프로젝터 지금 누가 갖고 있나"에 답할 수 있는 곳이 없어, 실물을 찾는 일이 매번 사람을 수소문하는 일이 되었습니다. 반출 건을 원장에 남겨 **물품 기준·사람 기준 양방향 조회**가 가능하게 합니다.
* **돌아오지 않은 물건을 드러냅니다**: 회의실은 시간이 지나면 저절로 비지만 물건은 누군가 돌려놓아야 비워집니다. **반납 예정일과 실제 반납일을 별개 값으로 두어** 연체를 화면이 스스로 알아보게 합니다.
* **미리 잡아 둘 수 있게 합니다**: 다음 주 외부 행사에 쓸 장비를 그날 가서 없는 것을 확인하는 일이 없도록, **기간 점유(예약)** 를 지원하고 겹침을 DB가 원자적으로 차단합니다.
* **통제 강도를 물건마다 다르게 둡니다**: 노트북 거치대와 법인 차량을 같은 절차로 다룰 수는 없습니다. **자산별 승인 필요 여부**를 켜서, 그 물건만 승인을 거치게 합니다.

---

## 2. 이 문서가 다루는 범위

* **포함**:
  * 반출 원장(`public.asset_checkouts`) 정의와 상태 6종의 전이 규칙
  * 기간 점유·겹침 차단 규칙과 연체 판정
  * 자산별 승인 필요 여부(`assets.requires_approval`)와 승인·반려 흐름
  * 내부 임직원 전원에게 반출 후보 자산을 노출하는 경로(`public.portable_assets` 뷰)
  * 반출대장 목록·등록·반납 화면 사양
  * 권한·RLS 및 마이그레이션 설계
* **제외(별도 범위)**:
  * **소모품 재고** — 보유 수량은 다루지만(§5.5), 쓰면 줄어드는 소모품(용지·배터리)의 입출고는 다루지 않습니다. 반출은 나갔다가 **돌아오는** 것이며, 돌아오지 않는 물품의 재고는 다른 원장의 일입니다.
  * **반출증 출력·서명** — 종이 반출증 양식 출력과 서명 수집은 다루지 않습니다. 결재가 필요한 반출은 전자결재를 쓰고, 본 대장은 사실 기록을 담당합니다.
  * **알림·리마인더** — 반납 예정일 임박·연체 알림은 후속 과제입니다. 본 범위는 화면에서 연체를 드러내는 데까지입니다.
  * **바코드·QR 스캔** — 현장 스캔 입력은 후속 과제입니다.
  * **분실·파손 처리의 후속 절차** — 반납 시 상태를 메모로 남기는 데까지이며, 변상·폐기 전환은 자산 관리 쪽 조치입니다.

---

## 3. 핵심 사용자

* **반출자(내부 임직원 전원)**: 반출 가능 물품을 찾아 기간·목적을 적어 등록하고, 돌아와서 반납 처리합니다. 본인 반출 건만 만들 수 있습니다.
* **동료(내부 임직원 전원)**: 물건이 지금 어디 있는지, 언제 돌아오는지를 조회합니다. 남의 반출 건을 고치지는 않습니다.
* **자산 담당자(`management` write)**: 승인이 필요한 물건의 반출을 승인·반려하고, 연체 건을 확인하며, 반출자가 처리하지 못한 반납을 대리로 처리합니다.
* **관리자(`super_admin`)**: 위 모든 권한을 가지며, 잘못 등록된 반출 건을 비활성화합니다.

## 4. 정보 구조 (Information Architecture)

```
[반출대장 탭]
 ├── 지사 탭 (지사 관리의 활성 지사)
 ├── 검색(물품명·품목·시리얼·반출자) + 상태 필터
 └── 반출 가능 물품 표
      ├── 도메인 열: 물품(사진+이름) · 품목 · 시리얼 · 상태 · 반출자 · 반납 예정
      ├── 처리 열: 대표 처리 하나만 — [반출하기] 또는 [반납하기]
      └── 행 클릭 → 물품 모달
           ├── 사진 · 품목 · 시리얼 · 지사 · 승인 필요 여부 · 설명(비고)
           ├── 지금 걸려 있는 반출 목록 (각 건에 [승인/반려] [반출 시작] [반납하기] [취소])
           ├── 지난 기록 (최근 5건)
           └── [+ 반출하기] → 같은 모달 안에서 등록 폼으로 전환
```

> [!NOTE]
> **화면의 주인공은 반출 기록이 아니라 물품입니다.** 대장을 여는 사람이 실제로 하는 일은 "빌릴 것을 찾는다" 또는 "내가 빌린 것을 돌려놓는다" 둘이며, 둘 다 **물건**에서 시작합니다. 그래서 목록에는 반출 가능한 물건이 늘어서고, 반출 기록은 그 물건을 열었을 때 그 안에 있습니다 — 회의실 예약이 회의실을 늘어놓고 그 방의 예약을 모달에서 다루는 것과 같은 구조이며, 다른 것은 빌리는 대상이 공간이 아니라 물건이라는 점뿐입니다.

> [!NOTE]
> **지사가 탭인 것은 자산 관리와 같은 이유입니다.** 목록의 단위가 반출 기록이 아니라 자산이고, 자산은 지사에 필수로 귀속되므로 지사가 곧 목록의 자리입니다. 다만 회의실이 **카드 격자**인 것과 달리 반출대장은 **표**입니다 — 후보 자산이 관리자가 만든 소수 목록이 아니라 원장에서 걸러진 수십~수백 행이라, 카드로 늘어놓으면 찾는 일이 오히려 어려워집니다.

## 5. 반출 원장 데이터 모델

### 5.1 필드 정의

| 화면 항목 | 컬럼 | 타입 | 필수 | 설명 |
| :--- | :--- | :--- | :---: | :--- |
| 물품 | `asset_id` | `uuid` → `assets(id)` | O | 반출 대상 자산. 등록 후에는 바꿀 수 없음 |
| 물품명(당시) | `asset_name` | `text` | O | 등록 시점 자산명 스냅샷(트리거 스탬프) |
| 품목(당시) | `asset_item_type` | `text` | | 등록 시점 품목 스냅샷 |
| 시리얼(당시) | `asset_serial_no` | `text` | | 등록 시점 시리얼 스냅샷 |
| 지사 | `branch_id` | `uuid` → `branches(id)` | O | 등록 시점 자산의 귀속 지사 스냅샷. 지사 탭의 기준 축 |
| 상태 | `status` | `public.asset_checkout_status` | O | 6종. 초기값은 자산의 승인 필요 여부가 정함 |
| 반출 일시 | `checkout_at` | `timestamptz` | O | 물건이 나가는(나간) 때. 날짜와 시각을 함께 받음 |
| 반납 예정 일시 | `due_at` | `timestamptz` | O | 돌려놓기로 한 때. **기간 점유의 끝** |
| 실제 반납 일시 | `returned_at` | `timestamptz` | | 실제로 돌아온 때. 상태 `RETURNED`와 짝 |
| 수량 | `quantity` | `integer` | O | 이번 반출로 들고 나가는 개수. 기본값 1, 1 이상 |
| 목적 | `purpose` | `text` | O | 왜 들고 나가는가. 대장의 존재 이유이므로 필수 |
| 행선지 | `destination` | `text` | | 어디로 가는가(고객사·행사장 등) |
| 비고 | `note` | `text` | | 자유 메모 |
| 반출자 | `created_by` | `uuid` → `users(id)` | O | 트리거 스탬프. 클라이언트 입력을 신뢰하지 않음 |
| 반출자명 | `created_by_name` | `text` | | `users` RLS 우회 표시용 비정규화(서버 스탬프) |
| 승인·반려자 | `decided_by` / `decided_at` | `uuid` / `timestamptz` | | 승인 또는 반려를 처리한 사람과 시각 |
| 처리 사유 | `decision_note` | `text` | | 반려 사유 등 |
| 반납 처리자 | `returned_by` / `returned_by_name` | `uuid` / `text` | | 본인 반납이면 반출자와 같고, 대리 반납이면 다름 |
| 반납 메모 | `return_note` | `text` | | 파손·분실 등 돌아온 상태 |
| 비활성 | `deleted_at` | `timestamptz` | | soft delete. 물리 삭제하지 않음 |

> [!NOTE]
> **자산의 표기 값을 스냅샷으로 복제하는 이유가 둘입니다.** 첫째는 사실입니다 — 대장은 "그때 그 물건을 들고 나갔다"는 기록이므로, 이후 자산명이 바뀌어도 그 시점의 이름으로 읽혀야 합니다. 둘째는 권한입니다 — `assets`의 조회 권한은 `app.can_read_workspace('management')`이라 MANAGEMENT 권한이 없는 임직원은 조인으로 자산명을 가져올 수 없습니다. 회의실 예약이 `created_by_name`을 비정규화한 것과 같은 이유이며, 같은 해법입니다.

### 5.2 상태 6종

| 값 | 라벨 | 의미 | 기간 점유 |
| :--- | :--- | :--- | :---: |
| `PENDING` | 승인 대기 | 승인이 필요한 자산에 대한 반출 요청 | O |
| `REJECTED` | 반려 | 승인권자가 거절 | |
| `RESERVED` | 예약 | 확정되었으나 아직 나가지 않음 | O |
| `OUT` | 반출 중 | 물건이 사외에 있음 | O |
| `RETURNED` | 반납 완료 | 돌아옴. 종결 | |
| `CANCELLED` | 취소 | 반출자가 스스로 물림. 종결 | |

* **승인 대기도 기간을 점유합니다**: 점유하지 않으면 승인이 떨어지는 순간 다른 예약과 겹쳐 실패하는데, 그 실패는 승인권자의 잘못이 아닌데도 승인권자 앞에서 일어납니다. 요청이 들어온 시점에 자리를 잡아 두고, 반려·취소되면 그때 놓습니다.
* **`RETURNED`·`REJECTED`·`CANCELLED`는 종결 상태입니다**: 이후 어떤 상태로도 되돌리지 않습니다. 잘못 처리했다면 새 반출 건을 만들며, 잘못 등록한 행은 관리자가 비활성화합니다.

### 5.3 상태 전이 규칙

| 전이 | 수행 주체 | 비고 |
| :--- | :--- | :--- |
| (등록) → `PENDING` | 반출자 | 자산의 `requires_approval`이 켜져 있을 때. **서버가 강제** |
| (등록) → `RESERVED` | 반출자 | 승인이 필요 없는 자산 |
| `PENDING` → `RESERVED` | 자산 담당자·관리자 | 승인. `decided_by`/`decided_at` 자동 스탬프 |
| `PENDING` → `REJECTED` | 자산 담당자·관리자 | 반려. 사유를 함께 적습니다 |
| `PENDING`·`RESERVED` → `CANCELLED` | 반출자 본인·자산 담당자·관리자 | |
| `RESERVED` → `OUT` | 반출자 본인·자산 담당자·관리자 | 실제로 물건을 가져간 시점 |
| `OUT` → `RETURNED` | 반출자 본인·자산 담당자·관리자 | `returned_on`(기본값 오늘)·`returned_by` 스탬프 |

* **초기 상태는 클라이언트가 정하지 않습니다**: 화면에서 승인 단계를 감추는 것만으로는 승인을 건너뛰는 요청을 막을 수 없습니다. INSERT 트리거가 대상 자산의 `requires_approval`을 읽어 상태를 덮어씁니다.
* **`asset_id`는 어떤 경우에도 바뀌지 않습니다**: 대상 자산을 바꿔치기할 수 있으면 승인받은 물건과 실제로 나간 물건이 달라질 수 있고, 그 순간 대장 전체가 거짓이 됩니다.
* **위 표에 없는 전이는 거부됩니다**: 트리거가 예외를 발생시킵니다.

### 5.4 기간 점유와 겹침 차단

* **점유 기간은 `반출 일시 ~ 반납 예정 일시`이며 끝을 포함하지 않습니다**(`tstzrange`, `[)`). 회의실 예약과 같은 규칙이며, 10시 반납과 10시 반출은 겹치지 않습니다. 처음에는 하루 단위(`daterange`, 양끝 포함)로 잡았으나 오전에 나갔다가 오후에 돌아오는 물건이 흔해, 하루를 통째로 잡으면 같은 날 다음 사람이 쓸 수 없었습니다. **시각까지 받으면 그 문제가 사라지고 겹침 판정도 반열림으로 정리됩니다.**
* **점유하는 상태는 `PENDING`·`RESERVED`·`OUT` 셋입니다**: 이 셋만 재고를 잡습니다. 처음에는 `EXCLUDE USING gist`로 겹침 자체를 막았으나, 보유 수량이 생기면서 재고 판정(§5.5)으로 바뀌었습니다.
* **길이가 0인 반출은 없습니다**: `due_at > checkout_at`을 강제합니다. 시각을 받는 순간 같은 시각에 나갔다 돌아온 기록은 기록이 아니게 됩니다.
* **연체는 제약이 아니라 사실입니다**: `status = 'OUT'`이고 `due_at < 지금`이면 연체입니다. 별도 컬럼을 두지 않고 조회 시점에 판정합니다 — 상태로 저장하면 시각이 지날 때마다 누군가 갱신해 주어야 하고, 그 갱신이 늦으면 화면이 거짓말을 합니다.
* **연체는 다음 예약을 침범합니다**: 점유는 *예정* 기간으로만 잡히므로, 반납되지 않은 채 다음 반출 시각이 오면 두 번째 사람이 빈손이 됩니다. 제약으로 막을 수 있는 종류의 문제가 아니므로(물건이 실제로 돌아오지 않은 것이니) **화면이 경고합니다** — 반출하러 온 사람에게 "이전 반출자 미반납(홍길동, 3일 경과)"을 띄웁니다.

### 5.5 재고 수량 (보유·잔여)

케이블·의자·측정기처럼 **같은 물건을 여러 개 두는 자산**이 실제로는 흔합니다. 보유 수량을 자산이 소유하고, 반출은 몇 개를 들고 나가는지를 함께 받습니다.

* **보유 수량은 자산 원장의 값입니다**(`assets.quantity`, 기본 1, 1 이상): MANAGEMENT `자산 관리`가 소유하며 반출대장은 읽기만 합니다. 수량 0은 "없는 자산"이라는 뜻이 되는데, 그것은 비활성화나 폐기로 말해야 할 일이라 1 미만을 허용하지 않습니다.
* **잔여는 저장하지 않고 계산합니다**: 보유 수량에서 그 시점에 나가 있는 개수를 뺍니다. 저장하면 반납·취소·연체 때마다 누군가 갱신해야 하고, 그 갱신이 늦으면 화면이 거짓말을 합니다(연체 판정과 같은 이유입니다).
* **겹침 차단(`EXCLUDE`)을 재고 판정으로 바꿉니다**: 제약은 두 행의 관계만 보므로 "다섯 개 중 몇 개 남았나"를 표현할 수 없습니다. 다섯 개 중 한 개를 빌린 시간에 다른 한 개를 빌리는 **정당한 요청까지 막아 버립니다.** 판정은 트리거 `app.check_asset_stock()`가 합니다.
* **판정 기준은 합계가 아니라 동시 최대입니다**: 오전에 한 개, 오후에 한 개가 나갔다면 그 하루에 동시에 나가 있는 것은 두 개가 아니라 한 개입니다. 요청 구간과 겹치는 점유들의 시작(+)·끝(−)을 시간순으로 훑어 누적의 최댓값을 취합니다. 합으로 세면 실제로는 남아 있는 물건을 못 빌리게 됩니다.
* **동시 요청은 자산 행 잠금으로 줄 세웁니다**: 두 사람이 같은 순간에 마지막 한 개를 집으면 각자 상대의 행을 아직 보지 못해 둘 다 통과합니다. 판정 전에 `assets` 행을 `for update`로 잠급니다.
* **거절 문구에 수치를 담습니다**: "이 기간에 2개를 요청했지만 잔여는 1개입니다(보유 3개)" — 화면이 다시 지어낼 수 없는 값이므로 서버 문장을 그대로 옮깁니다.

> [!NOTE]
> **물품의 상태는 저장하지 않고 파생하며, 수량이 생기면서 "나가 있음"과 "빌릴 수 없음"이 갈렸습니다.** 다섯 개 중 두 개가 나가 있어도 세 개는 빌릴 수 있으므로 상태는 여전히 `반출 가능`입니다. 잔여가 0일 때에야 무엇 때문에 못 빌리는지(`반출 중`·`승인 대기`·`예약`)를 적습니다. **연체만은 잔여와 무관하게 앞세웁니다** — 남은 게 있든 없든 돌아오지 않은 물건은 알려야 합니다.

## 6. 승인 필요 여부 (`assets.requires_approval`)

* **설정 자리는 자산 원장입니다**: MANAGEMENT `자산 관리`의 등록·수정 폼에서 **반출 가능 여부 토글 바로 아래**에 둡니다. 반출이 불가한 자산에 승인 여부를 묻는 것은 뜻이 없는 질문이므로, **반출 가능이 켜져 있을 때만 노출**합니다.
* **품목 단위가 아니라 자산 단위입니다**: 품목(`item_type`)은 원장이 없는 자유입력 텍스트라 정책을 매달 자리가 없습니다. 매달면 `노트북`과 `랩탑`이 서로 다른 승인 정책을 갖게 되고 오타 하나가 그대로 정책 구멍이 됩니다. 대신 **품목으로 검색해 여러 자산을 골라 한 번에 설정**할 수 있게 자산 목록의 선택 요약 줄에 일괄 설정을 둡니다(차량 12대를 한 번에 승인 대상으로 돌리는 실제 사용법이 이것입니다).
* **승인권자는 자산 원장의 주인입니다**: `app.can_write_workspace('management')` 또는 `super_admin`. 자산의 반출 가능 여부를 정하는 사람과 그 반출을 승인하는 사람이 같아야 기준이 하나로 유지됩니다.
* **기본값은 꺼짐입니다**: 기존 자산은 모두 승인 없이 반출됩니다. 통제가 필요한 물건만 켜는 쪽이, 전부 켜 두고 예외를 파는 쪽보다 운영이 정직합니다.

## 7. 반출 후보 자산의 노출 (`public.portable_assets`)

반출대장이 실제로 쓰이려면 MANAGEMENT 권한이 없는 임직원도 후보 자산을 볼 수 있어야 하는데, `assets`의 RLS는 그것을 허용하지 않습니다. 원장의 정책을 느슨하게 푸는 대신 **필요한 만큼만 보여 주는 뷰**를 별도로 둡니다.

* **뷰가 거르는 조건**: `deleted_at is null` AND `is_portable = true` AND `status <> 'RETIRED'` — [3_7_2](./3_7_2_management_assets.md) §7이 정한 후보 규칙 그대로입니다. 반출대장은 자산의 성격을 다시 판단하지 않습니다.
* **뷰가 내보내는 값**: `id` · `자산명` · `품목` · `시리얼` · `지사` · `승인 필요 여부` · `설명(비고)` · `사진 경로 전체`. **금액·결제 주기·할당 대상은 내보내지 않습니다** — 물건을 빌리는 데 필요한 정보가 아니고, 취득가와 담당자는 각각 비용 정보와 인사 정보입니다. 사진과 설명은 그 반대입니다: 물건을 알아보는 유일한 단서라 목록과 모달이 함께 씁니다.
* **뷰 자체가 접근을 판정합니다**: 뷰는 정의자 권한으로 실행되어 원장 RLS를 통과하므로, 본문 조건에 `app.is_internal_user()`를 포함해 외부 게스트를 차단합니다. `authenticated`에만 `SELECT`를 부여합니다.
* **사진 버킷의 조회 권한을 내부 임직원으로 넓힙니다**: `asset-photos`의 `storage.objects` SELECT 정책을 `app.can_read_workspace('management')`에서 `app.is_internal_user()`로 바꿉니다. 버킷은 그대로 **비공개**이며(공개 URL 없음, 표시는 단기 Signed URL) 업로드·수정은 계속 MANAGEMENT 쓰기 권한자만 합니다 — 원장의 주인이 사진의 주인이라는 규칙은 그대로 두고, 읽는 사람만 넓힙니다. 반출 화면에서 사진을 못 보면 같은 모델 세 대 중 무엇을 빌리는지 가릴 수 없습니다.

## 8. 화면 사양

### 8.1 물품 목록

* **지사 탭**: 활성 지사를 순서대로 노출하고 첫 진입 시 첫 지사를 선택합니다.
* **표 열 구성**: `물품`(사진 썸네일 + 자산명) · `품목` · `시리얼 번호` · `잔여`(`3 / 5`) · `상태` · `반출자` · `반납 예정` + 처리 열.
* **잔여는 보유와 나란히 적습니다**: `3`이라는 수는 보유가 3일 때와 10일 때 뜻이 다릅니다. 이 표에서 가장 자주 읽히는 숫자이므로 상태보다 앞에 둡니다 — "빌릴 수 있나"에 먼저 답하는 값입니다.
* **상태는 파생값입니다**: `반출 가능` · `승인 대기` · `예약` · `반출 중` · `연체`(§5.4).
* **연체 표기**: 반납 예정 칸에 경과를 함께 적습니다(`2026-07-25 14:00 3일 경과`). 큰 단위 하나만 적습니다 — 읽는 사람이 알고 싶은 것은 얼마나 늦었나의 크기뿐입니다. 행 전체를 붉게 칠하지 않고, **이 표에서 색은 연체 하나에만 씁니다** — 색을 여러 값에 나눠 주면 어느 색도 경고가 되지 못합니다.
* **검색·상태 필터는 화면에서 겁니다**: 조회 단위가 지사 하나라 서버로 되돌아갈 만큼 크지 않고, 상태는 애초에 서버에 저장되어 있지 않은 파생값이라 서버가 답할 수 없습니다. 검색은 물품명·품목·시리얼·반출자를 함께 훑습니다.
* **처리 열에는 대표 처리 하나만 둡니다**: 잔여가 있으면 [반출하기], 내가(또는 관리자가) 반납할 수 있으면 [반납하기], 승인 대기이고 승인권자면 [승인 처리](모달을 엽니다). 승인·취소처럼 판단이 필요한 일은 물건을 열어서 합니다 — 표에 버튼을 늘어놓으면 정작 "지금 있나"가 묻힙니다.

### 8.2 물품 모달

물건 하나가 곧 그 물건의 대장입니다. **좌우 2열**로 나누며, 회의실 예약 모달(그날 예약 목록 + `+ 예약하기`)과 같은 **목록 → 폼** 전환을 오른쪽 열에서 씁니다.

```
[물품명]                                        (모달 폭 xl)
┌── 좌: 사진 ─────────┬── 우: 알아야 할 것과 지금 할 수 있는 일 ──────┐
│  정사각 고정 틀      │  품목 · 시리얼 번호 · 보유 지사 · 반출 승인    │
│  ‹ 좌우 무한 넘김 ›   │  설명(자산 원장의 비고)                      │
│  · · · (점 표시)     │  반출 이력 (최근 5건)                        │
│                     │   └ 기간 · 상태 · 반출자 · 목적/행선지         │
│                     │     + [승인][반려][반출 시작][반납하기][취소]  │
│                     │  [+ 반출하기] → 오른쪽 열이 등록 폼으로 전환    │
└─────────────────────┴────────────────────────────────────────────┘
```

* **좌우로 가르는 이유는 두 열이 다른 질문에 답하기 때문입니다**: 왼쪽은 "이게 그 물건이 맞나", 오른쪽은 "지금 가져갈 수 있나"입니다. 위아래로 쌓으면 사진을 보는 동안 답이 화면 밖으로 밀립니다.
* **사진 틀은 고정하고 사진을 잘라 맞춥니다**(정사각 · `object-cover` · 가운데 기준). 사진마다 비율이 달라, 틀을 사진에 맞추면 넘길 때마다 모달 높이가 출렁이고 옆 열까지 함께 밀립니다. 잘려 나가는 가장자리보다 자리가 흔들리지 않는 편이 물건을 알아보는 데 낫습니다.
* **넘김은 끝에서 처음으로 이어집니다(무한)**: 다섯 장뿐인 목록에서 마지막 장의 버튼이 죽어 있으면, 되돌아가려고 왼쪽 버튼을 네 번 누르게 됩니다. 몇 번째인지는 점으로만 알립니다 — 숫자를 적으면 사진보다 글자가 먼저 읽힙니다.
* **이력은 한 목록입니다**: 지금 걸린 건과 지난 기록을 함께 담고 최근 5건까지 적되, **지금 걸린 건이 항상 먼저 옵니다** — 처리할 수 있는 것을 스크롤해서 찾게 하지 않습니다. 끝난 건은 배경을 빼서 손댈 수 있는 건과 갈라 보입니다.
* **폼으로 바뀌어도 사진은 남습니다**: 오른쪽 열만 등록 폼으로 바뀌므로, 시각을 고르는 동안에도 무엇을 빌리는 중인지가 눈앞에 있습니다.

### 8.3 반출 등록 폼(모달 안)

```
 ├── (있을 때) 승인 필요 안내 / 미반납 경고
 ├── 1행: 반출 일시(필수, 기본 지금) | 반납 예정 일시(필수, 기본 하루 뒤)
 ├── 2행: 수량(필수, 기본 1 — "이 기간 잔여 n개 / 보유 m개")
 ├── (있을 때) 재고 부족 경고 / 같은 기간 점유 안내
 ├── 3행: 목적(필수)                | 행선지
 ├── 비고
 └── [뒤로] [반출 등록 / 승인 요청]
```

* **물건을 다시 고르게 하지 않습니다**: 물건을 눌러 들어온 자리이므로 대상은 이미 정해져 있습니다.
* **"지금 가져감"과 "미리 잡아 둠"을 화면에서 가르지 않습니다**: 반출 일시 기본값이 지금일 뿐, 둘은 같은 등록입니다. 모드를 나누면 사용자가 먼저 자기 상황을 분류해야 하는데, 그 분류는 이미 시각이 말하고 있습니다.
* **반납 예정은 필수이며 기본값은 하루 뒤입니다**: 기간이 없으면 겹침을 판정할 수 없어 예약 자체가 성립하지 않습니다. 반출 일시를 고치면 아직 손대지 않은 반납 예정은 함께 따라갑니다.
* **승인이 필요한 자산이면 그 자리에서 알립니다**: 등록 버튼의 문구를 `승인 요청`으로 바꾸고, 등록 후 상태가 `승인 대기`임을 안내합니다. 눌러 보고 나서 알게 되지 않도록 합니다.
* **잔여를 고르는 자리 옆에 계속 적어 둡니다**: 일시를 바꾸면 잔여도 함께 바뀝니다. 요청이 잔여를 넘으면 경고를 띄우고 등록 버튼을 잠급니다.
* **기간이 겹친다고 곧바로 막지 않습니다**: 다섯 개 중 두 개가 나가 있어도 세 개는 빌릴 수 있습니다. 겹치는 건은 "누가 몇 개를 잡고 있는지" 알려 주는 정보로 두고(info), 경고(danger)는 요청 수량이 잔여를 넘을 때만 냅니다.
* **최종 판정은 서버입니다**: 화면의 잔여는 조회 시점의 값이라, 그 사이 다른 사람이 먼저 가져갔을 수 있습니다. 거절되면 서버가 보낸 수치 있는 문장을 그대로 보여 줍니다.

### 8.4 반납 처리

* **반출자 본인이 스스로 처리합니다**: 물건을 돌려놓으면서 표나 모달에서 [반납하기]를 누르며, 실제 반납 일시(기본 지금)와 상태 메모를 남깁니다. 예정과 다른 때가 흔하고, 그 차이가 곧 이 대장이 남기려는 사실입니다.
* **관리자 대리 반납이 있습니다**: 퇴사·장기 연체처럼 본인이 처리하지 못하는 건을 자산 담당자·관리자가 대신 종결합니다. `returned_by`가 반출자와 다르게 남아 대리 처리였음이 기록됩니다.
* **파손·분실은 메모로 남깁니다**: 반납 메모에 적으며, 자산의 상태(`MAINTENANCE`·`RETIRED`) 전환은 MANAGEMENT `자산 관리`의 조치입니다. 대장이 자산의 실물 상태를 바꾸지 않습니다.

## 9. 권한·RLS

* **조회는 내부 임직원 전원입니다**(`app.is_internal_user()`): "누가 무엇을 갖고 있나"는 전사가 공유해야 하는 사실입니다. 외부 스타트업·전문가·임시 게스트는 접근하지 못합니다.
* **등록은 본인 명의만 가능합니다**: `created_by = app.current_app_user_id()`를 `WITH CHECK`로 강제합니다. 남의 이름으로 반출 건을 만들 수 없습니다.
* **수정 권한자는 셋입니다**: 반출자 본인 · `management` 쓰기 권한자 · `super_admin`. 다만 **무엇으로 바꿀 수 있는가는 RLS가 아니라 전이 트리거가 판정합니다**(§5.3) — 승인은 승인권자만, 반납·취소는 본인·관리자입니다.
* **DELETE 정책은 만들지 않습니다**: soft delete만 사용합니다.
* **자산 원장은 건드리지 않습니다**: 반출대장은 `assets`에 쓰지 않습니다. "반출 중"이라는 상태를 자산 원장에 만들지 않는 이유는 §12에 적습니다.
* **감사 로그 대상이 아닙니다**: 사내 물품 대여 기록으로 개인정보 원본 조회·대량 Export·권한 변경 어디에도 해당하지 않습니다. 반출자·반납 처리자 추적은 행의 `created_by`/`returned_by`로 남습니다.

## 12. 자산 상태와의 관계

**`assets.status`에 `반출중`을 추가하지 않습니다.** 이유가 셋입니다.

* **축이 다릅니다**: 상태 4값(`보유`/`할당`/`보수`/`폐기`)은 자산의 소유 국면이고 반출은 위치입니다. 할당된 노트북을 반출하면 두 사실이 동시에 참인데, 한 컬럼에 담으면 둘 중 하나를 잃습니다.
* **권한이 어긋납니다**: 반출 등록만으로 자산 원장을 고칠 수 있어야 하는데, 그러려면 임직원 전원에게 MANAGEMENT 쓰기 권한을 주거나 그 권한을 우회하는 함수를 만들어야 합니다. 둘 다 대가가 이득보다 큽니다.
* **파생값은 어긋나지 않습니다**: "지금 반출 중인가"는 대장에 유효한 `OUT` 행이 있는가로 언제나 정확히 답할 수 있습니다. 저장하면 두 곳의 사실이 갈라질 수 있지만, 파생하면 갈라질 자리가 없습니다.

MANAGEMENT 자산 표에 "지금 나가 있음(반출자·반납 예정)"을 파생 열로 보여 주는 것은 후속 과제입니다.

## 13. 후속 과제

* **반납 예정일 알림** — 임박·연체 건을 알림 센터와 전사 캘린더에 띄웁니다.
* **MANAGEMENT 자산 표의 반출 현황 열** — 자산 목록에서 지금 나가 있는 물건을 파생 열로 표기합니다.
* **관리자 대리 등록** — 전화·구두로 요청받은 반출을 관리자가 타인 명의로 등록하는 경로(현재는 본인 등록만 가능합니다).
* **QR·바코드 스캔 반출** — 자산 명판을 찍어 반출·반납을 처리합니다.
* **반출 통계** — 물품별 반출 빈도와 평균 대여 기간으로 보유 수량 판단을 돕습니다.

## 14. 테스트 기준

* 반출 가능 토글이 꺼진 자산과 폐기 자산은 물품 목록에 나타나지 않는다.
* MANAGEMENT 권한이 없는 임직원도 물품 목록과 사진을 볼 수 있고, 그 목록에 금액·할당 대상이 없다.
* 외부 게스트 계정으로는 물품 목록과 반출대장이 모두 조회되지 않는다.
* 승인 필요 여부가 꺼진 자산을 등록하면 상태가 `예약`, 켜진 자산을 등록하면 `승인 대기`가 된다.
* 클라이언트가 상태를 `RESERVED`로 지정해 보내도, 승인 필요 자산이면 `PENDING`으로 저장된다.
* 보유 3개인 물품에서 2개를 반출한 뒤 같은 시간대에 2개를 더 요청하면 거부되고, 1개는 등록된다.
* 보유 3개인 물품을 오전에 1개, 오후에 1개 반출해도 각각 등록된다(동시 최대는 1개이므로).
* 한 개짜리 물품에 시간대가 겹치는 반출을 등록하면 두 번째 등록이 거부된다.
* 다섯 개 중 두 개가 나가 있는 물품의 상태는 `반출 가능`이고 잔여 칸은 `3 / 5`로 적힌다.
* 잔여가 0인 물품에는 표의 [반출하기] 버튼이 나타나지 않는다.
* 앞 건의 반납 예정과 같은 시각에 시작하는 반출은 등록된다(반열림 구간).
* 반납 예정을 반출 일시와 같거나 앞선 시각으로 입력하면 저장되지 않는다.
* 승인 권한이 없는 사용자가 `승인 대기` 건을 `예약`으로 바꾸려 하면 거부된다.
* 반출자 본인이 `예약` 건을 취소할 수 있고, 취소한 시간대에 다른 사람이 곧바로 예약할 수 있다.
* `반출 중` 건을 반납 처리하면 실제 반납 일시가 기록되고, 그 물품의 상태가 `반출 가능`으로 돌아온다.
* 관리자가 대리 반납하면 반납 처리자가 반출자와 다르게 기록된다.
* 반납 예정이 지난 `반출 중` 물품은 상태가 `연체`로 표기되고 경과가 함께 적힌다.
* 한 물품에 반출 중 건과 다음 주 예약이 함께 있으면 목록에는 `반출 중`으로 적히고, 물품을 열면 두 건이 모두 보인다.
* 사진이 다섯 장인 물품에서 마지막 장의 다음 버튼을 누르면 첫 장으로 돌아온다.
* 세로로 긴 사진과 가로로 긴 사진을 번갈아 넘겨도 사진 틀의 크기가 변하지 않는다.
* 사진이 없는 물품을 열어도 왼쪽 열의 자리는 유지되고 오른쪽 정보가 밀리지 않는다.
* 종결 상태(`반납 완료`·`반려`·`취소`)의 건은 어떤 상태로도 되돌릴 수 없다.
* 반출 건의 대상 자산을 다른 자산으로 바꾸려 하면 거부된다.
* 자산명을 바꿔도 이미 등록된 반출 건에는 등록 당시의 이름이 남는다.
* 마이그레이션 재실행 시 오류 없이 통과한다(멱등).
