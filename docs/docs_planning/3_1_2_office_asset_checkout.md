# [3-1-2] OFFICE 반출대장 기획서

본 문서는 OFFICE 워크스페이스 `반출대장`(`/office?tab=outbound`) 화면의 데이터 모델과 기능 요건을 명세합니다. 반출대장은 **회사 물건이 사외로 나갔다가 돌아오는 사실을 기록하는 원장**이며, 후보가 되는 자산과 그 반출 가능 여부는 MANAGEMENT `자산 관리`([3_7_2_management_assets.md](./3_7_2_management_assets.md))가 소유합니다. 상위 워크스페이스 기획은 [3_1_workspace_hub.md](./3_1_workspace_hub.md)입니다.

---

## 1. 목적

* **물건의 현재 소재를 사실대로 답합니다**: "그 빔프로젝터 지금 누가 갖고 있나"에 답할 수 있는 곳이 없어, 실물을 찾는 일이 매번 사람을 수소문하는 일이 되었습니다. 반출 건을 원장에 남겨 **물품 기준·사람 기준 양방향 조회**가 가능하게 합니다.
* **돌아오지 않은 물건을 드러냅니다**: 회의실은 시간이 지나면 저절로 비지만 물건은 누군가 돌려놓아야 비워집니다. **반납 예정일과 실제 반납일을 별개 값으로 두어** 연체를 화면이 스스로 알아보게 합니다.
* **미리 잡아 둘 수 있게 합니다**: 다음 주 외부 행사에 쓸 장비를 그날 가서 없는 것을 확인하는 일이 없도록, **기간 점유(예약)** 를 지원하고 겹침을 DB가 원자적으로 차단합니다.
* **통제 강도를 물건마다 다르게 둡니다**: 노트북 거치대와 법인 차량을 같은 절차로 다룰 수는 없습니다. **자산별 승인 필요 여부**를 켜서, 그 물건만 승인을 거치게 합니다.

---

## 2. 이 문서가 다루는 범위

* **포함**:
  * 반출 원장(`public.asset_checkouts`) 정의와 상태 6종의 전이 규칙
  * 기간 점유·겹침 차단 규칙과 연체 판정
  * 자산별 승인 필요 여부(`assets.requires_approval`)와 승인·반려 흐름
  * 내부 임직원 전원에게 반출 후보 자산을 노출하는 경로(`public.portable_assets` 뷰)
  * 반출대장 목록·등록·반납 화면 사양
  * 권한·RLS 및 마이그레이션 설계
* **제외(별도 범위)**:
  * **수량·재고 관리** — 자산 원장은 1행이 물건 하나이므로 "3개 중 2개 대여 중" 같은 개념이 없습니다. 소모품 재고는 자산 원장의 대상이 아닙니다.
  * **반출증 출력·서명** — 종이 반출증 양식 출력과 서명 수집은 다루지 않습니다. 결재가 필요한 반출은 전자결재를 쓰고, 본 대장은 사실 기록을 담당합니다.
  * **알림·리마인더** — 반납 예정일 임박·연체 알림은 후속 과제입니다. 본 범위는 화면에서 연체를 드러내는 데까지입니다.
  * **바코드·QR 스캔** — 현장 스캔 입력은 후속 과제입니다.
  * **분실·파손 처리의 후속 절차** — 반납 시 상태를 메모로 남기는 데까지이며, 변상·폐기 전환은 자산 관리 쪽 조치입니다.

---

## 3. 핵심 사용자

* **반출자(내부 임직원 전원)**: 반출 가능 물품을 찾아 기간·목적을 적어 등록하고, 돌아와서 반납 처리합니다. 본인 반출 건만 만들 수 있습니다.
* **동료(내부 임직원 전원)**: 물건이 지금 어디 있는지, 언제 돌아오는지를 조회합니다. 남의 반출 건을 고치지는 않습니다.
* **자산 담당자(`management` write)**: 승인이 필요한 물건의 반출을 승인·반려하고, 연체 건을 확인하며, 반출자가 처리하지 못한 반납을 대리로 처리합니다.
* **관리자(`super_admin`)**: 위 모든 권한을 가지며, 잘못 등록된 반출 건을 비활성화합니다.

## 4. 정보 구조 (Information Architecture)

```
[반출대장 탭]
 ├── 상단 액션 (반출 등록)
 ├── 뷰 탭 (반출 중 · 연체 · 승인 대기 · 예약 · 내 반출 · 전체)
 ├── 검색(물품명·시리얼·반출자) + 지사 필터
 └── 반출 표
      ├── 도메인 열: 물품 · 지사 · 반출자 · 반출일 · 반납 예정 · 실제 반납 · 상태
      ├── 관리 열: 상태에 따라 [승인/반려] [반출 시작] [반납] [취소]
      └── 행 클릭 → 반출 상세 모달(목적·행선지·비고·처리 이력)
```

> [!NOTE]
> **지사는 탭이 아니라 필터입니다.** 자산 관리에서 지사가 탭인 것은 "이 지사에 무엇이 있는가"가 그 화면의 질문이기 때문입니다. 반출대장의 질문은 "이 물건이 지금 어디 있는가"이고 그 답은 지사를 가로지릅니다 — 지사를 탭으로 두면 다른 지사 물건을 빌린 기록이 목록에서 사라져, 찾는 일이 탭을 하나씩 여는 일이 됩니다. 탭 자리는 대신 **뷰**(무엇을 묻고 있는가)가 씁니다.

> [!NOTE]
> **회의실 예약과 골격은 같고 축이 다릅니다.** "조회는 내부 전원, 쓰기는 본인 것만"이라는 권한 규칙과 목록 → 모달 흐름은 [회의실 예약](./3_1_workspace_hub.md)에서 그대로 가져옵니다. 다만 회의실이 **카드 격자**인 것과 달리 반출대장은 **표**입니다 — 후보 자산이 관리자가 만든 소수 목록이 아니라 수백 행의 원장이라, 카드로 늘어놓으면 찾는 일이 오히려 어려워집니다.

## 5. 반출 원장 데이터 모델

### 5.1 필드 정의

| 화면 항목 | 컬럼 | 타입 | 필수 | 설명 |
| :--- | :--- | :--- | :---: | :--- |
| 물품 | `asset_id` | `uuid` → `assets(id)` | O | 반출 대상 자산. 등록 후에는 바꿀 수 없음 |
| 물품명(당시) | `asset_name` | `text` | O | 등록 시점 자산명 스냅샷(트리거 스탬프) |
| 품목(당시) | `asset_item_type` | `text` | | 등록 시점 품목 스냅샷 |
| 시리얼(당시) | `asset_serial_no` | `text` | | 등록 시점 시리얼 스냅샷 |
| 지사 | `branch_id` | `uuid` → `branches(id)` | O | 등록 시점 자산의 귀속 지사 스냅샷. 지사 탭의 기준 축 |
| 상태 | `status` | `public.asset_checkout_status` | O | 6종. 초기값은 자산의 승인 필요 여부가 정함 |
| 반출일 | `checkout_on` | `date` | O | 물건이 나가는(나간) 날 |
| 반납 예정일 | `due_on` | `date` | O | 돌려놓기로 한 날. **기간 점유의 끝** |
| 실제 반납일 | `returned_on` | `date` | | 실제로 돌아온 날. 상태 `RETURNED`와 짝 |
| 목적 | `purpose` | `text` | O | 왜 들고 나가는가. 대장의 존재 이유이므로 필수 |
| 행선지 | `destination` | `text` | | 어디로 가는가(고객사·행사장 등) |
| 비고 | `note` | `text` | | 자유 메모 |
| 반출자 | `created_by` | `uuid` → `users(id)` | O | 트리거 스탬프. 클라이언트 입력을 신뢰하지 않음 |
| 반출자명 | `created_by_name` | `text` | | `users` RLS 우회 표시용 비정규화(서버 스탬프) |
| 승인·반려자 | `decided_by` / `decided_at` | `uuid` / `timestamptz` | | 승인 또는 반려를 처리한 사람과 시각 |
| 처리 사유 | `decision_note` | `text` | | 반려 사유 등 |
| 반납 처리자 | `returned_by` / `returned_by_name` | `uuid` / `text` | | 본인 반납이면 반출자와 같고, 대리 반납이면 다름 |
| 반납 메모 | `return_note` | `text` | | 파손·분실 등 돌아온 상태 |
| 비활성 | `deleted_at` | `timestamptz` | | soft delete. 물리 삭제하지 않음 |

> [!NOTE]
> **자산의 표기 값을 스냅샷으로 복제하는 이유가 둘입니다.** 첫째는 사실입니다 — 대장은 "그때 그 물건을 들고 나갔다"는 기록이므로, 이후 자산명이 바뀌어도 그 시점의 이름으로 읽혀야 합니다. 둘째는 권한입니다 — `assets`의 조회 권한은 `app.can_read_workspace('management')`이라 MANAGEMENT 권한이 없는 임직원은 조인으로 자산명을 가져올 수 없습니다. 회의실 예약이 `created_by_name`을 비정규화한 것과 같은 이유이며, 같은 해법입니다.

### 5.2 상태 6종

| 값 | 라벨 | 의미 | 기간 점유 |
| :--- | :--- | :--- | :---: |
| `PENDING` | 승인 대기 | 승인이 필요한 자산에 대한 반출 요청 | O |
| `REJECTED` | 반려 | 승인권자가 거절 | |
| `RESERVED` | 예약 | 확정되었으나 아직 나가지 않음 | O |
| `OUT` | 반출 중 | 물건이 사외에 있음 | O |
| `RETURNED` | 반납 완료 | 돌아옴. 종결 | |
| `CANCELLED` | 취소 | 반출자가 스스로 물림. 종결 | |

* **승인 대기도 기간을 점유합니다**: 점유하지 않으면 승인이 떨어지는 순간 다른 예약과 겹쳐 실패하는데, 그 실패는 승인권자의 잘못이 아닌데도 승인권자 앞에서 일어납니다. 요청이 들어온 시점에 자리를 잡아 두고, 반려·취소되면 그때 놓습니다.
* **`RETURNED`·`REJECTED`·`CANCELLED`는 종결 상태입니다**: 이후 어떤 상태로도 되돌리지 않습니다. 잘못 처리했다면 새 반출 건을 만들며, 잘못 등록한 행은 관리자가 비활성화합니다.

### 5.3 상태 전이 규칙

| 전이 | 수행 주체 | 비고 |
| :--- | :--- | :--- |
| (등록) → `PENDING` | 반출자 | 자산의 `requires_approval`이 켜져 있을 때. **서버가 강제** |
| (등록) → `RESERVED` | 반출자 | 승인이 필요 없는 자산 |
| `PENDING` → `RESERVED` | 자산 담당자·관리자 | 승인. `decided_by`/`decided_at` 자동 스탬프 |
| `PENDING` → `REJECTED` | 자산 담당자·관리자 | 반려. 사유를 함께 적습니다 |
| `PENDING`·`RESERVED` → `CANCELLED` | 반출자 본인·자산 담당자·관리자 | |
| `RESERVED` → `OUT` | 반출자 본인·자산 담당자·관리자 | 실제로 물건을 가져간 시점 |
| `OUT` → `RETURNED` | 반출자 본인·자산 담당자·관리자 | `returned_on`(기본값 오늘)·`returned_by` 스탬프 |

* **초기 상태는 클라이언트가 정하지 않습니다**: 화면에서 승인 단계를 감추는 것만으로는 승인을 건너뛰는 요청을 막을 수 없습니다. INSERT 트리거가 대상 자산의 `requires_approval`을 읽어 상태를 덮어씁니다.
* **`asset_id`는 어떤 경우에도 바뀌지 않습니다**: 대상 자산을 바꿔치기할 수 있으면 승인받은 물건과 실제로 나간 물건이 달라질 수 있고, 그 순간 대장 전체가 거짓이 됩니다.
* **위 표에 없는 전이는 거부됩니다**: 트리거가 예외를 발생시킵니다.

### 5.4 기간 점유와 겹침 차단

* **점유 기간은 `반출일 ~ 반납 예정일`이며 양끝을 포함합니다**(`daterange`, `[]`). 회의실이 `[)`(09:30 종료와 09:30 시작은 겹치지 않음)인 것과 다릅니다 — 시간은 연속이지만 날짜는 하루가 통째이고, 같은 날 오전에 돌아온 물건을 오후에 다시 내보내는 일을 허용하려면 시각을 받아야 하는데 그러면 회의실과 같은 화면이 되어 버립니다. 하루를 통째로 잡는 쪽이 현장에서 안전합니다.
* **겹침은 DB가 원자적으로 막습니다**: `EXCLUDE USING gist (asset_id with =, 기간 with &&)`를 `PENDING`·`RESERVED`·`OUT` 상태의 유효 행에만 겁니다. 두 사람이 동시에 같은 장비를 잡아도 한 명만 성공합니다.
* **연체는 제약이 아니라 사실입니다**: `status = 'OUT'`이고 `due_on < 오늘`이면 연체입니다. 별도 컬럼을 두지 않고 조회 시점에 판정합니다 — 상태로 저장하면 날짜가 바뀔 때마다 누군가 갱신해 주어야 하고, 그 갱신이 늦으면 화면이 거짓말을 합니다.
* **연체는 다음 예약을 침범합니다**: 점유는 *예정* 기간으로만 잡히므로, 반납되지 않은 채 다음 반출일이 오면 두 번째 사람이 빈손이 됩니다. 제약으로 막을 수 있는 종류의 문제가 아니므로(물건이 실제로 돌아오지 않은 것이니) **화면이 경고합니다** — 반출하러 온 사람에게 "이전 반출자 미반납(홍길동, 3일 경과)"을 띄웁니다.

## 6. 승인 필요 여부 (`assets.requires_approval`)

* **설정 자리는 자산 원장입니다**: MANAGEMENT `자산 관리`의 등록·수정 폼에서 **반출 가능 여부 토글 바로 아래**에 둡니다. 반출이 불가한 자산에 승인 여부를 묻는 것은 뜻이 없는 질문이므로, **반출 가능이 켜져 있을 때만 노출**합니다.
* **품목 단위가 아니라 자산 단위입니다**: 품목(`item_type`)은 원장이 없는 자유입력 텍스트라 정책을 매달 자리가 없습니다. 매달면 `노트북`과 `랩탑`이 서로 다른 승인 정책을 갖게 되고 오타 하나가 그대로 정책 구멍이 됩니다. 대신 **품목으로 검색해 여러 자산을 골라 한 번에 설정**할 수 있게 자산 목록의 선택 요약 줄에 일괄 설정을 둡니다(차량 12대를 한 번에 승인 대상으로 돌리는 실제 사용법이 이것입니다).
* **승인권자는 자산 원장의 주인입니다**: `app.can_write_workspace('management')` 또는 `super_admin`. 자산의 반출 가능 여부를 정하는 사람과 그 반출을 승인하는 사람이 같아야 기준이 하나로 유지됩니다.
* **기본값은 꺼짐입니다**: 기존 자산은 모두 승인 없이 반출됩니다. 통제가 필요한 물건만 켜는 쪽이, 전부 켜 두고 예외를 파는 쪽보다 운영이 정직합니다.

## 7. 반출 후보 자산의 노출 (`public.portable_assets`)

반출대장이 실제로 쓰이려면 MANAGEMENT 권한이 없는 임직원도 후보 자산을 볼 수 있어야 하는데, `assets`의 RLS는 그것을 허용하지 않습니다. 원장의 정책을 느슨하게 푸는 대신 **필요한 만큼만 보여 주는 뷰**를 별도로 둡니다.

* **뷰가 거르는 조건**: `deleted_at is null` AND `is_portable = true` AND `status <> 'RETIRED'` — [3_7_2](./3_7_2_management_assets.md) §7이 정한 후보 규칙 그대로입니다. 반출대장은 자산의 성격을 다시 판단하지 않습니다.
* **뷰가 내보내는 값**: `id` · `자산명` · `품목` · `시리얼` · `지사` · `승인 필요 여부` · `대표 사진 1장`. **금액·결제 주기·할당 대상·비고는 내보내지 않습니다** — 물건을 빌리는 데 필요한 정보가 아니고, 취득가와 담당자는 각각 비용 정보와 인사 정보입니다.
* **뷰 자체가 접근을 판정합니다**: 뷰는 정의자 권한으로 실행되어 원장 RLS를 통과하므로, 본문 조건에 `app.is_internal_user()`를 포함해 외부 게스트를 차단합니다. `authenticated`에만 `SELECT`를 부여합니다.

## 8. 화면 사양

### 8.1 목록

* **뷰 탭**: `반출 중`(기본) · `연체` · `승인 대기` · `예약` · `내 반출` · `전체`. 처음 열었을 때 답해야 할 질문이 "지금 나가 있는 물건이 무엇인가"이므로 기본값이 `반출 중`입니다.
* **지사 필터**: 활성 지사 다중 선택. 조건이지 자리가 아닙니다(§4).
* **검색**: 물품명 · 시리얼 · 반출자명을 함께 훑습니다(현장에서 반출 건을 찾는 세 가지 단서입니다).
* **표 열 구성**: `물품`(자산명 + 품목·시리얼 보조 표기) · `지사` · `반출자` · `반출일` · `반납 예정` · `실제 반납` · `상태` + 관리 열.
* **연체 표기**: 반납 예정일이 지난 `OUT` 행은 반납 예정 칸에 경과 일수를 함께 적습니다(`2026-07-25 (5일 경과)`). 행 전체를 붉게 칠하지 않습니다 — 표에서 색은 상태 열이 이미 쓰고 있습니다.
* **관리 열**: 상태와 권한에 따라 버튼이 갈립니다. `PENDING`이면 승인권자에게 [승인] [반려], `RESERVED`면 본인·관리자에게 [반출 시작] [취소], `OUT`이면 [반납], 종결 상태면 비어 있습니다.

### 8.2 반출 등록 모달

```
[반출 등록]
 ├── 물품 (반출 후보 검색 선택 — 필수)
 │    └── 선택 시: 승인 필요 여부 안내 / 미반납 경고(있을 때)
 ├── 1행: 반출일(필수, 기본 오늘) | 반납 예정일(필수)
 ├── 2행: 목적(필수)             | 행선지
 ├── 비고 (여러 줄)
 └── 푸터: [취소] [등록]
```

* **"지금 가져감"과 "미리 잡아 둠"을 화면에서 가르지 않습니다**: 반출일 기본값이 오늘일 뿐, 둘은 같은 등록입니다. 모드를 나누면 사용자가 먼저 자기 상황을 분류해야 하는데, 그 분류는 날짜가 이미 말하고 있습니다.
* **반납 예정일은 필수입니다**: 기간이 없으면 겹침을 판정할 수 없어 예약 자체가 성립하지 않습니다. 끝을 모르는 반출은 대장에서 영원히 열린 행으로 남습니다.
* **승인이 필요한 자산을 고르면 그 자리에서 알립니다**: 등록 버튼의 문구를 `승인 요청`으로 바꾸고, 등록 후 상태가 `승인 대기`임을 안내합니다. 눌러 보고 나서 알게 되지 않도록 합니다.
* **겹침은 저장 시 DB가 판정합니다**: 화면은 선택한 자산의 다가오는 점유 기간을 미리 보여 주되, 최종 판정은 제약입니다. 실패하면 "그 기간에는 이미 예약이 있습니다"로 안내합니다.

### 8.3 반납 처리

* **반출자 본인이 스스로 처리합니다**: 물건을 돌려놓으면서 [반납]을 누르며, 실제 반납일(기본 오늘)과 상태 메모를 남깁니다.
* **관리자 대리 반납이 있습니다**: 퇴사·장기 연체처럼 본인이 처리하지 못하는 건을 자산 담당자·관리자가 대신 종결합니다. `returned_by`가 반출자와 다르게 남아 대리 처리였음이 기록됩니다.
* **파손·분실은 메모로 남깁니다**: 반납 메모에 적으며, 자산의 상태(`MAINTENANCE`·`RETIRED`) 전환은 MANAGEMENT `자산 관리`의 조치입니다. 대장이 자산의 실물 상태를 바꾸지 않습니다.

## 9. 권한·RLS

* **조회는 내부 임직원 전원입니다**(`app.is_internal_user()`): "누가 무엇을 갖고 있나"는 전사가 공유해야 하는 사실입니다. 외부 스타트업·전문가·임시 게스트는 접근하지 못합니다.
* **등록은 본인 명의만 가능합니다**: `created_by = app.current_app_user_id()`를 `WITH CHECK`로 강제합니다. 남의 이름으로 반출 건을 만들 수 없습니다.
* **수정 권한자는 셋입니다**: 반출자 본인 · `management` 쓰기 권한자 · `super_admin`. 다만 **무엇으로 바꿀 수 있는가는 RLS가 아니라 전이 트리거가 판정합니다**(§5.3) — 승인은 승인권자만, 반납·취소는 본인·관리자입니다.
* **DELETE 정책은 만들지 않습니다**: soft delete만 사용합니다.
* **자산 원장은 건드리지 않습니다**: 반출대장은 `assets`에 쓰지 않습니다. "반출 중"이라는 상태를 자산 원장에 만들지 않는 이유는 §12에 적습니다.
* **감사 로그 대상이 아닙니다**: 사내 물품 대여 기록으로 개인정보 원본 조회·대량 Export·권한 변경 어디에도 해당하지 않습니다. 반출자·반납 처리자 추적은 행의 `created_by`/`returned_by`로 남습니다.

## 10. 마이그레이션 설계

`20260730180000_asset_checkouts.sql` 한 건으로 처리합니다.

1. **`assets` 확장**: `requires_approval boolean not null default false` 컬럼 추가. 기존 RLS 정책을 그대로 승계합니다(새 테이블이 아니므로).
2. **enum 신설**: `public.asset_checkout_status`(`PENDING`/`REJECTED`/`RESERVED`/`OUT`/`RETURNED`/`CANCELLED`) — 멱등 생성(`duplicate_object` 무시).
3. **원장 신설**: `public.asset_checkouts`(§5.1). check 제약 3종 —
   * `due_on >= checkout_on`
   * `(status = 'RETURNED') = (returned_on is not null)` — 반납일과 반납 상태는 함께 성립하거나 함께 없습니다
   * `returned_on >= checkout_on`
4. **겹침 차단**: `EXCLUDE USING gist (asset_id with =, daterange(checkout_on, due_on, '[]') with &&) WHERE (deleted_at is null and status in ('PENDING','RESERVED','OUT'))`. `btree_gist`는 회의실 마이그레이션이 이미 설치했습니다.
5. **인덱스**: `(status, due_on)`(뷰 탭·연체 조회의 기본 경로) · `(created_by, checkout_on desc)`(내 반출) · `(asset_id, checkout_on desc)`(물품별 이력).
6. **RLS**: 즉시 활성화하고 SELECT/INSERT/UPDATE 정책을 분리합니다(§9). DELETE 정책 없음.
7. **트리거 3종**:
   * `app.set_updated_at()` — 기존 공용 트리거
   * `app.stamp_validate_asset_checkout()`(BEFORE INSERT, `SECURITY DEFINER`) — 반출자·이름 스탬프, 자산 스냅샷(이름·품목·시리얼·지사) 복제, 후보 자격 검증(존재·미삭제·`is_portable`·`status <> 'RETIRED'`), `requires_approval`에 따른 초기 상태 강제
   * `app.validate_asset_checkout_transition()`(BEFORE UPDATE, `SECURITY DEFINER`) — 전이 허용 여부와 수행 주체 판정, `asset_id` 변경 금지, 승인·반납 시각과 처리자 스탬프
8. **뷰 신설**: `public.portable_assets`(§7). 본문에 `app.is_internal_user()` 조건을 포함하고 `authenticated`에만 `SELECT`를 부여합니다.

`SECURITY DEFINER` 함수가 필요한 이유는 두 트리거 모두 **`assets`를 읽어야** 하는데(후보 자격·승인 필요 여부·스냅샷), 반출자에게는 그 원장의 조회 권한이 없기 때문입니다. 두 함수 모두 `set search_path = app, public`으로 고정하며, 자산의 어떤 값도 호출자에게 반환하지 않고 **행에 스탬프하거나 예외를 발생시키는 데만** 씁니다. 노출되는 자산 값은 뷰가 정한 목록으로 한정됩니다.

## 12. 자산 상태와의 관계

**`assets.status`에 `반출중`을 추가하지 않습니다.** 이유가 셋입니다.

* **축이 다릅니다**: 상태 4값(`보유`/`할당`/`보수`/`폐기`)은 자산의 소유 국면이고 반출은 위치입니다. 할당된 노트북을 반출하면 두 사실이 동시에 참인데, 한 컬럼에 담으면 둘 중 하나를 잃습니다.
* **권한이 어긋납니다**: 반출 등록만으로 자산 원장을 고칠 수 있어야 하는데, 그러려면 임직원 전원에게 MANAGEMENT 쓰기 권한을 주거나 그 권한을 우회하는 함수를 만들어야 합니다. 둘 다 대가가 이득보다 큽니다.
* **파생값은 어긋나지 않습니다**: "지금 반출 중인가"는 대장에 유효한 `OUT` 행이 있는가로 언제나 정확히 답할 수 있습니다. 저장하면 두 곳의 사실이 갈라질 수 있지만, 파생하면 갈라질 자리가 없습니다.

MANAGEMENT 자산 표에 "지금 나가 있음(반출자·반납 예정)"을 파생 열로 보여 주는 것은 후속 과제입니다.

## 13. 후속 과제

* **반납 예정일 알림** — 임박·연체 건을 알림 센터와 전사 캘린더에 띄웁니다.
* **MANAGEMENT 자산 표의 반출 현황 열** — 자산 목록에서 지금 나가 있는 물건을 파생 열로 표기합니다.
* **관리자 대리 등록** — 전화·구두로 요청받은 반출을 관리자가 타인 명의로 등록하는 경로(현재는 본인 등록만 가능합니다).
* **QR·바코드 스캔 반출** — 자산 명판을 찍어 반출·반납을 처리합니다.
* **반출 통계** — 물품별 반출 빈도와 평균 대여 기간으로 보유 수량 판단을 돕습니다.

## 14. 테스트 기준

* 반출 가능 토글이 꺼진 자산과 폐기 자산은 반출 등록 후보 목록에 나타나지 않는다.
* MANAGEMENT 권한이 없는 임직원도 반출 후보 목록과 반출대장을 조회할 수 있고, 그 목록에 금액·할당 대상이 없다.
* 외부 게스트 계정으로는 반출 후보 목록과 반출대장이 모두 조회되지 않는다.
* 승인 필요 여부가 꺼진 자산을 등록하면 상태가 `예약`, 켜진 자산을 등록하면 `승인 대기`가 된다.
* 클라이언트가 상태를 `RESERVED`로 지정해 보내도, 승인 필요 자산이면 `PENDING`으로 저장된다.
* 같은 자산에 기간이 겹치는 반출을 등록하면 두 번째 등록이 거부된다.
* 반납 예정일을 반출일보다 앞선 날짜로 입력하면 저장되지 않는다.
* 승인 권한이 없는 사용자가 `승인 대기` 건을 `예약`으로 바꾸려 하면 거부된다.
* 반출자 본인이 `예약` 건을 취소할 수 있고, 취소한 기간에 다른 사람이 곧바로 예약할 수 있다.
* `반출 중` 건을 반납 처리하면 실제 반납일이 기록되고, 그 자산이 다시 반출 후보가 된다.
* 관리자가 대리 반납하면 반납 처리자가 반출자와 다르게 기록된다.
* 반납 예정일이 지난 `반출 중` 건은 연체 필터에 나타나고 경과 일수가 표기된다.
* 종결 상태(`반납 완료`·`반려`·`취소`)의 건은 어떤 상태로도 되돌릴 수 없다.
* 반출 건의 대상 자산을 다른 자산으로 바꾸려 하면 거부된다.
* 자산명을 바꿔도 이미 등록된 반출 건에는 등록 당시의 이름이 남는다.
* 마이그레이션 재실행 시 오류 없이 통과한다(멱등).
