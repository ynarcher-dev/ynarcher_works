# [3-3-1] 스타트업 풀 구분·담당자·관리현황 상세 기능 요건서

> [!NOTE]
> 본 문서는 STARTUP 기업 목록의 **구분(분류) 체계**(투자기업·보육기업·발굴기업·기타기업), **담당자 권한 모델**, **관리현황 적용 범위**를 규정하는 세부 요건서입니다. 물리 원장은 `startups` 하나를 유지하되 화면·권한 키의 소유자는 `STARTUP`이며, 본 문서의 권한 규칙은 UI가 아니라 **서버(RLS/RPC)에서 강제**함을 원칙으로 합니다.

---

## 1. 목적 및 범위

* **목적**: 스타트업을 우리와의 관계 심화 단계에 따라 4개 구분으로 분류하고, 구분에 따라 편집 권한·표시 필드를 차등화한다.
* **범위**: `startups` 마스터의 구분(`management_status`), 담당자(`startup_managers`), 관리현황(`pool_status`) 및 이들과 연동되는 목록·상세·등록 화면.
* **제외**: 스타트업의 기본 프로필/성장지표/주주/미디어 등 콘텐츠 필드 자체의 정의(기존 마이그레이션 및 상세 폼에서 관리).

---

## 2. 구분(management_status) 라이프사이클 모델

스타트업의 구분은 **관계가 깊어지는 라이프사이클의 현재 상태 한 개**로 표현합니다. 발굴 → 보육 → 투자는 관계 심화의 승격 경로이며, 기타는 사다리 밖의 별도 버킷입니다. 한 기업은 동시에 여러 구분을 갖지 않습니다(단일값).

| 코드 | 라벨 | 정의 |
| :--- | :--- | :--- |
| `sourced` | 발굴기업 | 우리 관리를 받지 않았으나 미팅한 기업. 담당자 없음. |
| `incubated` | 보육기업 | 우리 사업·활동을 통해 액셀러레이팅/보육을 받은 기업. 담당자 없음. |
| `invested` | 투자기업 | 펀드를 모아 실제 투자를 집행하고, 내부 담당자가 배정된 기업. |
| `other` | 기타기업 | 위 분류에 해당하지 않는 기타. 자유 분류 텍스트(`management_status_etc`) 병기 가능. |

> [!IMPORTANT]
> 라이프사이클·권한 판정이 "투자냐 아니냐"에 직접 의존하므로, `management_status`는 자유 텍스트가 아니라 위 **소문자 코드값 4종**으로 정규화합니다. 한글 라벨은 UI 매핑에서만 관리하며 코드값이 단일 원천입니다. 기존 한글 문자열 데이터는 코드로 이관하고, 매핑 불가값은 `other`로 격리합니다.

## 3. 구분 → 노출 규칙

STARTUP 워크스페이스의 목록 메뉴는 **스타트업 DB** 한 줄이며(2026-09-05 통합), 범위(**내 스타트업**/**전체 스타트업**)는 목록 상단 토글이, 구분은 목록의 **필터 축 하나**가 답합니다(2026-08-20 확정). 한 기업은 언제나 그 목록에 그대로 있고, 구분값은 목록의 `구분` 열과 `구분` 필터가 답합니다. 구분에 따라 갈리는 것은 '어느 메뉴에 있는가'가 아니라 담당자 모델과 표시 필드입니다.

| 구분 | 담당자 | 관리현황(pool_status) | 발굴경로 |
| :--- | :---: | :---: | :---: |
| `sourced` | 없음(공동관리) | 숨김 | 사용 |
| `incubated` | 없음(공동관리) | 숨김 | 선택 |
| `invested` | **필수(지정)** | **사용** | 숨김 |
| `other` | 없음(공동관리) | 숨김 | 선택 |

* **메뉴에서 필터로 옮긴 이유**: 분류를 메뉴로 두면 그것이 '어디에 있는가'가 되어 소재지·단계 같은 다른 축과 함께 걸 수 없고(보육기업 중 시드 단계만, 같은 질문에 답할 수 없습니다), 분류를 하나 늘릴 때마다 사이드바가 길어집니다. AC 사업구분이 2026-08-03에 밟은 경로와 같습니다. 옛 링크(`?tab=invested`·`?tab=discovered` 등)는 `스타트업 DB`로 주소까지 바로잡습니다.
* **민감정보 정책 키**: ADMIN '민감정보 관리'의 구분별 키(`startup.invested`·`startup.discovered` 등)는 이름을 그대로 둡니다 — 정책이 이 키로 저장되어 있고, 구분이 하나로 정해지는 자리(기업 상세·전역 검색의 구분별 결과)가 계속 이 키를 씁니다. 목록 두 곳은 범위 키(`startup.mine`·`startup.all`)를 씁니다.

## 4. 담당자 권한 모델

### 4.0 역할 3분류 (용어 고정)

"누가 만들었나"와 "누가 관리하나"는 별개 축입니다. 아래 세 용어는 서로 겹치지 않으며, 코드·주석·화면 라벨에서 혼용하지 않습니다(특히 생성자를 담당자 자리에 폴백 표시하지 않습니다).

| 용어 | 정의 | 저장 위치 | 성격 |
| :--- | :--- | :--- | :--- |
| **생성자** | 이 레코드를 최초로 만든 사람 | `startups.created_by` | 최초 생성 기록. 권한을 부여하지 않음 |
| **담당자** | 이 정보를 관리하는 주체 (아래 2모드) | 모드별 상이 | 관리 주체를 지칭 |
| ┗ 공동관리(비투자) | 특정인 없음. STARTUP 쓰기 권한자 누구나 관리, 수정 이력은 기여자 로그로 누적 | `entity_contributions`(역할이 아닌 로그) | 발굴·보육·기타 |
| ┗ 특정 지정(투자) | 배정된 특정인(리드 1 + 지원 N)만 관리 | `startup_managers` | 투자기업 |
| **관리자** | 시스템 전역 우회 권한 | `current_app_role() = 'super_admin'` | 위 두 축과 직교하는 예외적 전역 권한 |

> [!NOTE]
> "관리자"라는 단어는 `super_admin`(예외적 전역 권한)에만 사용합니다. 공동관리하는 주체는 "담당자"이지 "관리자"가 아닙니다. 투자기업의 담당자(특정 지정)와 생성자는 서로 다를 수 있습니다. 담당자는 목록과 상세에, 생성자는 상세의 기록 정보에 표시합니다.

### 4.1 권한 규칙

* **원칙**: 투자기업에만 지정 담당자가 존재하며, 지정 담당자와 관리자만 해당 기업 정보를 수정·비활성화할 수 있습니다. 담당자가 없는 구분(발굴·보육·기타)은 STARTUP 쓰기 권한자 누구나 편집할 수 있습니다(공동관리).
* **담당자 구조(복수)**: 투자기업은 **리드 1명 + 지원 N명**의 담당자를 가질 수 있습니다. 담당자는 전용 조인 테이블 `startup_managers`로 관리하며, 레코드 생성자(`startups.created_by`)와는 별개 개념입니다.
* **재지정 권한**: 담당자 추가·해제·리드 변경은 **관리자 또는 해당 기업의 기존 담당자**만 수행할 수 있습니다.

| 구분 | 생성(INSERT) | 수정(UPDATE) | 삭제(soft delete) |
| :--- | :--- | :--- | :--- |
| 발굴·보육·기타 | STARTUP 쓰기 권한자 누구나 | STARTUP 쓰기 권한자 누구나 | STARTUP 쓰기 권한자 누구나 |
| 투자 | STARTUP 직접 등록 불가 | 지정 담당자 + 관리자 | 지정 담당자 + 관리자 |

> [!NOTE]
> `super_admin`은 상위 헬퍼(`is_admin()`)에서 항상 우회 통과합니다. 물리 삭제는 금지되며 삭제는 `deleted_at` 소프트 삭제(UPDATE)로만 처리되어 위 수정 권한 규칙에 귀속됩니다.

## 5. 등록·승격 흐름

STARTUP 신규 등록은 `/startup/discovered/new`의 페이지형 폼에서 수행하며 **비투자 구분만** 생성합니다. 투자기업 전환은 자사 투자 집행과 분리할 수 없으므로 FUND 포트폴리오 등록 흐름이 소유합니다.

* **비투자 등록(발굴·보육·기타)**: 이름 중복을 확인한 뒤 `startups`를 생성합니다. 생성·수정 기여 이력은 원장 트리거가 남기며 담당자 행은 만들지 않습니다.
* **투자 직접 등록 금지**: STARTUP 등록 폼에서 투자기업과 담당자를 동시에 만드는 경로를 제공하지 않습니다.
* **승격(비투자 → 투자)**: FUND에서 자사 투자 건을 먼저 생성한 뒤, 리드 1명·지원 N명·관리현황·단계·폐업일(해당 시)을 `promote_to_invested` RPC로 원자 적용합니다.
* **투자기업 편집 경계**: STARTUP 상세 폼은 투자기업의 `management_status`와 `pool_status`를 payload에서 제외합니다. 전환·담당자·관리현황은 FUND 투자 흐름에서 관리합니다.

```
promote_to_invested(startup_id, lead_user_id, support_user_ids[],
                    pool_status?, stage?, closed_on?)
  SECURITY DEFINER, 트랜잭션 내:
   1) 자사 투자(investments) 존재 여부와 호출 권한 확인
   2) lead 없음 → 거부
   3) startup_managers 원자 교체
   4) management_status='invested', 관리현황·단계·폐업일 정합성 반영
```

> [!IMPORTANT]
> 투자 전환 시점에는 담당자 행이 아직 없어 행 단위 RLS의 WITH CHECK가 스스로를 막는 치킨에그가 발생합니다. FUND 투자 생성과 승격 RPC가 필요한 선행 데이터와 담당자 지정을 한 업무 흐름으로 묶어 이 문제를 제거합니다.

## 6. 관리현황(pool_status) 규칙

* **적용 범위**: 관리현황(`pool_status`)은 **`management_status = 'invested'`일 때만** 표시·편집·필터합니다. 비투자 구분에서는 목록 컬럼값을 숨김(N/A) 처리합니다.
* **무결성**: 투자가 아닌 구분에서는 `pool_status`가 NULL이 되도록 트리거로 강제합니다(투자 → 하위 강등 시 자동 클리어).

---

## 7. 권한(RLS) 설계

`startups` 원장은 STARTUP 권한 키와 투자기업 행 단위 담당자 잠금을 함께 검사합니다(소프트 삭제 UPDATE도 이 정책에 귀속).

```
-- startups UPDATE : using / with check
can_write_workspace('startup')
AND (
  management_status IS DISTINCT FROM 'invested'      -- 비투자: 누구나
  OR is_admin()
  OR EXISTS (select 1 from startup_managers m
              where m.startup_id = startups.id
                and m.user_id = current_app_user_id())  -- 투자: 담당자만
)
```

```
-- startup_managers INSERT/UPDATE/DELETE (담당자 배정·해제·리드 변경)
is_admin()
OR EXISTS (요청자가 해당 startup의 기존 담당자)          -- 관리자 + 기존 담당자
```

* **SELECT**: 담당자 존재 여부와 무관하게 STARTUP 읽기 권한자 전원 조회합니다.
* **INSERT(startups)**: STARTUP 쓰기 권한자의 비투자 생성에 사용합니다.

## 8. 화면 사양

### 8.1 목록(스타트업 DB — 범위 토글: 내 스타트업 · 전체 스타트업)

* 두 범위는 동일한 `StartupPoolTab`을 공유하며 담당 스코프만 다릅니다. 범위 토글은 `대용량 업로드` 버튼 왼쪽에 서고, 전환해도 검색어·필터는 유지하며 페이지와 선택만 되돌립니다. 구분은 화면이 고정하지 않고 필터 바의 `구분`(코드 4종 다중선택)이 좁힙니다.
* 필터 바는 표의 열 순서를 그대로 따릅니다: 소재지 → 분야 → 단계 → **구분** → 관리현황 → 업력(최소~최대).
* 컬럼 구성은 두 범위가 동일하며, 값이 구분에 따라 갈립니다.

| 컬럼 | 발굴 | 보육 | 투자 | 기타 |
| :--- | :---: | :---: | :---: | :---: |
| 담당자 | `공동관리` | `공동관리` | **지정 담당자(리드 강조), 미지정 시 "미지정"** | `공동관리` |
| 관리현황 | — | — | 사용 | — |
| 발굴경로 | 사용 | 선택 | — | 선택 |

* **생성자 vs 담당자 분리**: 목록은 현재 관리 주체를 답해야 하므로 생성자 열을 숨깁니다. 담당자 열은 비투자(발굴·보육·기타)에 `공동관리`, 투자기업에 지정 담당자(리드 1명 + `외 N`)를 표시합니다. 생성자는 상세 기본 데이터의 수정일 옆 기록 정보에만 두며 담당자 대체값으로 사용하지 않습니다.
* **내 스타트업 범위**: 목록에서 생성자를 숨겨도 이 범위의 조회는 생성자 또는 지정 담당자가 나인 기업을 함께 찾습니다. 조회 편의와 권한/표시는 별개입니다.

### 8.2 상세

* 구분에 따라 카드를 조건부 노출합니다(투자 = 담당자 카드 + 관리현황 카드, 발굴 = 발굴경로).
* 비담당자가 투자기업 상세를 열면 읽기전용으로 표시하되, 최종 차단은 서버(RLS)가 강제하고 UI는 보조 수단으로만 둡니다.

### 8.3 등록

* `/startup/discovered/new`에서 상세 편집과 같은 페이지형 폼을 등록 모드로 사용합니다.
* 신규 STARTUP 등록은 비투자 구분만 허용하며 담당자 피커를 노출하지 않습니다.
* 투자 승격과 담당자 지정은 STARTUP 상세의 단독 액션이 아니라 FUND 투자 등록/수정 흐름에서 `promote_to_invested`를 호출해 처리합니다.

## 9. 데이터 모델 변경 요약

```sql
-- (1) 구분 코드 정규화
management_status  text  NOT NULL DEFAULT 'sourced'
  CHECK (management_status IN ('sourced','incubated','invested','other'))
management_status_etc  text  -- other 자유 분류 라벨

-- (2) 담당자 조인(복수, 리드 1명)
create table startup_managers (
  startup_id  uuid not null references startups(id),
  user_id     uuid not null references users(id),
  is_lead     boolean not null default false,
  assigned_by uuid references users(id),
  assigned_at timestamptz not null default now(),
  primary key (startup_id, user_id)
);
create unique index startup_managers_one_lead
  on startup_managers(startup_id) where is_lead;

-- (3) 관리현황 투자 전용 무결성: management_status<>'invested' → pool_status = NULL (트리거)
```

## 10. 구현 작업 분해

**DB / 보안**

1. `management_status` 코드화 + CHECK + 한글→코드 데이터 이관 마이그레이션
2. `startup_managers` 테이블 + RLS + 리드 유니크 인덱스
3. `pool_status` 투자 전용 무결성 트리거
4. `startups` UPDATE 정책 교체(행 단위 담당자 잠금)
5. FUND 자사 투자 존재를 게이트로 삼는 `promote_to_invested` RPC(SECURITY DEFINER)

## 12. 열린 이슈

* **컬럼명 혼동**: `management_status`(실제 의미 "구분")와 `pool_status`(실제 의미 "관리현황")의 이름이 직관과 어긋남 — 주석/문서로 고정하되 장기 리네이밍을 검토합니다.
* **강등 정책**: 투자 → 하위 강등 시 담당자 이력 보존 범위와 배타 잠금 해제 처리 세부.
* **생성자·리드 관계**: 투자 승격 시 생성자(`created_by`)와 리드 담당자는 자동 동일화하지 않습니다. 잘못된 생성자는 ADMIN `생성자 교체`에서 사유와 감사 로그를 남기고 정리합니다.
