# [3-9-1] 게스트 통합 계정 (Unified Guest Account)

> [!IMPORTANT]
> 본 문서는 **게스트 계정의 단일 원천(SSOT)** 입니다. 계정의 발급·자격증명·사업 매핑·접근 기간·세션 맥락에 관한 판단은 모두 이 문서가 답하며, [3_4_4](./3_4_4_ac_participant_pool.md) §6.3~6.7, [3_2](./3_2_workspace_admin.md) §1.7, [3_9](./3_9_workspace_guest.md)의 해당 절은 이 문서를 승계합니다.

**확정일**: 2026-09-05 · **적용 범위**: WORKS(OFFICE·ADMIN·AC·M&A·PROJECT) + GUEST 앱

---

## 1. 목적

게스트 계정을 **사업 단위 발급에서 대상 단위 발급으로 전환**합니다. 한 기업·한 전문가에게 계정 하나를 발급하고, 사업은 그 계정에 줄로 붙였다 뗍니다.

---

## 2. 배경 — 무엇이 문제였는가

종전 구조는 "사업코드 + 이메일 + 비밀번호"의 3요소 로그인이었고, 불편의 표면은 사업코드였습니다. 그러나 원인은 코드가 아니라 **계정 자체가 사업마다 별개였다는 것**입니다.

* `guest_invitations`는 명부 행당 1건(`uq_guest_invitations_participant`)이고 **비밀번호 해시가 그 행에 있었습니다.**
* `issueGuestSession`은 초대 행의 `app_user_id`가 비어 있으면 **이메일 조회 없이 `users` 행을 새로 만들었습니다.**
* 결과: A기업이 두 사업에 참여하면 **계정 2개, 비밀번호 2개**. 코드를 두 개 안내하는 문제가 아니라 자격증명을 두 벌 안내하는 문제였습니다.
* 실패 응답이 사유를 가리지 않으므로(계정 열거 차단), 담당자도 "코드가 틀렸는지 비밀번호가 틀렸는지" 답해 줄 수 없었습니다.

파생 결함이 둘 더 있었습니다.

* **사업코드는 비밀이 아닙니다.** `guest-access-invite`가 알림톡·메일 본문에 코드를 평문으로 실어 보냅니다. 3요소 중 하나가 이미 공개값이었으므로, 코드를 로그인에서 빼는 것의 보안 손실은 사실상 없습니다.
* **새 사업에 초대되면 전화번호로 다시 들어올 수 있었습니다.** 비밀번호가 초대 행마다 있어서 새 초대 행의 `password_hash`는 언제나 비어 있었기 때문입니다. 계정으로 자격증명을 옮기면 이 구멍이 자동으로 닫힙니다.

---

## 3. 핵심 축 — 계정 · 문 · 열쇠

세 가지를 서로 다른 주체가 소유합니다. 종전에는 셋이 사업 담당자 한 사람에게 뭉쳐 있었습니다.

| 축 | 무엇인가 | 소유자 | 저장 위치 |
| :--- | :--- | :--- | :--- |
| **계정** | 이 회사·이 사람이 존재한다 | 내부 전원(생성) / ADMIN(정지·해제) | `users` + `guest_credentials` |
| **문** | 이 계정이 이 사업을 본다 | 그 사업의 담당자(PM·MEMBER) | `program_participants` |
| **열쇠** | 비밀번호 | **본인만** | `guest_credentials.password_hash` |

> [!IMPORTANT]
> **열쇠를 아무도 대신 쥐지 않습니다.** 종전에는 담당자가 비밀번호를 초기화하면 그 값(원장 연락처)을 담당자도 알 수 있었습니다. 계정이 사업마다 갈려 있을 때는 그래 봐야 자기 사업만 열렸지만, 계정을 합치면 **그 게스트가 참여 중인 다른 팀 사업까지 전부 열립니다**(포트폴리오사 제출 자료 등). 그래서 초기화를 **재설정 안내 발송**으로 바꿉니다 — 직원은 보내기만 하고, 새 비밀번호는 본인만 정합니다.

---

## 4. 계정의 키 — 이메일이 아니라 원장 행

계정을 이메일로 묶으면 **A기업 대표이면서 B사 자문인 사람**이 한 계정으로 뭉칩니다. 그런데 `users.user_type`(`external_startup` / `external_expert`)도 `company_id`도 `workspace_permissions.scope_type`(`company` / `self`)도 서로 배타라, 한 계정이 두 인격을 동시에 가질 수 없습니다.

계정 키는 **원장 행**입니다.

* `users.guest_master_table` + `guest_master_id` — `startups` 행 또는 `networks` 행
* 같은 원장 행을 가리키는 계정은 **하나뿐**입니다(부분 유니크 인덱스)
* 같은 사람이 기업 인격과 전문가 인격을 함께 가지면 **계정 2개가 정상입니다.** 인격이 다르고 권한 범위가 다르기 때문이며, 사용자가 겪는 불편은 로그인 후 목록에서 한 번 고르는 것뿐입니다(§7)
* `temporary_guest`처럼 원장 행이 없는 유형은 초대 행이 곧 계정입니다(종전 유지)

이 선택의 근거는 코드 안에 이미 있습니다 — `readLedgerIdentity`·`syncGuestName`이 *"이름의 정본은 언제나 원장"* 을 전제로 계정·초대장의 복사본을 원장 값으로 되돌리고 있습니다. 계정의 정체성도 같은 축에 둡니다.

---

## 5. 자격증명 — 별도 원장에 둡니다

비밀번호 해시를 `users`에 두지 않습니다. **`users`의 SELECT 정책은 내부 사용자 전원에게 열려 있고**(참가자 명부가 게스트 이름을 붙이려면 그래야 합니다), 거기에 해시를 두면 전 직원이 읽게 됩니다.

* 새 원장 `public.guest_credentials` — `user_id`(PK), `password_hash`, `password_set_at`, `login_attempts`, `locked_until`
* **RLS는 Default Deny 그대로 두고 정책을 하나도 만들지 않습니다.** 접근 경로는 `service_role`로 도는 Edge Function뿐입니다
* 잠금 카운터도 여기로 옮깁니다 — 종전처럼 초대 행에 세면 **초대가 3건인 사람은 잠금이 사실상 15회**가 됩니다

`guest_invitations`의 `password_hash`·`login_attempts`·`locked_until`은 이관 후 읽지 않습니다(컬럼은 남겨 두되 신규 경로가 쓰지 않습니다).

---

## 6. 로그인 — 2요소

* **아이디 = 이메일**, **비밀번호 = 본인이 정한 것 하나**. **사업코드는 로그인에서 뺍니다.**
* **초기 비밀번호는 원장 연락처(숫자만)를 유지합니다.** 계정에 비밀번호가 아직 없을 때만 유효하며, 그 시점에는 사업이 하나뿐이라 종전과 위험이 같습니다. 한 번 정하고 나면 새 사업에 추가되어도 전화번호는 더 이상 통하지 않습니다(§2의 파생 결함 해소).
* 초기 비밀번호로는 **세션을 주지 않습니다.** 10분짜리 비밀번호 설정 티켓만 발급하는 종전 방식을 그대로 씁니다.
* 실패 응답은 사유를 가리지 않고, 연속 5회면 15분 잠급니다(카운터 위치만 §5로 이동).

> [!NOTE]
> **계정 열거 관점.** 코드를 빼면 이메일 하나로 존재 여부를 물을 수 있게 됩니다. 완화는 종전과 같은 통일 응답 + 계정 단위 잠금이며, 코드 자체가 안내문에 평문으로 나가던 값이라 잃는 방어선은 없습니다.

## 7. 참여 목록과 세션 맥락

로그인이 성공하면 그 계정에 붙어 있는 **열린 참여 목록**을 돌려줍니다.

```
A기업 · 2026 액셀러레이팅        ~ 2026-12-31
A기업 · 글로벌 진출 지원          ~ 2027-03-31
전문가 홍길동 · 창업멘토링         ~ 2026-11-30
```

* **1건이면 목록을 건너뛰고 바로 진입합니다.**
* 고른 항목 하나로 세션이 고정됩니다 — **한 세션은 언제나 한 맥락**입니다.
* 0건이면 *"현재 접근 가능한 사업이 없습니다"* 를 표시합니다. 종전에는 로그인 자체가 실패해 사유를 알릴 수 없었습니다.

### 7.1 맥락 클레임의 일반화

세션 토큰의 `program_id` 클레임을 **`context_type` + `context_id`** 쌍으로 넓힙니다.

* 현재 값: `context_type ∈ { program, ma_program, project_program }`
* 장래 값: FUND 온기보고(§10)가 `fund` 등으로 들어옵니다

지금 `program_id` 하나만 있는 상태로 FUND를 붙이면 `fund_id` 클레임이 하나 더 생기고 `app.guest_*_ids()` 계열이 두 벌로 갈라집니다. **섞임을 막는 것은 계정 분리가 아니라 맥락이 언제나 하나라는 것**이므로, 클레임을 먼저 일반화합니다.

* `app.guest_session_program_id()`는 `context_type`이 사업 3종일 때 `context_id`를 돌려주고, 없으면 옛 `program_id` 클레임으로 폴백합니다(세션 수명 8시간의 전환 유예).

## 8. 접근 기간 — 계정이 아니라 줄에 붙습니다

"사업마다 기간이 다르다"가 문제가 되는 것은 기간을 **계정에** 붙일 때입니다. 계정 하나에 종료일 하나를 달면 사업이 둘일 때 답이 없습니다.

* `program_participants.access_starts_at` / `access_ends_at` — **줄마다** 갖습니다
* **기본값 = 그 사업의 종료일 + 유예 14일.** 담당자가 아무것도 채우지 않아도 기간이 생깁니다. 사업에 종료일이 없으면 개방일 + 1년
* 담당자가 그 줄에서 덮어쓸 수 있습니다(예: 평가위원 2주)
* 만료된 줄은 **목록에서 사라질 뿐** 계정과 다른 줄은 그대로입니다

기존 자동 차단은 그대로 유지됩니다 — 사업 종료·취소, 담당자 수동 차단, 초대 만료(1년), 세션 8시간.

## 9. 권한표

| | 내부 사용자 전원 | 사업 담당자(PM·MEMBER) | ADMIN |
| :--- | :---: | :---: | :---: |
| 계정 발급 | O | O | O |
| 전체 계정 조회 | O (연락처 마스킹) | O | O (원본) |
| 비밀번호 **재설정 안내 발송** | O | O | O |
| 자기 사업에 매핑 | X | O | X |
| 자기 사업 게스트 화면 구성(메뉴 공개) | X | O | X |
| 자기 사업 접근 기간·차단 | X | O | X |
| **남의 사업 줄 손대기** | X | X | X |
| **계정 정지·해제** | X | X | O |
| **비밀번호 값을 아는 것** | X | X | X |

* **계정 발급이 전원에게 열려도 안전한 이유**: 발급만으로는 아무것도 보이지 않습니다. 사업에 매핑되기 전까지 로그인해도 §7의 0건 화면입니다. 대상도 임의가 아니라 **NETWORKS·STARTUP 원장에 이미 있는 행**으로 제한되며, 발급은 감사 로그에 남습니다.
* **정지·해제가 ADMIN인 이유**: 한 계정이 여러 사업에 걸리므로 담당자가 정지하면 남의 사업까지 죽습니다. 담당자는 자기 사업 줄만 닫습니다.

## 10. FUND 연동 전망

[3_5](./3_5_workspace_fund.md) §4의 투자기업 사후관리 입력은 GUEST 앱을 창구로 합니다. 그 상대는 **투자기업**, 즉 `startups` 원장 행이며 AC 사업 참여기업과 같은 실체입니다.

* 계정 키가 원장 행이므로 **같은 계정이 그대로 재사용됩니다.** 계정을 쪼갠 채로 붙이면 그 회사에 자격증명 4벌을 안내하게 됩니다.
* 참여 목록에 `A기업 · 2026년 3분기 사후관리` 한 줄이 늘어날 뿐이며, 고른 항목 하나만 보이는 것은 동일합니다.
* 필요한 선행 작업은 §7.1의 클레임 일반화 하나입니다.

## 11. 화면

### 11.1 OFFICE > 게스트 계정 (신설)

내부 사용자 전원이 접근합니다. ADMIN 워크스페이스는 관리자만 들어가므로, 전원에게 열리는 발급·조회 창구는 전사 허브인 OFFICE에 둡니다.

* **목록**: 이름 · 유형 · 소속 기업 · 이메일(마스킹) · 참여 사업 수(열림/전체) · 최근 접속 · 계정 상태
* **계정 발급**: 원장(기업·전문가) 검색 → 이름·이메일·연락처 자동 채움 → 발급. 사업에 붙지 않은 상태로 생성됩니다
* **재설정 안내 보내기**: 게스트 본인 연락처로만 링크가 나갑니다. 누른 사람 화면에는 아무 값도 표시되지 않습니다
* 정지·해제는 없습니다(ADMIN 전용)

### 11.2 ADMIN > 게스트 계정 (기존 화면 승계)

[GuestAccountPanel](../../apps/works/src/features/admin/GuestAccountPanel.tsx)을 그대로 쓰되 §11.1의 기능을 포함하고 다음이 추가됩니다.

* 연락처 **원본** 표시
* **정지·해제** — 사유 필수, `GUEST_ACCOUNT_SUSPEND` / `GUEST_ACCOUNT_RESTORE` 감사 로그, `session_version` 증가
* 정지해도 `login_status`는 건드리지 않습니다(사업 운영 기록이지 계정 상태가 아닙니다)

### 11.3 사업 상세 > 참가자 명부

담당자는 **계정 발급 페이지에 가서 확인할 필요가 없습니다.** 명부 행이 이미 원장에 연결되어 있으므로 계정 유무를 시스템이 압니다.

```
참가자              계정                    접근
──────────────────────────────────────────────────────
A기업 (김대표)      O 있음 · 2026-08-14     [연결]
B기업 (박대표)      - 없음                  [연결]
C기업 (이대표)      O 있음                  열림 ~2026-12-31
```

* **버튼은 `연결` 하나**입니다. 계정이 있으면 이 사업을 붙이고, 없으면 만들어 붙입니다. 담당자는 둘을 구분할 필요가 없습니다
* 여러 행을 선택해 일괄 처리할 수 있습니다(종전 `participantIds` 배열 경로 유지)
* 접근 기간은 §8의 기본값으로 자동 설정되며 이 화면에서 수정합니다

### 11.4 GUEST 앱 사이드바 상단

```
┌──────────────────────────┐
│ A기업                    │
│ 2026 액셀러레이팅    ▾   │
├──────────────────────────┤
│  공지사항 / 자료실 / ... │
└──────────────────────────┘
```

* `▾`를 누르면 §7의 참여 목록이 펼쳐지고, 고르면 **아래 메뉴가 통째로 갈립니다**
* 재로그인이 필요 없습니다(맥락 전환 = 토큰 재발급)
* 참여가 1건이면 `▾` 없이 이름만 표시합니다

### 11.5 NETWORKS·STARTUP 원장 상세

기업·전문가 상세에 `게스트 계정 있음 / 없음` 한 줄을 표시합니다. 원장에서도 계정 유무가 바로 확인됩니다.

## 12. 데이터 모델 변경

| 대상 | 변경 |
| :--- | :--- |
| `users` | `guest_master_table text`, `guest_master_id uuid` 추가 + 부분 유니크 인덱스 |
| `guest_credentials` (신설) | `user_id` PK, `password_hash`, `password_set_at`, `login_attempts`, `locked_until`. **정책 없음(Default Deny)** |
| `program_participants` | `access_starts_at timestamptz`, `access_ends_at timestamptz` 추가 |
| `guest_invitations` | 자격증명 컬럼은 신규 경로에서 읽지 않음(보존) |

### 12.1 데이터 이관

같은 원장 행을 가리키는 기존 `users` 행이 여럿이면 **가장 먼저 만들어진 행으로 병합**합니다.

1. `guest_invitations` → `program_participants` → (`master_table`, `master_id`)로 계정을 묶습니다
2. 대표 계정을 정하고 `users.guest_master_*`를 채웁니다
3. 그 계정을 가리키던 참조(`program_participants.user_id`, `guest_invitations.app_user_id`, `workspace_permissions.user_id`, 게스트가 남긴 기록의 작성자)를 대표 계정으로 재배선합니다
4. 흡수된 계정은 **물리 삭제하지 않고** `is_active=false` + `deleted_at`으로 재웁니다(물리 삭제 금지 원칙)
5. 병합된 초대 행들 중 **가장 최근에 설정된 비밀번호**를 `guest_credentials`로 옮깁니다

> [!WARNING]
> 이관은 게스트 수가 적은 지금이 가장 쌉니다. FUND 연동(§10) 이후에는 재배선 대상이 늘어납니다.

## 13. 완료 기준 (Definition of Done)

1. 같은 기업이 두 사업에 걸려도 `users` 행이 하나이고 비밀번호가 하나다
2. 로그인 화면에 사업코드 칸이 없다
3. 로그인 후 참여가 2건 이상이면 목록이 뜨고, 1건이면 바로 진입한다
4. 사이드바에서 맥락을 바꾸면 재로그인 없이 메뉴가 갈린다
5. 한 맥락에 들어간 상태에서 다른 사업의 데이터가 어떤 경로로도 조회되지 않는다
6. 명부의 `연결` 한 번으로 계정 유무와 무관하게 매핑이 끝난다
7. 접근 기간이 지난 줄은 목록에서 사라지고 계정과 다른 줄은 살아 있다
8. 비밀번호 재설정은 안내 발송만 가능하며, 발송자 화면에 어떤 값도 표시되지 않는다
9. 담당자가 남의 사업 줄을 조회·수정할 수 없고, 계정을 정지할 수 없다
10. 이관 후 게스트가 남긴 기존 기록의 작성자가 대표 계정으로 이어진다

## 14. 미결 사항

* **OFFICE 배치**: 발급·조회 창구를 OFFICE에 둔 것은 "내부 사용자 전원"이라는 권한 요건에서 도출한 결정입니다. NETWORKS에 두는 대안이 있으나, 대상이 `startups`(STARTUP 워크스페이스)와 `networks` 양쪽에 걸쳐 있어 한쪽 원장 워크스페이스에 두면 나머지가 어색해집니다.
* **재설정 링크 발송 채널**: 실발송 어댑터가 아직 없습니다(PROGRESS 백로그). 어댑터 도입 전까지는 발송 시도만 기록되고 실제 전달은 되지 않으므로, 그 기간에는 담당자가 원장 연락처 재확인으로 안내합니다.
